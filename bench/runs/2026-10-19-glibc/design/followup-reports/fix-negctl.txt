SUMMARY: I applied the fixes from inv-wd and inv-mem to test/native/negative-control.sh, the only repo file I edited. md5 went from 7d191b40 to 452d869b; it is LF with 0 CR, and `sh -n` passes on bash 5.3, bash 4.4 and dash.

What changed:
- **notimer:** it now picks its sabotage by `$OCLJ_OS`. Windows keeps the old lj52_wd_fire text. Linux removes `lj52_wd_inject(M);` from lj52_wd_thread. A preprocessor guard stops the run if the sabotage is in code this host compiles out.
- **nohyst and unbounded:** MEMTEST_CFLAGS is now set and cleared on lines of its own instead of as a prefix to the function call, and it is cleared once at the top of section 4.
- **New 4.31 guard:** it reads each arm's W16 cap count from that arm's own output and requires the arms that did not sweep 96 caps to be exactly nohyst and unbounded, both at 8.

inv-mem's product_issue was NONE, so no allocator expectation was changed or made per-platform. The expected id sets are the same on every host.

Full runs [M], each against a fresh md5-checked mirror of the named build:
- **AlmaLinux 8:** the edited script gives 57 PASS, 0 FAIL, NEGATIVE CONTROL: PASS (10m08s). The original script on the same objects gives 51 PASS, 5 FAIL, which reproduces the chain.
- **Ubuntu:** the edited script gives 57/0, PASS. The original gives 55 PASS and 1 FAIL (notimer only). This was the first full negative-control.sh run on Ubuntu.
- **Windows (win-fixed):** the edited script gives 57/0, PASS.

The RESULT labels are identical on all three hosts, and the old runs' 56 labels match the chain's Windows run.

Proof that the new checks can fail [M]:
- With the case labels swapped, the notimer guard stops with SETUP FAIL, exit 2, on all three hosts (empty tu.err). The block as written is caught on all three (exit 99, ALARM).
- The 4.31 guard fails on the chain's Alma work dir, on my old Alma run and on inv-mem's A-1. It passes on every new run and on inv-mem's A-2. On synthetic copies it fails for nohyst at 96 caps, for a reshaped W16 line, for a new default of 64 caps, and for a 16-cap leak.

product_issue: NONE.

PRODUCT_ISSUE: NONE. With the harness fixed, the shipped allocator/RAM-cap machinery and the watchdog behave the same on AlmaLinux 8, Ubuntu and Windows. Every arm catches its sabotage with the same expected ids and exit status on all three hosts: 57/57 PASS each in run-alma-new, run-ubuntu-new and run-win-new [M]. The Linux watchdog enforces deadlines: wdcanon passes on all three, and with the old Windows text that Linux compiles out, W2 was still interrupted at 55.6 ms (Alma) and 55.7 ms (Ubuntu) [M].
