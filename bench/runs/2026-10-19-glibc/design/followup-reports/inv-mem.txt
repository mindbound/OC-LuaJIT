SUMMARY: The four allocator arms that fail on AlmaLinux 8 (rawverdict, nolook, refusalkeeps, noarm) fail because of a shell difference in the test harness. Neither the platform nor the RAM-cap machinery is the cause. negative-control.sh lines 565 and 577 write `MEMTEST_CFLAGS="-DW16_N=8 -DW16R_N=8" sabotage_mem nohyst|unbounded ...`, putting the assignment in front of a shell FUNCTION call. Alma's /bin/sh is bash 4.4.20 in POSIX mode, and there that assignment stays set after the function returns. Git Bash's sh (bash 5.3.15, POSIX mode) and Ubuntu's dash scope it to the call [M persist.sh]. So on Alma, every mem arm after nohyst (23 arms) was built with the W16 sweeps cut from 96 caps (0..6080 B, one whole 6 KB step of the fill) to 8 caps (0..448 B) [M build/native/negctl/*/run.log, the chain's Alma work dir]. The four arms' expected sets were measured at 96 caps. Their W16-family refusals first land at offsets past +448 B (+5952, +5824, +5888, +4416, +5760, +1920), so 8 caps miss them [M]. Measured with the four sabotages extracted (arms.sh): at 96 caps all four match their expected sets on Alma, Ubuntu and Windows. At 8 caps all three platforms give exactly the sets the chain logged on Alma (rawverdict W16R W16RL W20 W20L; nolook none; refusalkeeps W19; noarm W17). The fix: set and clear MEMTEST_CFLAGS on separate lines, clear it once at the top of section 4, and add a guard (4.31) that reads the cap count from each arm's own W16 line. Proven: the guard FAILS on the chain's real Alma artifacts, in a fresh Alma run of the original script and in a Windows run with a leaked value. With the fix, all of section 4 plus the guard passes on Alma (32/32, the first time every mem arm ran at its intended cap count on Linux), and the subsets pass on Windows and Ubuntu. Verdict for all four arms: (a) TEST CALIBRATION. More precisely a harness portability bug, not a Windows-calibrated expected set; the expected sets are correct on every platform.

PRODUCT_ISSUE: NONE. On Linux the shipped RAM-cap machinery (verdict, proof, refusal, window, reserve) behaves the same as on Windows. At the cap counts the arms were written for, every sabotage fails the same check ids on AlmaLinux 8, Ubuntu and Windows, with the same first-failing cap offsets, stall/down counts and request sizes; only the absolute base heap differs by a constant of about 150-170 B [M arms.sh runs]. The canonical mem suite passes 86/0 on Linux, and the fixed section 4 passes 32/32 on Alma (A-2). Accounting uses LuaJIT's requested block sizes, not OS pages (lj52shim.c:402-446) [S].
