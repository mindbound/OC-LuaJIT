RECOMMENDATION: Build safe-point. Shim-only is safer to write but has two failures that safe-point avoids by construction: credit lost across eris, and allocate-first retries that never reach a checkpoint. vm-faithful should not be built.

Order, with each stage gated by its own fail-first against cb29485d:

(0) Instrument first.
- Make the CAP-* lines print stat positions 2, 3, 5, 7, 8, 9, 15 and 16 plus the new _OCLJ_GCWALL.
- Show it reading -1 or absent on cb29485d, and showing stepmul 0 mid-fill.
- Fix negative-control.sh's stale paths.

(1) Scalar-only fixes shared by all three designs.
- Every refusal arms (shape 2).
- Park reset in the armed branch (GCSpause, unchanged white, threshold > gc.total).
- Keep an ARMCAP valve that counts only growth attempts, as an alarm. Safe-point deletes it.
- Gate on W5a/b/c and W2b.

(2) The hook carrier as the only new collection site, before any overdraft.
- lj52_gc_request / atsafe / the hook prefix / unhook.
- The build gate allows exactly one `lua_gc(...LUA_GCCOLLECT)` inside atsafe, with awk-checked call sites. g1-g3 must each fail with their own message.
- Test this FIRST: a stress build that files a request on every growing allocator call, so a full collection runs at nearly every instruction boundary. Run it with LUA_USE_ASSERT and freed-block poisoning over mem_test, shim_test, wd_test (35/0, W6b 20 ms) and TRACE_CHUNK, plus one harness arm.
- Canary: a sabotage calling atsafe from inside lj52_alloc must crash. If it does not, the gate is blind.
- Also measure recording aborts. callhook calls lj_trace_abort, which leads to penalty_pc and possible blacklisting. A JIT-hot fill loop must still hold its trace after the wall. If it does not, skip the inject while J->state != LJ_TRACE_IDLE and rely on the checkpoint carrier.
- Also handle a request filed during atsafe's own fullgc. A string-table shrink crossing the cap would leave gc_req stale and lose the hook carrier until the next outermost arm.

(3) Overdraft bands.
- Sandbox band of 16 KiB with credit close/open; kernel band of 32 KiB keyed on cur_L / wd_depth.
- Gate on X1 (including JIT-hot and record shapes), X2, X3, X8, X9.
- Graft shim-only's W7 creep test, with a 'credit = total' sabotage that must fail.
- Add a reload test: fill to OOM, keep the data, persist/unpersist with OC's lift and restore, then the next push must succeed.

(4) P2: gc_next hysteresis and the back-off.
- Gate on X4 and X6, then the 60-run capacity matrix from the main session under nohup plus Monitor: 0 recovery-refused, 0 down, t_last5 at most 3x stock, at most 3 collections per batch.

(5) P4: kernel site 13 (jit.off first, jit.on after the baseline yield).
- Only after (4) passes the 192 KB idle gate on arm E.
- For the flush predicate, consider grafting vm-faithful's rule (flush when resident trace metadata is at least the post-cycle headroom) instead of the fixed 32 KiB, which is not cap-relative.

If safe-point's hook coupling is rejected, build shim-only instead, with two fixes:
- (a) Derive RESERVE from used > total + G/2 on the first call after settotal/load, so credit survives eris.
- (b) Add a test of an allocate-first pcall retry loop, and accept it as a documented residual.

QUESTIONS:
- All three designs grant first and decide later. With safe-point, a request inside a pcall that goes past the cap by up to 16 KiB succeeds, and 'not enough memory' lands on the program's next allocation, possibly outside the pcall. Is that acceptable, or should a request that alone exceeds headroom plus the band be refused on the spot?
- Safe-point needs build-native.sh's collector gate re-scoped to allow exactly one lua_gc(LUA_GCCOLLECT) in the shim, reachable only from the watchdog hook and from arm/disarm. Do you accept lifting that invariant, which has held since 8c279a3?
- With the JIT off during kernel init (arm E), kernelMemory becomes 164 393 B, deterministic but about 10 KB below stock's 174 605 B, so users get slightly more RAM than on stock. Keep that, or pad the figure to match stock?
- Safe-point ties the GC's safe point to the watchdog's count hook. With a foreign hook installed, for example the stock-kernel fallback, grants are disabled and behaviour reverts to today's refusals. Is that coupling acceptable?
- Finalizers, which run only when sandbox __gc is allowed, would now also run inside the hook-carrier's full collection at an instruction boundary, earlier than today and still without a deadline, as on stock. Is that acceptable?

Rationale, against the weighted requirements: shim-only alone meets R7 (no gate change, no watchdog change, zero VM lines). Every advantage safe-point has on R2 and R4 comes from parts that can be lifted out of it without its costly hook machinery. The hook carrier buys only one thing: recovery when no checkpoint runs. The order below measures whether that is needed before paying the review cost of touching the deadline path.

Order:

0. Fix the instrument first.
   - Fix the stale paths in negative-control.sh.
   - Make the CAP-* lines print _OCLJ_GCSTATS positions 2, 3, 5, 7, 8, 9 and 15, plus the new stats.

   - From the designs: W5a, W5b and W5c (park); W2b and W2c (refusal with no arm); W1 and W1j (recovery); W3 (trace exit); W4 (cadence, with a same-run ratio).
   - Three tests none of the designs had, placed where the mitigations break:
     - (i) Catch the refusal, build 'err: '..err, drop the data, then allocate. This must pass. By reading it fails under safe-point's close-credit rule.
     - (ii) A recovery with no checkpoint (X1f-style array growth), sized to exceed G/2 at the 192 KB cap. This is expected to fail in stage 1, and documents the residual.
