1. LUAJIT INTERNALS
======================================================================================

1.0 How every refusal travels [code]
  - The shim returns NULL (SH :415 C mode, :486 legacy).  lj_mem_realloc or
    lj_mem_newgco then calls lj_err_mem (LJ lj_gc.c:873-875, :887-889).
  - lj_err_mem (LJ lj_err.c:813-844) pushes the PREALLOCATED, fixed "not enough memory"
    string (LJ lj_state.c:202).  It does not allocate.  It then calls lj_err_throw(L,
    LUA_ERRMEM).
  - lj_err_throw (LJ lj_err.c:768-771) first does lj_trace_abort(g), i.e.
    J->state &= ~LJ_TRACE_ACTIVE (LJ lj_trace.h:45).  An ERRMEM anywhere therefore aborts
    any recording in progress, asynchronously (LJ lj_trace.c:751-753).
  - An ERRMEM never calls an xpcall message handler.  Only lj_err_run does, for runtime
    errors (LJ lj_err.c:898-919).  So OpenOS's and OC's handlers (traceback, process.lua's
    {msg, traceback}, init.lua's msgh) see the bare string and add no traceback.  PUC 5.2
    is the same: luaD_throw(LUA_ERRMEM) bypasses the handler.  An ERRMEM raised INSIDE a
    message handler that is running for a runtime error becomes LUA_ERRERR "error in
    error handling" (LJ lj_err.c:815-816).
  - Every refusal is counted by lj52_gc_refused (SH :1251-1263) BEFORE anyone catches it.
    Unless HOOK_GC, a host GCSTOP, norefuse or gc_busy is in force, it then:
      * sets gc_odstate = RESERVE;
      * sets gc_win = 0 (the window shuts, and a standing verdict is consumed);
      * arms a cycle.
    It does all three whoever ends up catching the error.  That is the defect's mechanism.

1.1 A1 -- THE TRACE RECORDER: the one absorber that is silent and of the VM's own making

 1.1.1 What happens to an ERRMEM during recording [code]
  - Recording is driven by lj_trace_ins (LJ lj_trace.c:770-778):
        while (lj_vm_cpcall(J->L, NULL, (void *)J, trace_state) != 0)
          J->state = LJ_TRACE_ERR;
  - Entry points:
      * lj_dispatch_ins, once per instruction while recording (LJ lj_dispatch.c:425-432);
      * lj_dispatch_call (:494-503);
      * lj_trace_hot, for hot loops and calls (lj_trace.c:781-796);
      * trace_hotside, after a trace exit (:799-811);
      * lj_trace_stitch (:814-823).
    Every one of them goes through this loop.
  - A refusal inside trace_state unwinds to that cpcall, which returns LUA_ERRMEM.  The
    loop sets LJ_TRACE_ERR and calls trace_state again.  Case LJ_TRACE_ERR (:754-760) runs
    trace_abort (:585-656):
      * e stays LJ_TRERR_RECERR, because the error object is a string, not a number (:596-597);
      * a root trace's start pc is penalised (penalty_pc :392-417).  Past PENALTY_MAX
        blacklist_pc rewrites the loop to ILOOP/IFORL, and it stays interpreted for the
        prototype's life;
      * a stitched trace's link is blacklisted on the FIRST abort (:612-613);
      * the vmevent "abort" fires (:618-647; only with a handler attached);
      * the trace number is dropped;
      * L->top-- REMOVES THE ERROR OBJECT (:653);
      * the state returns to IDLE (:757-759).
    lj_trace_ins then returns normally, and the interpreter executes the instruction it
    was about to execute.  Nobody retries the refused request.  The program cannot
    observe any of this.
  - The recorder's nested protected calls all re-throw to that outer cpcall:
      * rec_mm_concat_cp (LJ lj_record.c:2182-2190);
      * rec_stop_stitch_cp (lj_ffrecord.c:144-157);
      * recff_metacall_cp (:467-471);
      * recff_xpcall_cp (:566-571);
      * cploop_opt (lj_opt_loop.c:425-445, which rethrows anything that is not a numeric
        trace error);
      * cpsplit (lj_opt_split.c:831-837; 32-bit only).
    So a refusal anywhere in recording, optimisation or assembly ends in trace_abort.
  - trace_abort allocates nothing itself, except through the vmevent with a handler
    attached (1.4).
  - An ERRMEM from the PROGRAM's own instruction while recording is active also goes
    through lj_err_throw -> lj_trace_abort.  The program's pcall gets it as usual, and the
    next lj_trace_ins hits "Trace aborted asynchronously" (:751-753).  Not an absorber.

 1.1.2 What the recorder allocates: (e) [code; sizes are estimates]
  All of it goes through the state's allocator, so it is charged and can be refused:
  - IR buffer, grown only, kept across traces:
      * lj_ir_growtop reallocs it to 2x (LJ lj_ir.c:73-86), delta = current size;
      * lj_ir_growbot allocates a NEW 2x block and then frees the old one (:89-115), so
        the request is the whole new size;
      * 8 B per IRIns, starting at 32 entries: requests of 256 B up to tens of KB.
  - Snapshot buffers, grown only:
      * lj_snap_grow_buf_ (lj_snap.c:38-46): growvec of SnapShot;
      * lj_snap_grow_map_ (:48-58): realloc to 2x, minimum 64 entries of 4 B.
  - The trace vector: trace_findfree -> lj_mem_growvec (lj_trace.c:65-80), up to
    maxtrace x 8 B.
  - One GCtrace copy per completed trace: lj_trace_alloc, called from the assembler
    (lj_trace.c:122-140).
      * Size: GCtrace + IR + snapshots + snapmap;
      * d2-verdict measured 568-668 B in the probe; larger traces take KBs.
  - Loop optimisation scratch: lps.subst, nins x 2 B, freed straight after
    (lj_opt_loop.c:281, :426).
  - Constant strings made at record time:
      * argv2str (lj_ffrecord.c:85);
      * :489 and :1085;
      * folding (lj_opt_fold.c:506, :694-758, :916), which also grows g->tmpbuf.
      * Tens of bytes each.
  - Machine code is VirtualAlloc'd (lj_mcode.c), and neither the allocator nor the shim
    charges it.
  Could A1 be the one refused at a top?  Yes, and it is more exposed than the program
  [inference]:
  - it runs on the sandbox's thread (cur_L = J->L), so it gets the sandbox's credit AND
    THE WINDOW's lend (SH :1229-1244);
  - near a top its requests (KB-scale IR doublings, trace copies) are refused by
    used + delta > S + 4 KiB where the program's 50-300 B objects still fit;
  - the verdict refuses "the next crossing", whoever makes it.  A verdict delivered to
    the recorder is wasted: trace_abort drops it, while lj52_gc_refused has already shut
    the window (gc_win = 0) and opened RESERVE.
  - On the kernel thread (kernel loops are recorded after site 13 turns the JIT back on,
    K :1619) a recorder refusal past the kernel's slice is ALSO absorbed, and also opens
    the sandbox's reserve tier.

 1.1.3 What the program learns: (c)
  Nothing.  The only traces are the shim's refusal counter, the tier change, the
  penalty/blacklist, and harness-only vmevents.

 1.1.4 (d) Can the shim tell?  Not with what it reads today; yes with one more read, or
       exactly with a 2-line patch
  - J->state != LJ_TRACE_IDLE is NOT enough [code].  After lj_record_ins returns, the state
    stays LJ_TRACE_RECORD while the interpreter executes the recorded instruction,
    INCLUDING the program's own allocations (TNEW, CAT, FNEW...).
  - g->vmstate is not enough either: it stays ~LJ_VMST_RECORD over that instruction.
    d2-verdict.md:568, :831 said so, and it is correct: vm_record / vm_inshook reset
    nothing (LJ vm_x64.dasc, the ->vm_record path).
  - What does separate them [code]: THE INNERMOST C FRAME of the running thread.
      * lj_vm_cpcall writes SAVE_NRES = -savestack(L, L->top), always negative
        (LJ vm_x64.dasc:656-670): "Neg. delta means cframe w/o frame".
      * The frames Lua code normally runs on are positive or zero:
          - vm_resume sets nres 0 (:575-589); every coroutine, including the kernel's
            resumes, enters there;
          - vm_pcall / vm_call set nres1 >= 0 (:610-623).
      * lj_vm_cpcall also sets cur_L = L (:670), so
            cf = cframe_raw(gco2th(gcref(g->cur_L))->cframe);  cframe_nres(cf) < 0
        (LJ lj_frame.h:280, :294) means: "this allocation is made by C code running
        directly inside an lj_vm_cpcall".  It is two loads with no allocation, on the
        running thread's own stack.
  - Who runs inside an lj_vm_cpcall in a live machine:
      * the recorder (absorbs);
      * trace_exit_cp (re-throws to the program, sec. 1.2).  It overwrites nres with the
        sentinel -2*LUAI_MAXSTACK*sizeof(TValue) = -1 048 000 (lj_trace.c:840), which no
        savestack offset can equal, so it can be excluded exactly;
      * cpgrowstack (A5/A6);
      * cpparser (A7);
      * cpwriter (A8).
  - A recorder test without a patch would be [inference, not checked]:
        J->state != LJ_TRACE_IDLE  &&  cframe_nres(cf) < 0  &&  cframe_nres(cf) != the
        exit sentinel  &&  g->vmstate != ~LJ_VMST_C
    The parser, checkstack and dump cpcalls are reached only through C functions, which
    run with vmstate C (vm_x64.dasc:4908/4918).  A non-recordable function is aborted, or
    stitched (state back to IDLE), BEFORE the interpreter executes it.
    This has to be shown to FAIL on a program allocation inside an active recording
    before it can be trusted.
  - EXACT, with a patch in the native/luajit/patch-*.sh style: a field in jit_State (or a
    shim-visible per-state counter), incremented before and decremented after the while
    loop in lj_trace_ins.  The loop always returns normally, because the cpcall catches
    everything, so the pair is exception-safe.  It costs two instructions per recorded
    bytecode.

1.2 A2 -- TRACE EXIT AND SNAPSHOT RESTORE: not an absorber [code]
  - lj_snap_restore can allocate:
      * stack growth (LJ lj_snap.c:968);
      * sunk allocations rebuilt with lj_tab_new / lj_tab_set / lj_cdata_newx
        (:846, :894, :927).
  - It runs under trace_exit_cp (lj_trace.c:835-842), which forces errfunc = 0.
  - On error lj_trace_exit returns -errcode (:921-923).  vm_exit_interp checks it
    (vm_x64.dasc:2529) and calls lj_err_trace (:2578-2582; lj_err.c:932-939), which
    RE-THROWS the ERRMEM from the right C frame into the program.
  - The program's handler receives an ordinary "not enough memory".  mem_test W3 tests
    this.
  - After the exit:
      * the vmevent TEXIT (harness only);
      * an unprotected lj_gc_step when the GC is in atomic or finalize (:942-945).  That
        step can throw only through S2;
      * trace_hotside, which is the recorder (A1).

1.3 lj_trace_flushall: allocates nothing [code]
  - lj_trace_flushall (lj_trace.c:276-302):
      * returns 1 under HOOK_GC;
      * unlinks the traces;
      * frees machine code through lj_mcode_free (VirtualFree);
      * sends the vmevent "flush" (only with a handler).
  - It cannot be refused outside a handler.  The shim's flush at the safe point
    (SH :1370-1412) "raises nothing".  Recorder buffers survive a flush.

1.4 A3/A4 -- FINALIZERS AND VM EVENTS [code]
  - Finalizer: gc_call_finalizer (LJ lj_gc.c:503-535):
      * lj_trace_abort, then hook_entergc (HOOK_GC);
      * threshold = LJ_MAX_MEM;
      * lj_vm_pcall on vmthread(g);
      * an error goes to the ERRFIN vmevent and is otherwise dropped (:527-534).
    The shim gives no credit under HOOK_GC and lj52_gc_refused returns before opening the
    reserve (SH :1258).  ALREADY HANDLED, except that the refusal counter still counts it
    (SH :1254).
    Reachability on our architecture:
      * LuaJIT never runs __gc on tables;
      * the sandbox has no newproxy;
      * the kernel's sgc wrapper (K :740-770) is therefore inert;
      * jnlua's gcjavaobject (JN :2121-2135) is C and does not allocate.
    So in practice NO finalizer can refuse.
  - VM events: lj_vmevent_call (LJ lj_vmevent.c:38-60):
      * sets hook_vmevent (HOOK_VMEVENT);
      * runs the handler on vmthread(g) under lj_vm_pcall;
      * on error prints "VM handler failed: ..." to stderr and drops it.
    The handler exists only when something calls jit.attach.  The sandbox has no `jit`
    (the kernel keeps it: K :20-21, :1619); the harness attaches __ocljTrFn for capacity
    runs (HA :4128-4130).  That handler's own allocations are ~0: it updates existing keys
    with numbers, and the "start"/"stop"/"abort"/"flush" strings are anchored as its keys.
    (d): YES, by g->hookmask & HOOK_VMEVENT, or by cur_L == vmthread(g).  The shim does
    NOT exclude it today, so such a refusal would open the reserve tier.  Harness only.

1.5 A5-A8 -- C-LEVEL PROTECTED CALLS THAT CONVERT THE ERROR [code]
  - lua_checkstack -> lj_state_cpgrowstack (LJ lj_api.c:102-115, lj_state.c:163-170)
    swallows the ERRMEM and returns 0.  Its callers then turn that into something else:
      * luaL_checkstack -> ERRRUN "stack overflow (%s)" (lj_api.c:117-121);
      * unpack -> "too many results to unpack" (lib_base.c:237-238);
      * jnlua's checkstack -> Java IllegalStateException("stack overflow") (JN :2009-2011).
        The only catch for that is Machine.scala:987-989, crash("Error.InternalError").
  - coroutine.resume grows the child's stack under cpgrowstack and re-raises the message
    as ERRRUN IN THE RESUMER (lib_base.c:629-632).  For the kernel's own resume that is
    pcall(main), i.e. down.
  - load(): lj_load runs the parser under lj_vm_cpcall (lj_load.c:72), so load returns
    nil, "not enough memory".  This matters for package.delay (OS lib/package.lua:104-110):
    it clears mt.__index BEFORE dofile, so a refused delay-load leaves the library without
    its delayed functions for good (event.timer and event.onError live in
    full_event.lua).
  - string.dump: cpwriter (lj_bcwrite.c:448) -> "unable to dump given function"
    (lib_string.c:144).
  - (d) for all four: partly.  They are the cpcall frames of 1.1.4 with vmstate C.  The
    program sees them, but converted, not as ERRMEM.

1.6 S1/S2 -- THE STRING TABLE: a refusal no program owns, large and sticky [code + inference]
  - lj_str_alloc LINKS the new string into the table, increments num, and only THEN grows
    the table (LJ lj_str.c:300-309):
        if (g->str.num++ > g->str.mask) lj_str_resize(L, (g->str.mask<<1)+1);
  - lj_str_resize allocates a fresh vector of (newmask+1) x 8 B on GC64 (:129-140) through
    lj_mem_newvec, which throws.
  - A refused growth therefore:
      (i) raises ERRMEM in whatever code made the string: the fill, paint, OpenOS or the
          kernel;
     (ii) leaves num > mask, so EVERY later new string, from anyone, retries the same
          doubling and is refused again.  This continues until a sweep (lj_str.c:360
          decrements num) brings num <= mask, or until the request fits.
  - Sizes: the table grows from 256 slots, and a booted OpenOS plus a string fill is
    plausibly at 2K-8K slots, so the request is 32-128 KB [estimate].  At the 192 KB stick
    (cap ~509 KB, G = 32 KB) a 32 KB doubling is past the burst tier (G/2) and can be
    lent only from RESERVE.
  - This answers u2-stalls' "[not checked] whether such a refusal leaves num > mask":
    from the code, it does.
  - It is a candidate for refusals beyond the paint's in the downs (5/4/3 against pf = 1):
    one doubling refused, then a refusal per new string anywhere until the next sweep
    [inference, not checked].
  - S2: the sweep shrinks the table (lj_gc.c:695-696), also as a NEW allocation, inside
    lj_gc_step.  It can throw out of any GC check, including the unprotected step after a
    trace exit.  Rare: it runs only after 3/4 of the table's strings died, i.e. after a
    sweep that freed a lot.
  - (d): YES, cheaply.  At refusal time g->str.num > g->str.mask, plus a request equal to
    2*(mask+1)*sizeof(GCRef), identifies S1.
  - PUC 5.2 grows the table BEFORE creating the string (PUC lstring.c:116-127), behind a
    full emergency GC.  It is just as sticky, but only on live data.

1.7 Other unprotected internal allocations [code]
  These are refused where they happen, and the error goes to whoever is running.  None of
  them is an absorber:
  - stack growth (lj_state.c growstack, lj_dispatch.c call_init);
  - g->tmpbuf growth for concatenation and format.  The buffer is halved in every atomic

7. WHAT THE RESERVE TIER MUST KEEP DOING
======================================================================================
  - Its purpose (SH :945-963) is "catch, format the message, drop, carry on".  The program
    that caught its OWN refusal at the burst top must be able to allocate between the
    catch and the drop.
  - MT W8 (W8_CHUNK :555-562, case :1866-1894):
      * the program builds 'err: ' .. tostring(err) while the data is still held, and a
        cycle (a proof) runs IN BETWEEN and finds the heap still past the cap;
      * then it drops, then string.rep(256) and {1,2,3};
      * "err: not enough memory|256|3" must come back.
    So the reserve must SURVIVE a proof that precedes the drop.  This is why "close at the
    next proof regardless" is ruled out: d2-final.md's sabotage 4.12 closereserve fails W8,
    W11, W16Rj, W19 and W7k.
  - MT W2b/W2c (:1600-1623): a refusal arms the collector from ANY headroom, and the
    retry succeeds once the garbage is collected.  That is the arm in lj52_gc_refused.
    It is independent of the tier and should stay on every lever.
  - MT W11 (:2124-2156): a fresh record (an eris load) whose live data is already past
    total + G/2 takes RESERVE with no refusal (SH :1182-1185).  That is a separate rule;
    keep it.
  - W7/W7k/W19 (no ratchet, the kernel's room past the window) and W16R/W16Rj (the
    probe's program after an absorbed first refusal, MT :750-795) check the reserve tier's
    ceiling and landings.  Any lever that changes the reserve re-scopes them.
    w16r_rec judges the tier from the shim's refusal COUNT (MT :798-806) and says a
    recorder-absorbed refusal opens the reserve; that changes under L1.
  - The bytes it actually needs: W8 ~50 B; the probe's done branch ~40 B plus a paint
    that is already in a pcall; a typical recovery that prints its error through the tty
    ~1-3 KB [estimate].  Today's reserve gives G/2 more: 16 KB at the 192 KB stick, up to
    256 KB at caps of 8 MB and above.

  - luaM_realloc_ (PUC lmem.c:73-94): a NULL from the allocator, while the GC is running,

9. CANDIDATE LEVERS (not designed in depth)
======================================================================================
  L0  INSTRUMENT FIRST.  Settle where the 5/4/3 refusals of the downs went.  Keep a
      fixed-size per-state ring in the shim, written in lj52_gc_refused with no
      allocation:
        - delta;
        - tier;
        - lj52_gc_kernel;
        - J->state;
        - g->vmstate;
        - cframe_nres(innermost) < 0, and whether it equals the exit sentinel;
        - hookmask & (HOOK_GC|HOOK_VMEVENT);
        - str.num > str.mask;
        - wd_depth;
        - and, with L5's redirect, the JNI depth.
      Covers: attribution of A1, A4, A5-A8, S1, J1.  Risk: none, since nothing is
      decided by it.  It extends u2-stalls §5.3's three fields.
  L1  A RECORDER REFUSAL OPENS NO RESERVE, SHUTS NO WINDOW, CONSUMES NO VERDICT.  Count
      it separately.  Arm or not: arming is harmless but costs a cycle.
      Identify it by the 2-line lj_trace_ins patch (exact), or by 1.1.4's cframe test.
      Covers: A1, on the sandbox and the kernel thread.  Hermetically A1 was 35 of 204
      second chances under THE WINDOW and 563 of 796 under "prevent" (j2-practice.md:
      236-238).  In-machine it is unmeasured; the JIT-on/JIT-off contrast (u2-stalls
      §4: 18/76 against 3/40) points to it.
      W8/W2b/W2c: unaffected.  W8 runs jit.off(), and its refusals are the program's.
      Risk: W16Rj re-scoped (sec. 7); stage C's ~2% JIT-on "surplus" goes, which
      d2-prevent §7.5 already showed was this artifact.
  L1b The recorder gets NO credit and NO window: refused at the cap.  The window's
      4 KiB is then never spent on JIT metadata, and no verdict is ever delivered to the
      recorder.
      Risk:
        - no trace completes past the cap, because every one needs a GCtrace copy;
        - each refusal penalises its loop (penalty_pc), so hot loops near the wall get
          BLACKLISTED for their prototype's life.  patch-penalty-scrub clears entries
          only on prototype death, and lj_trace_flushall clears the cache but not the
          ILOOP rewrites;
        - pair it with a patch that does not penalise an ERRMEM abort.  Not LJ_TRERR_RETRY
          (an immediate retry would loop); a normal hotcount reset.
  L1c Alternatively the recorder gets its OWN budget past the cap, a fixed slice outside
      the sandbox's tiers, like KSLICE.  The JIT keeps working at the wall, and only the
      flush reclaims what it holds.
      Risk: the absolute bound grows by that budget, and W7/W7k/W19's arithmetic moves.
  L2  HOOK_VMEVENT handled like HOOK_GC: no credit, no reserve.  Covers: A4, harness
      only.  Risk: none.
  L3  THE RESERVE'S SIZE: a fixed R past the refusal point, not total + G.
      - After a refusal at used u, the program may reach min(u + R, total + G) until a
        proof finds the heap under the cap.  R is granted once per reserve episode, so
        repeated absorbed refusals cannot creep up to total + G.
      - R should be a few KiB: above what catch-format-drop needs (sec. 7), far below
        today's G/2 of 16-256 KB.
      Covers: EVERY absorber, including the ones no test can identify (H1, O1, O2, K3,
      J2).  A second chance buys R bytes instead of up to 256 KB, so the fill's next
      refusal lands within R of the first, most likely inside its next batch.
      Risk:
        - W8 OK (~50 B);
        - W2b/W2c unaffected;
        - W11 must keep its separate rule;
        - W7/W7k/W19/W16R/W16Rj re-scoped;
        - a program whose recovery allocates more than R before dropping is refused
          mid-recovery.  Stock would refuse it too unless garbage covered it.
  L4  THE RESERVE'S LIFETIME, BY RESUME: close a refusal-opened reserve at the first
      proof after the sandbox's next resume.  The shim sees resumes: lj52_wd_arm, with
      wd_depth going 0 -> 1.
      Covers: H1, O1 and O2 in the probe's shape.  The absorbed refusal is followed by a
      yield, and the next batch then starts with the reserve closed.
      Risk:
        - W8 unaffected (no yield between catch and drop);
        - a recovery that yields before it drops is refused after the yield, as on stock.
          Yields include os.sleep, an indirect (synchronized) component call, and a
          print that hits the direct-call budget;
        - W16R/W16Rj's "carried into the reserve" case becomes "carried back to the burst
          tier".
  L5  THE RESERVE'S LIFETIME, BY PCALL ENTRY: close it at the next SANDBOX pcall or xpcall
      entry after the refusal.  That needs a kernel patch: K :808-814 and :858-884 call a
      shim C function.  It costs one C call per pcall, against the wrapper's existing
      Java call to computer.realTime.
      Covers: O1, since the dispatcher's next pcall(callback) closes it before the next
      step, and the fill is then refused inside its own pcall.
      Risk:
        - recoveries that use pcall, or the kernel's spcall wrappers (unicode.*,
          computer.pushSignal), close their own reserve;
        - this is the most invasive lever.
      The same redirect gives L0 its JNI depth, and could stop J2's soft-returned
      refusals from opening the reserve.  Their value is small: in the probe gpu.set's
      results allocate nothing.
  L6  CLOSE AT THE NEXT PROOF REGARDLESS: REJECTED by evidence.  The 4.12 closereserve
      sabotage fails W8, W11, W16Rj, W19 and W7k (d2-final.md).
  L7  DO NOT REFUSE THE INTERN TABLE'S GROWTH (S1).  Either charge it under a
      norefuse-style window, or patch LuaJIT so that a failed growth keeps the old table
      (the load factor just rises past 100%) instead of throwing after the string is
      already linked.
      Covers: a large, sticky refusal source no program owns, a candidate for the extra
      refusals.  Verify with L0 first.
      Risk:
        - charging it moves the excursion bound by the table's size, at most
          16 B x live strings;
        - the non-throwing patch costs nothing but chain length;
        - S2 (the sweep's shrink) can simply skip the shrink on failure.
  L8  "OPENED ONLY BY REFUSALS THE PROGRAM CAN SEE".  This is L1 + L2 + (L5's JNI part),
      plus leaving the HOOK_GC exclusion as it is.  Every identifiable case is covered.
      It CANNOT reach the Lua-level absorbers (H1, O1, O2, K2-K4, O3-O4).  Those are
      sandbox code on the sandbox's thread, and only L3, L4 or L5 bound them.
      Identifying them by walking the Lua stack to the nearest FRAME_PCALL and reading
      its caller's chunk name is possible without allocating.  It is fragile: every
      sandbox pcall goes through the kernel's wrapper, and errors cross coroutines as
      return values, not by unwinding.  It is also a policy choice about who "the
      program" is.  Not recommended.
