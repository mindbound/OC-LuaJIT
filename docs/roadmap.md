## v0.5 — ocelot-brain harness *(the development environment)*

Adopted 2026-09-01 after evaluation ([research/ocelot-brain.md](research/ocelot-brain.md)).
**This inverts the previous plan.** v1 assumed the JNI bridge would be validated
in-game; it is validated here instead, and Minecraft is touched only at v1's
final line. The reason is epistemic rather than convenience: this project's
standing weakness is that every verification claim was one step removed from
reality, and this closes that gap for the machine layer — where all the
remaining risk lives. Minecraft was never going to give us a differential
oracle against real Eris. ocelot-brain does.

- [ ] **The false-green guard, before anything else runs.** ocelot-brain sets
  `includeLuaJ = !isAvailable`, so a failed native load silently substitutes
  LuaJ — which has no Eris, so every persistence test then passes **vacuously**.
  This is the single failure mode that manufactures false confidence. A shared
  harness base class asserts the architecture is what we think it is and dies
  loudly otherwise. A base class, not a convention.
- [x] **Run the smoke suite on OUR architecture, not only on the dropin — DONE 2026-09-16.** Every persistence, deadline, RAM-cap and bytecode-gate milestone had been measured with `NativeLua52Architecture` over a substituted `libjnlua52`; `OcljSmoke` pinned that class unconditionally and its `guard()` refused `ocljit.native=additive`. So the port was proven to BOOT and never to SAVE — and that is not a quibble, because `LuaStateLuaJIT` redeclares the five natives `PersistenceAPI` drives (`lua_dump`, `lua_pushbytearray`, `lua_tobytearray`, `lua_next`, `lua_rawset`) into our own JNI symbol family. The suite now derives the architecture from the same switch as the native, and the additive arm reports **32 checks, 0 failures** (`bench/runs/2026-09-16-additive-smoke/`). Two silent defects fell out: `setArchitecture` rejects any class absent from `MachineAPI`'s registry, so `register()` is required rather than optional as the adapter claimed; and `m2-persist-flush-observed` was gated on the literal `"luajit"`, skipping it for the shipped shape. The fingerprint now carries `class=`, which is the only discriminator between the dropin and additive arms — same VM, different JNI family, identical `_OCLJ_NATIVE` marker.
- [ ] Vendor ocelot-brain at a pinned commit. No published artifact; consumed as
  a git submodule + sbt composite build, with three dependency jars fetched by
  URL from asie.pl — vendor those too. MIT, compatible with ours.
- [x] ~~Split `LuaJITArchitecture` into a host-agnostic core plus two thin
  shells (~60 lines each).~~ **DONE 2026-09-15, and there is no shared core:
  there is nothing left to share.** The plan assumed we would implement
  `Architecture` and factor out what the two hosts have in common. We do not
  implement it at all. `NativeLuaArchitecture` is a `public abstract class` in
  both OpenComputers and ocelot-brain whose **only** abstract member is
  `factory()`, and each host's own three VMs are one-line subclasses of it; so
  are ours. The four divergences the plan enumerated — `recomputeMemory`'s
  body, the memory getters, the NBT write, the imports — are all **inherited**,
  which is why they stopped being our problem. What each adapter supplies is a
  `LuaStateFactory` subclass: `version()`, `create()`, `openLibs()`.
  `version()` is the load-bearing one — it determines the library filename the
  host's own loader hunts for, which is why the additive artifact is named
  `libjnluajit52-*`. See [research/shipping-model.md](research/shipping-model.md),
  "The port is a subclass, not a port".
  - harness adapter: `test/native/OcljArch.scala` — **runs**; AxisOS boots to
    `localhost login:` on it (`bench/runs/2026-09-15-census-axisos-additive/`)
  - mod adapter: `src/main/java/io/github/astronfo/ocluajit/arch/` — written
    and compile-checked against the pinned OC jar; **not run**, that needs
    Minecraft
- [ ] **Bound the `@Mod` OpenComputers dependency.** We now subclass
  `li.cil.oc.server.machine.luac.NativeLuaArchitecture` and `LuaStateFactory`,
  OpenComputers' implementation classes, pinned only at COMPILE time. The `@Mod`
  string is `required-after:OpenComputers;` with no version range, so an
  OpenComputers whose shape changed gives a `NoSuchMethodError` at class load —
  a startup crash for the player, not a build failure for us. Not guessed at:
  a malformed FML range stops the mod loading outright, and nothing here can run
  FML to validate one. Settle it in `runClient`.
- [ ] Pin `NativeLua52Architecture` for every comparison. **Three languages are
  in play**: ocelot defaults to 5.3, GTNH ships 5.2, we are LuaJIT 5.1 +
  `LUA52COMPAT`. Any 5.3/5.4 result is inadmissible.
- [ ] **The differential oracle.** Same host, same workload, same save point:
  persist with real Eris on PUC 5.2 and with `eris_lj` on LuaJIT, then compare
  accept/refuse decisions and post-restore observables. This is the strongest
  test available to this project, and nothing else can produce it.
- [ ] Tests are "run until a condition, with a timeout" — never "step N ticks".
  Lua runs on a thread pool against a wall clock, so tick-counting tests flake,
  and a flaky persistence test is worse than none. Saves cannot tear:
  `Machine.save` and `Machine.run` share a lock.
- [ ] **Two one-run measurements, both left open by the MineOS census** ([research/mineos-census.md](research/mineos-census.md)): (a) boot MineOS on ocelot-brain with the machine's RAM set to its own declared floor (2048 KB) and try to save -- this either promotes "the save may not fit" to a ranked defect or retires it, and it is the only census row whose fix would be in OUR C code (the write buffer doubles through the host allocator and `lua_pushlstring` then copies it again, so peak is live + buffer + blob); (b) capture a save point with an application WINDOW open -- the stock baseline covers only an idle desktop, and three of MineOS's four interesting shapes exist only once a window is open.
- [ ] **Mirrored host state is an atomicity obligation.** MineOS keeps a full Lua-side framebuffer mirror and renders only the diff, so its `currentFrame*` is a cached belief about the screen used to SUPPRESS work. Not a defect today -- stock OC and ocelot-brain satisfy it by construction (one lock, both halves in the same NBT) -- but our architecture must never break it: one lock, one instant, never restore one half without the other, never pair a stale component NBT with a fresh blob after a failed or retried save. Measured consequence of breaking it: ~64% of the desktop missing permanently, `isRunning=true`, `crashes=0`, `lastError=null`, and it re-saves cleanly.
- [ ] Record the three ocelot-brain defects that will otherwise be misread as
  ours: `Integer` signal loss (`Machine.scala:800-814` has no
  `java.lang.Integer` case and falls through to `setByte(-1)`),
  `new Memory(ExtendedTier.Creative)` throwing on insert, and `brain.conf`
  replacing rather than overriding config.

**What a green harness run does NOT prove**, and this matters more than what it
does: it is not Minecraft (no energy, no `SaveHandler` deferral or world-save
ordering, no tile-entity lifecycle, no inventory/driver resolution — which is
precisely the one method whose body differs between the two `Architecture`
interfaces, so `recomputeMemory` is structurally unexercisable here), and it is
not GTNH. Deeper still: it cannot prove the two things the shape census says
actually kill real machines — PatchGuard-style `tostring(f)` fingerprinting and
unrebased `computer.uptime()` deadlines. Both are true of real Eris too, so the
harness will show us passing exactly where stock OpenComputers also fails,
which is comforting and irrelevant.

## v1 — Working architecture, interpreter-only

The goal: OpenOS boots and runs on the LuaJIT architecture, with the JIT compiler deliberately left off (CCLuaJIT parity: ~1.5–3× vs PUC 5.3, zero trace-safety risk while the plumbing matures).

- [x] **HOW THIS SHIPS — RESOLVED, and it is our own `Architecture`, not native substitution** ([research/shipping-model.md](research/shipping-model.md)). Everything proven so far was proven by SUBSTITUTING our native under OpenComputers' own PUC-Lua architecture (`debug.forceNativeLibPathFirst`, which is real in shipping GTNH OC at `LuaStateFactory.scala:200-210`, not just in the harness). **That can never be a product, for a structural reason**: OC reads its config and `System.load`s its native in the same `preInit` (`Proxy.scala:32` then `:74`, with `init()` in each `LuaStateFactory` object's constructor), and we declare `required-after:OpenComputers`, so FML sorts us after it — there is no moment at which our code could set the key. It is also a `debug.*` key a player would hand-edit, has no IMC hook (OC's `IMC.java` offers ten, none for natives), and is destructive rather than additive: our DLL would have to be *named* `libjnlua52-windows-x86_64.dll` and every computer in the world would switch at once with no way back. **Keep it as the benchmark/CI harness — that is what it is for.** The product is `api.Machine.add`, which OC's own source calls out for exactly this: *"This allows providing architectures without implementing a custom CPU item."* Players sneak+right-click a CPU to cycle architectures (`CPULike.scala:28-48`); the choice is stored on the ItemStack and **degrades gracefully if our mod is removed** (`DriverCPU.scala:52-57`); and because OC registers in preInit and we register in init, we can never become the silent default. `OCLuaJIT.java` already registers correctly and `LuaJITArchitecture` already has the `@Architecture.Name` and the required `Machine` constructor. **THREE THINGS THIS ALSO DE-RISKED, each previously an assumption**: GTNH 1.12.58's `machine.lua` differs from the harness's by ONE line in 1548 (`realTime = computer.realTime`); `patch-machine-lua.lua` applies cleanly to the real GTNH kernel (4 sites, exit 0, and it refuses rather than guessing when an anchor misses); and `LuaStateFactory` is a line-for-line port between the two. **ocelot-brain is representative.** Cost of the build-out: of the ten `Architecture` methods, 4 are trivial, 1 small, `initialize` is 20 lines fronting ~823 lines of `ArchitectureAPI` glue, and 4 are hard — `runThreaded` (~107 lines, the yield-classification state machine, and it must self-enforce `Settings.timeout`), `runSynchronized` (a strict stack-shape protocol whose violation crashes the computer), and `save`/`load` (the only parts reaching outside the API, for `SaveHandler` and the internal `Machine.state`). **It is a diff-port, not a from-scratch write**: ocelot-brain's `NativeLuaArchitecture` is ~85% identical to OC's, with OC's original lines left commented above each replacement at all four persistence sites.
- [x] **Watchdog kernel delivery — SOLVED 2026-09-16, by replacing what initialize() loaded rather than how it loads.** `NativeLuaArchitecture.initialize()` loads the kernel from a fixed path in **OpenComputers'** resource domain, and the harness only got its patched kernel in by shadowing that path on a classpath it controls — which a mod cannot do, since FML orders mod jars for us and OC's jar holds that exact resource. Two routes were rejected before the third: **overriding `initialize()` outright is impossible**, because four of its sixteen lines are `apis.foreach(_.initialize())` and `apis` is private with no accessor in either host; and **intercepting `debug.sethook` in the native**, which would need no kernel of ours at all, founders on `machine.lua:47` calling `debug.sethook(coroutine.running(), checkDeadline, "", 1)` — the same function as the three deadline arms with a different count — so telling them apart from C is a heuristic that mis-fires silently where `patch-machine-lua.lua` refuses loudly. What works: let `super.initialize()` do all of its work, then drop the kernel thread it left on the stack, load ours from **our own** resource domain (`/assets/ocluajit/lua/machine.lua`), and make a thread of it again. Six lines. Proven in the harness with the patched kernel present ONLY at our path and nothing at OpenComputers': `_OCLJ_KERNEL=watchdog`, 147 traces against ~2500 under the standing hook, sandbox loop 0.0047 s against 0.47 s, 32 checks 0 failures. The mod-side copy is the same sequence through OC's public `lua()` accessor (ocelot-brain hides it behind `private[machine]`, so the harness reaches it reflectively) and is compiled, not run.
- [ ] **The deadline watchdog MISSED ENTIRELY in 2 of ~6 runs under host load** (`fires=0`: the timer-queue callback was never delivered inside a 15 s window, so a runaway sandbox loop would not have been interrupted at all). A watchdog that is usually on time is not a watchdog; this is a reliability property, not a latency one, and it needs its own measurement before any JIT work leans on it.
- [x] **`d-autorun-counter-live` fixed 2026-09-16 — and it was the boot wait, not the milestone.** It failed in every stock-KERNEL arm (`additive+stock`, `luajit+stock`) with `nonce=<missing>` and `counter -1`. The cause was one level up: the boot loop waits for the shell prompt AND the autorun's first line, but capped at a flat 600 ticks, and OpenComputers' standing count hook makes boot roughly a hundred times slower — so the loop left on its timeout with the shell up and the autorun line not yet printed, `c-openos-shell` passed (it asserts only the prompt), and `d` failed describing the symptom. Both waits now follow the roadmap's own rule, *wait until a condition with a timeout*: the cap is sized for the slowest legitimate arm (it only binds when something is wrong, so it costs the fast arms nothing), `d` waits until the counter ADVANCES rather than stepping a fixed 60 ticks, and `c` now says which way its loop left. Measured after: `counter 9 -> 29 in 10 of 2000 ticks` — the counter had been advancing all along.
- [ ] **Decide what a stock-KERNEL arm should ASSERT, now that one can finish.** Fixing the boot wait let `additive+stock` run to completion for the first time, and it exposed `p0-compute-checksum: FAIL -- mandelbrot CHECK=too_long_without_yielding`. That is not a defect: under the standing hook our VM genuinely cannot compute the reference workload inside OC's deadline, which is precisely the "before" picture hook-vs-jit.md exists to show. But it means a documented control arm still reports SMOKE FAIL — now for the true reason rather than a bogus one. The harness already has the right pattern for this (`k5-baseline-has-no-watchdog`, `m1-baseline-has-no-mcode` assert the ABSENCE that defines a baseline), so the fix is to invert `p0` for stock-kernel arms rather than to relax it. Left undone deliberately: turning a real failure into an expected pass is a measurement-semantics decision, not a cleanup.
- [ ] **Licensing and attribution — both files are wrong and the jar ships one of them.** The root `LICENSE` still reads `Copyright (c) 2021 Johann Bernhardt`, the GTNH ExampleMod template author; `src/main/resources/LICENSE`, which goes INSIDE the jar, is an unfilled template (`Copyright (c) [year] [fullname]`). Separately, the shipped artifacts now bundle third-party code with no attribution: LuaJIT (MIT, Mike Pall), OC-JNLua (MIT), and `serializer/eris_lj.c`, a derivative of Eris. Needs the project's own copyright line and a NOTICE/THIRD-PARTY file covering what the jar actually contains. Blocking for any public release.
- [x] **Native packaging — DONE 2026-09-16.** The VM now reaches the player: `build.gradle.kts` stages `build/native/dist/libjnluajit52-*` into the jar at `assets/opencomputers/lib/`, which is where OpenComputers' own `LuaStateFactory` resolves a classpath library (we subclass that factory rather than write a loader). `build-native.sh` collects every ADDITIVE artifact into `dist/` — never the dropin — so building on several platforms accumulates and one jar carries them all. Verified three ways: native present → it is in the jar; **no** native → `./gradlew build` still green with a clear log line, which is what CI needs since the runner cannot build a native; and `-Pocljit.nativesDir` pointed at the dropin directory → **refused**. That last guard took three attempts to make fireable — a relative `File()` resolved against the daemon's CWD, then a `Copy` with no matching sources was skipped `NO-SOURCE` taking its `doFirst` with it — so it lives in its own always-running task now. Nothing is checked in; binaries stay out of git.
- [x] **Package the patched kernel into the jar — DONE 2026-09-16.** `native/kernel/build-kernel.sh` extracts `assets/opencomputers/lua/machine.lua` from the OpenComputers jar **pinned in dependencies.gradle** (read from that file, not "whatever jar is lying around"), runs `patch-machine-lua.lua` over it, and writes `build/native/kernel/machine.lua`; `build.gradle.kts` stages that into the jar at `assets/ocluajit/lua/`, alongside the native. Verified: **GTNH's** kernel is the one patched — it carries `realTime = computer.realTime`, ocelot-brain's does not — and the jar holds both assets (47607 B kernel, 787740 B native). With neither present `./gradlew build` is still green and says what is missing and what that costs, which is what CI needs since the runner has neither a C toolchain nor a Lua interpreter. The step asserts its OUTPUT rather than the patcher's exit status: the `_OCLJ_KERNEL` marker present, `_OCLJ_WATCHDOG` read, exactly 3 `watchdog.arm` sites and exactly 3 surviving `debug.sethook` calls — a kernel that silently lost one arm site would leave that third path on OpenComputers' standing hook, and nothing else would notice. Also fixed while here: the patcher's success line reported `#src` AFTER substitution, so it printed `47162 -> 47607` for a 46483-byte input; it now reports the original.
- [x] **Cross-platform natives: the BUILD is portable as of 2026-09-16; the SHIM is not.** `native/build-native.sh` now detects the host and derives everything from it — the artifact name (`libjnluajit52-linux-x86_64.so`), the JNI `jni_md.h` subdirectory, the linker flags (`--enable-stdcall-fixup` is PE-only and an error on ELF), and **`-fPIC` spliced into the LUAJIT build**, without which a `BUILDMODE=static` archive will not link into a shared object on x86-64 ELF. The LuaJIT and object trees are per-platform too (`luajit-$PLATFORM`, `obj-$PLATFORM`), because they were one shared directory and the Windows build leaves the `luajit.exe` that both the harness and `build-kernel.sh` run. Proven on WSL Ubuntu 22.04: LuaJIT builds clean with PIC in 21 s, `host = linux-x86_64 (lib*.so, jni_md in linux/)`, and the Windows build is unchanged (89 exports, `LuaStateLuaJIT_*`=87, `LuaState_*`=0).
  - The **postflight** was the careful part and is now one reader with two backends and a single set of assertions, so neither platform can be waved through on weaker checks than the other. It had to branch: `nm -D` on a PE DLL prints "no symbols" and **exits 0**, so a naive port would have counted zero `LuaState_*` and called an additive build clean. The reader is checked for emptiness first, for the same reason. It earned its keep immediately — it caught the first version of itself matching objdump's `RVA` column header as a 90th export.
- [x] **A LINUX watchdog backend — DONE 2026-09-16, and the Linux native builds and passes its regression suite.** Not "POSIX": `pthread_condattr_setclock` is absent on macOS, so a Darwin build would have to put the deadline condvar on `CLOCK_REALTIME` and inherit an NTP-step hazard on a live deadline. The `#error` narrowed rather than vanished, and macOS gets its own backend when there is a machine to build and test one on. **Shape:** one parked thread per `lj52_mem` in `pthread_cond_timedwait` on a `CLOCK_MONOTONIC` condvar; the mutex that thread holds across `lj52_wd_inject` **is** the blocking cancel, and it is strictly stronger than `DeleteTimerQueueTimer` — afterwards no injection can even START, because only the Lua thread sets `wd_due`. Chosen over `timer_create` (glibc spawns a thread per expiry; 20/s per firing machine), `SIGEV_SIGNAL` (a signal handler inside a JVM that owns SIGSEGV, and `lj_dispatch_update` is not async-signal-safe) and `timerfd`+epoll (wins at scale but needs a process-global registry keyed by machine, and still needs the per-machine mutex). Costs no syscall per arm or disarm in the steady state, which matters because both run on every sandbox coroutine resume. **Measured: `wd_test` 32/32 on Linux and 32/32 on Windows**, including W2 (a 50 ms deadline interrupts a compiled `while true do end` at 55.1 ms), W6b (4M iterations in 12.8 ms with 1 trace, against ~900 ms and ~200 traces under a standing hook), W9c (the re-fire restores a hook cleared behind the watchdog's back) and W13a (1 s of hook-per-instruction with ~20 re-fires and no `HOOK_ACTIVE` wedge — the failure the atomic-OR discipline exists to make impossible).
- [ ] **The `fires=0` finding is still open, and CPU contention is NOT its cause — measured 2026-09-16.** Both backends were run under the same reproduction attempt: 48 busy loops on 16 cores, 3x oversubscription, `wd_test` unchanged. **Linux fired 6 of 6** (W2 at 55.9-73.7 ms against a 50 ms deadline) and **Win32 fired 5 of 5** (55.0-71.6 ms). Since the backend that HAS the fault passes this test, the test does not reproduce the fault, and the Linux result is **not** evidence of immunity — the same shape as the N4 "regression" that evaporated once PUC was measured on the same workload. Worst lateness under load was ~24 ms on either backend, against ~5 ms quiet.
  - **Where to look instead:** the original `fires=0` was seen in the ocelot-brain HARNESS, not in standalone `wd_test` — a JVM with 100+ threads, its own GC pauses and OC's per-machine executors. Reproduce it there, with the watchdog stats read out per run, before attributing it to anything.
  - The design's claim that delivery being DERIVED rather than registered makes a lost wake inexpressible remains plausible and unproven. It cannot be proven by a test the old backend also passes.
- [x] **THE FIRST IN-GAME RUN — 2026-09-16, and the adapter works.** Installed into a real ~200-mod GTNH-based instance on **OpenComputers 1.12.61-GTNH** (we pin 1.12.58; the skew is inert — `machine.lua` is byte-identical between them and all three classes we subclass have identical opcode streams, `ldc`/`ldc_w` width aside). Forge loaded the mod, `Found a compatible native library: 'OpenComputersMod-1.12.61-GTNH-jit52-libjnluajit52-windows-x86_64.dll'` and `Registered the LuaJIT architecture with OpenComputers.` one millisecond apart — that first line only logs after `System.load` AND a real throwaway state construct+close, so the native ran inside a Forge JVM. Architecture selectable on the CPU (`Lua 5.4 -> Lua 5.2 -> LuaJ -> LuaJIT`, our `Machine.add` appended after OC's preInit four, which is also why removing the jar falls back to **Lua 5.3**). OpenOS 1.8.9 installed and booted at 16384k RAM at the pack's stock `ramScaleFor64Bit=1.8` — so the 1-in-6 boot failure recorded at roadmap:122 did NOT reproduce, though on far more RAM than that measurement used, and the emergency collector has landed since; treat that item as untested rather than fixed. Identity confirmed three ways from inside the sandbox: `computer.getArchitecture()` = `LuaJIT`, `string.dump` header = `LJ`, `tostring(rawget)` = `function: builtin#12`.
  - **THE JIT WORKS IN MINECRAFT, measured.** 4M iterations of `x = x + i % 7` in **0.0065 s cpu** and 20M in **0.0296 s** — 615 and 676 M iter/s, near-linear (5x work, 4.55x time, slightly sublinear as trace warmup amortises). The same shape of loop measured **0.473 s** under OC's standing hook, so this is ~70x past the thrashing case. Both checksums verified exact (11999998, 60000003). Compute half only: the bimodal finding stands, and a component-bound test in-game will be flat by design.
  - Measurement note: `computer.uptime()` is tick-derived, so anything under 50 ms reads 0 — the first run's `real=0.0000` was the resolution floor, not a failure. `os.clock()` is in the sandbox and reports machine CPU time; on the 20M row `real=0.0500` against `cpu=0.0296` shows it correctly excluding unscheduled ticks.
- [x] **THE `_ENV` GAP — found in-game, and the compatibility audit was wrong.** `lua` died with `lua_shell.lua:14: attempt to index global '_ENV' (a nil value)`. LuaJIT is API/ABI-locked to 5.1 and cannot implement `_ENV`; `feasibility.md:68` and `report-compat-and-perf.md:28,93` asserted OpenOS never reads it. **It reads it at eleven sites across five files.** Both documents are now corrected in place rather than quietly edited.
  - **The silent half was worse than the crash.** An unbound global reads as nil, so `boot/01_process.lua:68`'s `env = _ENV` set the init process's env to nil, `lib/process.lua:32` propagated it down the whole tree, and `machine.lua`'s own `env or sandbox` default then handed **every program the raw sandbox**. Per-process environments were collapsed machine-wide since first boot, with nothing raised anywhere.
  - **The obvious fix is wrong and was rejected on evidence.** `sandbox._ENV = sandbox` alone resolves everywhere (every OpenOS env chains to `_G`) while answering with the sandbox instead of the chunk's own environment — silently breaking `.install` floppies' documented `_ENV.install` contract, letting program globals escape the shell's shadow table into `_G`, and making the `lua` REPL's require cache inject every module typed into the sandbox globals permanently. Established with an executable replica of `sandbox.load` + OpenOS's `intercept_load` + `shell.lua:21` + `process.lua:52`, run on our own `luajit.exe`; 9 of the 11 sites have a non-sandbox `_ENV`.
  - **Shipped fix:** two patch sites. Per-chunk `rawset(env, "_ENV", env)` in the sandbox `load` wrapper (raw accessors because OpenOS envs carry `__index`/`__newindex` that would otherwise hide the key or misdirect the write), plus `sandbox._ENV = sandbox` as the base case for kernel-loaded chunks such as the BIOS. `build-kernel.sh` asserts the per-chunk site **by name** — a bare `grep _ENV` would pass the wrong fix — and the check was proven to fail against a kernel carrying only the base case.
  - **VERIFIED IN-GAME 2026-09-16, and verified DISCRIMINATINGLY.** A loading `lua` shell proves nothing here — the wrong one-site fix would also make `lua_shell.lua:14` succeed. So: at the REPL `_ENV == _G` is **false** and `_ENV.print ~= nil` is **true** (a distinct env that still chains), and a program setting a global leaves `rawget(_G, ...)` **nil** — the containment check the one-site fix cannot pass. Deployment note learned the hard way: `NativeLuaArchitecture.load` opens with `lua.setTop(0)` and unpersists the saved kernel, so a machine RESTORED from a save keeps the kernel it was persisted with. The native is unchanged by this fix, so a stale blob is not rejected either — swapping the jar under a running machine looks exactly like the fix failing. Power the computer off before swapping.

LuaJIT GC64 needs more: the OC kernel alone measures ~320 KB. Measured on a 1024 KB machine booting OpenOS 1.8.9 — **1.8 boots 1 time in 6**, 2.5 boots 6/6, 3.0 boots 5/5. `test/native/smoke-test.sh` therefore pins the scale (`OCLJ_RAM_SCALE`, default 3.0) instead of inheriting it; `OCLJ_RAM_SCALE=1.8` reproduces the failure. Two things make this need a deliberate decision rather than a guess: the next item (there is no second chance at the wall), and the fact that the baseline OC sizes every machine from is not deterministic — `kernelMemory` ranged 296 493 to 395 089 across runs of the same build. **Plan in memory-accounting.md §11**: measure peak `used` over a full boot of OpenOS and the three census OSes, set our default from that with margin; ~1.8 × 1.85 (our kernel vs PUC's) ≈ 3.3 is the knob doing its job, not a fudge. One day, not a blocker.
- [x] **LuaJIT has no emergency GC, and under a hard cap that was a real divergence from PUC -- NARROWED 2026-09-15, built and measured** ([research/memory-accounting.md](research/memory-accounting.md) section 8f). `lj52_gc_pressure` in `native/lj52shim.c`: ~35 lines of shim, ZERO VM lines. It does NOT collect at the refusal -- section 11's C1, C5 and C6 each independently forbid that -- it writes two scalars the VM already owns (`gc.threshold = gc.total`, the trip-wire ~49 `lj_gc_check` sites test; and `gc.stepmul = 0`, which `lj_gc.c:734-736` turns into an unbounded step) and lets the VM collect at a safepoint. Disarms only on PROOF a cycle ran: the `gc.currentwhite` flip that only `atomic()` performs, plus a return to `GCSpause` -- because `gc_onestep` reaches `GCSpause` from `GCSsweep` and `GCSfinalize` WITHOUT calling `atomic()`, so the state alone would credit a sweep tail that re-marked nothing. Two traps caught in design review that a pass/fail benchmark would never have shown: writing `threshold = 0` instead of `gc.total` charges `debt += the whole heap` at `lj_gc.c:737-738` and pins the collector at 1024 bytes repaid per step for thousands of steps on the JIT-on path; and `GCSpause` is not evidence. RESULT, at DEFAULT pacing on the workload that died 6/6: **cell B survives 6/6 (1.47-1.52 s), cell C survives 6/6 (0.40-0.49 s against PUC's 2.65-2.84 s)**, with `arms` 134-160, `collects == arms` every run, **`bailouts == 0` and `refusals == 0`** -- the allocator never refused at all, so the wall is never reached rather than recovered from. `ENCORE_OK` throughout with nothing re-applied after the restore, closing section 8d's trap by construction. **NARROWED, NOT CLOSED**: the condition becomes `live + largest inter-safepoint burst <= cap` where PUC's is `live + largest single allocation <= cap`; the gap is irreducible without a finer safepoint, which would reintroduce C5 and C6. Superseded text follows for the record:  `lmem.c`'s `luaM_realloc_` runs `luaC_fullgc(L, 1)` and RETRIES when an allocation is refused; `lj_mem_realloc` throws immediately. So a LuaJIT machine can be refused while holding a heap of garbage a collection would have reclaimed. Tuning the collector instead (`lua_gc(LUA_GCSETPAUSE, ...)` when a cap is armed) is safe and looked promising, but does **not** rescue the stock RAM scale: paced at pause 150 / stepmul 400 it booted 0 times in 3 at ramScale 1.8. It also buys whatever margin it does give with collector CPU, which is the opposite of this project's point. Measured and **not shipped**; calibration is the answer, not pacing. The faithful fix is an emergency mode in `lj_gc.c` that skips finalizers the way PUC's `isemergency` does; that is VM surgery, not a small patch — a milestone of its own with its own review, and nothing is gated on it (memory-accounting.md §11). **MEASURED IN A MACHINE 2026-09-04 and it is no longer a mechanism argument** (memory-accounting.md §8c): `sieve` at its shipped parameters completes on PUC 5.2 **3 of 3** (2.65-2.84 s, 676-805 KB free) and dies of `not enough memory` on our native **6 of 6**, in freshly booted 1 MB machines with the RAM guard admitting the workload. Cell B ran with `jit.status()=false` after a `jit.flush()`, so **no trace memory is involved** — plain table churn. The live set is **52.4 KB** against a **3042 KB** budget, so the heap reached ~58x its live set and was over 98% garbage when the allocator refused; `LUAI_GCPAUSE` does not bound this because `lj_gc.c:752-753` pins `threshold = gc.total` once the collector falls behind. And the sandbox cannot work around it: `machine.lua` builds the sandbox global table at `:737` and **`collectgarbage` is not in it**, while the kernel's own collect at `:1526` fires only between resumes and `sieve` finishes inside one. Two scoping notes that survive: `strings` with the JIT on is **out of reach of any collector** (pinned traces, §8a) and needs a trace tier instead; and §8d records a third, previously unwritten memory failure on the **persistence path**, JIT off, after a successful run — worth measuring before this is designed, since a collector that fires at the wall depends on how much of a restored heap is genuinely live.

Goal: an Eris-API-compatible serializer (`eris-lj.c` sidecar compiled into the pinned LuaJIT build) so OC's `PersistenceAPI`/machine.lua machinery works unchanged and LuaJIT computers persist like the stock CPUs. ~3–4k LOC C, months part-time; runs in parallel with v1/v2 (M0–M2 don't depend on the JNI bridge).
