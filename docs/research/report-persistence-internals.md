# LuaJIT architecture for OpenComputers (GTNH): persistence feasibility research

## 1. How OC's Lua persistence actually works (verified in source)

### 1.1 The stack, top to bottom

**Mod layer (GTNH fork, MC 1.7.10).** `li.cil.oc.server.machine.luac.NativeLuaArchitecture` (https://github.com/GTNewHorizons/OpenComputers/blob/master/src/main/scala/li/cil/oc/server/machine/luac/NativeLuaArchitecture.scala) implements the `Architecture` interface. Its `save()` calls `SaveHandler.scheduleSave(..., persistence.persist(1))` on the kernel coroutine (stack index 1, plus index 2 when suspended inside a synchronized call), and `load()` calls `persistence.unpersist(SaveHandler.load(nbt, machine.node.address + "_kernel"))`, restoring the kernel thread mid-execution. Memory limits are lifted during persist/unpersist. Three subclasses exist in the GTNH repo: `NativeLua52Architecture`, `NativeLua53Architecture`, `NativeLua54Architecture`, with matching `LuaStateFactory` objects `Lua52`/`Lua53`/`Lua54` in `li/cil/oc/server/machine/luac/LuaStateFactory.scala`, which unpack `libjnlua{52,53,54}-<platform><ext>` natives from the jar (`/assets/opencomputers/lib/`) and open the `"ERIS"` library on every state.

**PersistenceAPI** (`li/cil/oc/server/machine/luac/PersistenceAPI.scala`, same repo): generates a per-machine UUID `persistKey`, passes it to Eris as the `spkey` setting (the name of the "special persist" metafield), builds a `perms` table (value → name) by recursively flattening everything reachable from globals — so every C function/API closure is a *permanent object* referenced by name instead of being serialized — and the inverse `uperms` table for loading. `persist()`/`unpersist()` then call `eris.persist(perms, value)` / `eris.unpersist(uperms, data)`, gated on the persistence-enabled setting.

**machine.lua** (`src/main/resources/assets/opencomputers/lua/machine.lua`, GTNH repo): userdata is never serialized directly; wrapper tables carry a metafield keyed by `persistKey and persistKey() or "LuaJ"` whose function returns a closure that re-creates the wrapper on unpersist (`userdata.save(...)` → NBT, then `userdata.load(className, nbt)` on restore). This is Eris's documented `__persist`-style protocol with a secret key so sandboxed code can't forge it.

**JNLua fork.** fnuecke/jnlua has branches `eris`, `eris-Lua5.3`, and `memory-limits`. In the `eris` branch's `jnlua/src/main/c/jnlua.c`, the Eris integration is minimal and clean: `openlib_protected()` case 10 does `libname = LUA_ERISLIBNAME; openfunc = luaopen_eris;` — i.e. JNLua just opens the eris C library into the state; all persistence traffic then happens through the Lua-visible `eris.persist`/`eris.unpersist`. The same file carries OC's memory accounting: `l_alloc_checked()` / `l_alloc_unchecked()` custom allocators and `controlled_newstate()` enforcing per-VM RAM limits via `lua_newstate`'s allocator parameter.

**Natives build repo.** BlueAmulet/JNLua-Natives (fork of MightyPirates/OC-Natives) has two branches: `master` (vendored stock-looking Lua 5.2 sources + jnlua.c, no eris — apparently a pre-restructure snapshot; its jnlua.c has the memory-limit allocator but no eris hook) and `master-Lua5.3`, whose `.gitmodules` pins **`jnlua` → https://github.com/fnuecke/jnlua.git branch `eris-Lua5.3`** and **`eris` → https://github.com/fnuecke/eris.git branch `master-lua5.3`**. So the shipped natives = fnuecke's Lua distribution with eris.c compiled in + fnuecke's JNLua glue. (MightyPirates/OC-Eris is the OC-maintained Eris fork, now archived.)

### 1.2 Eris itself

fnuecke/eris (fnuecke is OC's original author): "Heavy Duty Persistence for Lua 5.2 and 5.3", a rewrite of Pluto targeting 5.2+. Per its README: "Eris can serialize almost anything you can have in a Lua VM and can unserialize it again at a later point, even in a different VM. This in particular includes yielded coroutines." Closures are persisted with their upvalues recursively; "C functions cannot be persisted. Put them in the permanent object table"; userdata only via the special persistence metafield; only suspended (not running) threads persist. Critically, the README states outright that Eris **"won't work with other Lua implementations, such as LuaJIT, because Eris works directly on some internal structures of vanilla Lua"** and uses non-API macros/functions (README.md, https://github.com/fnuecke/eris). Pluto (https://github.com/hoelzro/pluto, docs at https://lua-users.org/wiki/PlutoLibrary) is the Lua 5.1-era predecessor with the same design (persist any function/thread, permanent-object table, metafunction hooks; Pluto 2.2 targets Lua 5.1.3).

### 1.3 The no-persistence precedents already inside OC

- The LuaJ fallback architecture (`li/cil/oc/server/machine/luaj/LuaJLuaArchitecture.scala`, GTNH repo) does **not** persist at all: `override def save(nbt) {}` and `override def load(nbt) { if (machine.isRunning) { machine.stop(); machine.start() } }` — running machines simply reboot on load.
- GTNH's `application.conf` ships a `disablePersistence` option: "Disable computer state persistence. This means that computers will automatically be rebooted when loaded after being unloaded, instead of resuming with their exection... Only relevant when using the native library." So reboot-on-load is an officially supported degraded mode, not an aberration.
- Third-party architectures are a supported API: `li.cil.oc.api.Machine.add(Class<? extends Architecture>)` ("Register an architecture that can be used to create new machines"), with `@Architecture.Name` for display. Proven by community addons on MC 1.7.10: OCMOS/J6502 (https://github.com/SolraBizna/j6502) and Thistle 6502 architectures (https://oc.cil.li/topic/1244-...). (Note those persist trivially because a 6502's entire state is a few KB of flat memory — the opposite of the LuaJIT situation.)

## 2. Why Eris/Pluto cannot run on LuaJIT

1. **The library authors say so, in both directions.**
   - Eris README (above): works "directly on some internal structures of vanilla Lua".
   - fnuecke, closing eris issue #4 "LuaJIT support" (Nov 6, 2013, https://github.com/fnuecke/eris/issues/4): "there is no LuaJIT support in Eris and there probably never will be" — Eris pokes vanilla internals via non-API macros; even if attempted, there'd be "a few more hurdles than with vanilla Lua, such as getting the functions re-jitted after unpersisting them."
   - OC maintainer payonel, closing MightyPirates/OpenComputers#3287 "LuaJit?" (May 2020): "we use our own lua (5.2 and 5.3, not 5.1) with some persistence magic baked in", pointing at Eris as the reason LuaJIT isn't used.
   - Mike Pall, lua-l "LuaJIT + Pluto" thread, Sep 2008 (http://lua-users.org/lists/lua-l/2008-09/msg00000.html, verbatim): "LuaJIT 2.x doesn't switch between different C stacks for coroutines anymore. A suspended coroutine could be serialized with some effort. But **the internal data formats are not compatible with standard Lua, so you won't be able to use Pluto at all.** I probably need to add a native serialization module at a later time ..." That promised module became the 2021 `string.buffer` serializer — which is data-only (see §3).

2. **Bytecode incompatibility is documented and absolute.** https://luajit.org/extensions.html: "Foreign bytecode (e.g. from Lua 5.1) is incompatible and cannot be loaded"; LuaJIT bytecode from `string.dump` is portable across architectures but "the bytecode compatibility versions must match" — "Bytecode only stays compatible within a major+minor version"; and LJ_GC64 vs 32-bit builds have "a different, incompatible bytecode format". So (i) an Eris stream (which embeds PUC-format function prototypes) can never be loaded by LuaJIT, and (ii) even a hypothetical LuaJIT-native persist format would break across LuaJIT upgrades.

3. **Object model divergence.** Eris walks PUC internals: `Proto`, the `CallInfo` call-frame list, PUC upvalue structs, per-thread stacks. LuaJIT has none of these in that shape — `GCproto` with its own bytecode, tagged-value/frame-linked stacks instead of a CallInfo array (see `lj_obj.h`/`lj_frame.h` in LuaJIT sources), plus per-state JIT machine-code traces and blacklisting state that have no serializable representation at all (fnuecke's "re-jitted after unpersisting" point). Every line of Eris's ~4k-line core would need a from-scratch rewrite against a moving, undocumented internal ABI.

## 3. Prior art on serializing/hibernating full LuaJIT VM state: none found

Searched: "luajit serialize coroutine", "luajit persist vm state", eris/pluto LuaJIT ports, "ljremote", lua-marshal, game-industry practice.

- **LuaJIT's own serializer** (`string.buffer`, https://luajit.org/ext_buffer.html) handles nil/booleans/numbers/strings/tables/lightuserdata/FFI numbers, and states verbatim: "**Functions, thread objects, other FFI cdata and full userdata cannot be serialized (yet).**" Also tree-only (no shared refs; circular refs error). This is the closest thing to Mike Pall's promised "native serialization module" — and it is deliberately data-only.
- **`string.dump`/`lua_dump` on LuaJIT**: dumps a *function prototype only* (no upvalue values — standard Lua semantics), in LuaJIT's own bytecode format, loadable only by the same LuaJIT major+minor/GC-mode (extensions.html, §2). Useless for suspended-coroutine state.
- **lua-marshal** (https://github.com/richardhundt/lua-marshal): serializes tables with cycles and "Lua functions with upvalues", but README limitations verbatim: "Coroutines are not serialized... Metatables and function environments are not serialized... Serialized code is not portable." Repo issues additionally report function marshaling failing on LuaJIT 2. Data-only in practice.
- **"ljremote"**: no such project found in web search.
- **Eris ports**: none exist (author: "probably never will be", §2).
- **Process-level**: CRIU (checkpoint/restore in userspace) can freeze whole Linux process trees, but for OC it would snapshot the entire JVM/Minecraft server, is Linux-only/privileged, and per-computer granularity would require one OS process per in-game computer plus an RPC bridge — noted for completeness, not viable inside a Forge mod on 1.7.10 (many GTNH servers are also Windows-hosted).
- **Game industry practice** matches Mike Pall's own advice in the same 2008 thread (http://lua-users.org/lists/lua-l/2008-09/msg00012.html): "most people who went down this road [coroutine persistence] sooner or later had to realize that this approach is quite restrictive... **Explicitly saving only the necessary state is often the better solution.**" Engines using LuaJIT (X-Plane, Defold, OpenResty, etc.) serialize data and re-run scripts; none hibernate VM state.

## 4. Hybrid approaches for an addon, assessed

**(a) No persistence — reboot on load.** Fully feasible and precedented: it is exactly what OC's own LuaJ architecture does (`save {}` / `load → stop(); start()`), and what `disablePersistence=true` does for native Lua. Cost: computers reboot on chunk unload/server restart. This is the pragmatic v1 for a LuaJIT addon.

**(b) Data-only persistence.** Serialize a designated state table (globals reachable plain data, or an explicit `computer.persistData()`-style API) with `string.buffer`-based encoding (fast, but needs a cycle-handling wrapper) at save; on load, reboot the VM and hand the blob back as a boot signal. Coroutines restart from entry points. This cannot resume OpenOS mid-`event.pull` — it requires an OS/program model designed for it (Factorio-style "save data, re-run code"). Feasible; genuinely useful for GTNH automation controllers whose logic is a stateless loop over component state; not transparent.

**(c) Interpreter-only mode (`-joff`/`jit.off()`).** Does **not** make state serializable: Pall's "internal data formats are not compatible with standard Lua" applies to the whole VM (object layout, stacks, bytecode), not just to traces; the bytecode incompatibility quote applies regardless of JIT status. Interpreter mode only removes the trace-state problem, and simultaneously removes most of the performance reason to use LuaJIT (see §6).

**(d) Persist under PUC 5.1/5.2 semantics, reload into LuaJIT.** Blocked at the first step that matters: "Foreign bytecode... is incompatible and cannot be loaded" (extensions.html). An Eris stream embeds PUC bytecode protos plus PUC stack/CallInfo records; there is no LuaJIT API to construct a mid-execution frame even if you transpiled the protos back to source. A source-level round trip could at best restore *functions*, never suspended coroutine stacks. Not viable.

**(e) CRIU/process snapshots.** See §3 — impractical in this setting.

**Closest achievable to "OC-style" persistence:** (a) as the default plus an opt-in (b) protocol. Anything that resumes a yielded LuaJIT coroutine across a save/load boundary would mean writing and forever maintaining an Eris-equivalent *inside a LuaJIT fork*, against undocumented internals, with output valid only for one LuaJIT build — no one has done this in ~18 years of LuaJIT, and both the Eris author and the LuaJIT author steered away from it.

## 5. Additional integration blockers an addon must solve (beyond persistence)

- **Timeout watchdog.** OC's 5s "too long without yielding" is enforced in machine.lua via **count debug hooks**: `debug.sethook(co, checkDeadline, "", hookInterval)` around every `coroutine.resume` (verified in GTNH machine.lua). LuaJIT does not invoke debug hooks from JIT-compiled code, and trace recording aborts when hooks are active (LuaJIT mailing-list threads "Debug hooks and JIT", https://www.freelists.org/post/luajit/Debug-hooks-and-JIT,1; tools like luatrace require `-joff` for reliable hooks). Consequence: keep the hooks and you effectively suppress/lose JIT on sandbox code; drop them and a hot compiled loop can starve the executor thread past the timeout with no in-VM recovery — you'd need a Java-side watchdog that hard-kills the Lua state (crash instead of catchable error).
- **RAM accounting.** OC meters RAM via a custom allocator (`l_alloc_checked` in jnlua.c). LuaJIT: on `LJ_64 && !LJ_GC64` builds, the public `lua_newstate` is stubbed to print "Must use luaL_newstate() for 64 bit target" and return NULL, and lib_aux.c carries `#error "Must use builtin allocator for 64 bit target"` for sysmalloc builds (verified in LuaJIT v2.1 `src/lj_state.c` and `src/lib_aux.c`). Modern GC64 builds (default on x64/ARM64) do accept custom allocators again, so OC-style accounting is possible — but JIT machine-code areas are allocated outside `lua_Alloc`, so mcode memory escapes the meter (fairness/DoS consideration).
- **Language level.** LuaJIT is Lua 5.1 + partial 5.2 (`-DLUAJIT_ENABLE_LUA52COMPAT`; extensions.html: "this provides only partial compatibility with Lua 5.2"). GTNH's machine.lua/OpenOS target 5.2/5.3/5.4 semantics (integer division semantics, `table.pack`, metamethod changes, `goto` is fine, but 5.3 integers don't exist). A LuaJIT arch would present roughly a "Lua 5.1+" environment; machine.lua needs a compatibility pass, and some OpenOS programs will misbehave.
- **JNI binding.** Feasible: LuaJIT is "fully ABI-compatible to Lua 5.1 at the linker/dynamic loader level" (extensions.html), so JNLua's 5.1-era C binding can link against it; the addon would bundle its own `libjnlua-luajit-<platform>` natives the same way LuaStateFactory unpacks OC's (per-platform builds: win/linux/mac × x64/arm64 at minimum).

## 6. Performance expectations (honest)

- Compute-bound pure-Lua code with JIT active: order-of-magnitude gains are the historical norm vs PUC interpreters (LuaJIT's old benchmark page claimed roughly 1.2x–135x vs Lua 5.1 depending on workload; that page has since been removed from luajit.org, so treat specific multipliers as folklore; 5–50x on numeric kernels is the commonly reproduced range). LuaJIT's interpreter alone is typically ~2–4x PUC.
- In OC reality the ceiling is lower: component calls cross the JNI boundary and are budget-throttled per tick (`callBudgets`), signals arrive at tick granularity, and typical OpenOS workloads are I/O/event-bound — those see little benefit. The big winners are in-VM compute: software 3D/graphics for GPUs, cryptography, parsing, emulators-in-the-emulator.
- The watchdog dilemma (§5) directly caps this: with count hooks kept for safety, sandboxed code runs mostly unJITted (≈ interpreter-only, ~2–4x); getting the 10x+ headline numbers requires replacing the hook-based timeout with a kill-the-state watchdog.

## 7. Conclusion

- **JNLua/Eris-compatible persistence on LuaJIT is not realistic.** Verified against: Eris's README, the Eris author's own issue-#4 statement ("probably never will be"), the OC maintainer's #3287 rationale, Mike Pall's 2008 analysis, and LuaJIT's documented bytecode/serializer limits. No prior art exists after 18 years.
- **A LuaJIT architecture addon is nonetheless feasible** via `li.cil.oc.api.Machine.add` with the LuaJ precedent for persistence semantics: `save()` writes nothing (or a data blob), `load()` reboots. GTNH's own config already normalizes reboot-on-load as an acceptable mode.
- **Best-value design:** LuaJIT arch with (a) reboot-on-load + (b) an explicit data-persistence API (string.buffer-based), a Java-side hard-kill watchdog instead of debug hooks, GC64 builds with the JNLua checked allocator for RAM limits, and a documented "Lua 5.1+LUA52COMPAT" environment — marketed as a high-performance, non-persistent CPU option beside the standard persistent 5.2/5.3/5.4 CPUs.

CORRECTION: Core facts confirmed, but three refinements: (1) "run effectively unJITted" mischaracterizes the failure mode — setting count/line hooks does NOT disable or slow the JIT (lua_sethook only aborts in-progress recording; lj_trace_hot blocks new traces only for HOOK_GC|HOOK_VMEVENT, not user hooks). JIT and hooks coexist; hooks fire at every interpreter transition (component calls, trace exits, uncompiled paths), so the watchdog still catches most real programs. The real problem is soundness: an exit-free compiled loop (e.g. `while true do end`) never returns to the interpreter and evades the watchdog forever, so for sandboxing untrusted code you must either force interpreter-only mode (reliable hooks, ~2-5x gain instead of 10-100x) or accept unsound hooks and add a backstop. (2) "Java-side state-kill" understates the difficulty: a JVM cannot cleanly stop a native thread spinning in trace mcode — Thread.interrupt() is a no-op in native code. The only shipped precedent (CCLuaJIT) escalates count-hook injection → thread abandonment, leaking a pinned CPU core, and it de facto ran with JIT off anyway (it never calls luaopen_jit, and JIT_F_ON is only set by jit_init() inside luaopen_jit). A robust kill requires process isolation or patching LuaJIT to check an interrupt flag on trace loop back-edges. (3) The allocator constraint is confirmed verbatim but is mild today — GC64 is the default on x64 in current v2.1 (LUAJIT_DISABLE_GC64 is the opt-out) and mandatory on ARM64/macOS. The sharper constraint the claim misses: OC's actual JNLua RAM accounting never passes an allocator to lua_newstate — it calls luaL_newstate() then swaps in the accounting allocator via lua_setallocf (jnlua.c l_alloc_checked). That swap trick is unsafe on ANY LuaJIT build (luaL_newstate memory comes from the internal lj_alloc arena; LuaJIT's lua_setallocf blindly swaps with no block migration), so the addon must create the state with the accounting allocator from the start — possible only on GC64 (or 32-bit) builds. Trivial detail: GTNH machine.lua's hookInterval is dynamic (initial 10000, recalibrated to ipsCount*0.005, min 1000), and LuaJIT hooks are VM-global, not per-coroutine, so machine.lua's per-coroutine sethook calls all target one global hook (functionally acceptable for a deadline watchdog, but different semantics than PUC Lua).
