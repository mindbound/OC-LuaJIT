# Practical engineering of a LuaJIT CPU-architecture addon for GTNH OpenComputers (MC 1.7.10)

## 1. GTNH addon build system — ExampleMod1.7.10

Verified from https://github.com/GTNewHorizons/ExampleMod1.7.10 (root listing via GitHub API; raw files fetched):

- **Build system**: `build.gradle.kts` contains only `plugins { id("com.gtnewhorizons.gtnhconvention") }`. The convention plugin comes from **GTNHGradle** (https://github.com/GTNewHorizons/GTNHGradle — "the container for most of our shared buildscript logic for all GTNH mods and some other 1.7.10 mods"), which is built on **RetroFuturaGradle** (RFG). `settings.gradle.kts` applies `com.gtnewhorizons.gtnhsettingsconvention` (observed version `2.0.20`) and registers the GTNH maven `https://nexus.gtnewhorizons.com/repository/public/`, Gradle Plugin Portal, Maven Central, mavenLocal.
- **Java versions**: `.java-version` = `25` — that is the JDK for *running Gradle*, not the bytecode target. `gradle.properties` sets `enableModernJavaSyntax = jabel` with the comment "Jabel syntax-only support, compiles to J8 bytecode" — i.e. mods ship **Java 8 bytecode** regardless (there is also a `jvmDowngrader` option per GTNH OC's gradle.properties comments). So an OC-LuaJIT addon compiles to Java 8 class files while being buildable on a modern JDK.
- **Dependencies on GTNH mods**: declared in `dependencies.gradle` using coordinates `com.github.GTNewHorizons:<Mod>:<version>:dev` (or `:api`), resolved from the GTNH nexus; configurations include `api`, `implementation`, `compileOnly`, `devOnlyNonPublishable`, `runtimeOnlyNonPublishable`. Concrete OC example verified in GTNewHorizons/Computronics `dependencies.gradle`: **`com.github.GTNewHorizons:OpenComputers:1.12.38-GTNH:dev`** — this is exactly how the addon would depend on GTNH OC (use `:api` or `compileOnly ... :dev` + `runtimeOnlyNonPublishable` for dev runs).
- **Mixins / coremods**: `gradle.properties` template exposes `usesMixins`, `mixinPlugin`, `mixinsPackage`, `coreModClass`, `forceEnableMixins`; the README describes "normal mixins", "GTNH IMixins (recommended)", and "GTNH Early/Late mixins" (UniMixins is auto-added as a dependency when `usesMixins = true`). A LuaJIT architecture addon should **not need mixins or a coremod at all**: OC has a public `li.cil.oc.api.machine.Architecture` API (`@Architecture.Name`, registered via `li.cil.oc.api.Machine.add(...)`), unlike ComputerCraft which forced CCLuaJIT to be an ASM-transforming FML coremod (`FMLCorePlugin: gay.vereena.cclj.CCLuaJIT`, `CCLJClassTransformer`).
- Packaging extras: `usesShadowedDependencies = true` in GTNH OC's own gradle.properties is how OC merges the JNLua/natives jars into its published jar; an addon can do the same with its LuaJIT natives (or just place them under `src/main/resources`).

## 2. CCLuaJIT native build & packaging (local repo, verified by reading files)

Files: `C:\Users\astro\Downloads\CCLuaJIT\build.gradle`, `build-natives.sh`, `Dockerfile`, `src\main\cpp\Makefile`, `src\main\cpp\build.sh`, `src\main\java\gay\vereena\cclj\computer\LuaJITMachine.java`, `src\main\cpp\LuaJITMachine.cpp`.

- **Gradle**: old ForgeGradle 1.2 (`apply plugin: 'forge'`), MC 1.7.10 / Forge 10.13.4.1614, `sourceCompatibility 1.8`. `task buildDynamicLibrary(type: Exec) { commandLine "./build-natives.sh" }; jar.dependsOn buildDynamicLibrary` — the native cross-build is a jar prerequisite.
- **Cross-compilation** (`Dockerfile`, Fedora 29 container):
  - toolchains: `clang` (linux), `mingw64-gcc-c++.x86_64` (windows), **osxcross** built from source with the `MacOSX10.11.sdk` fetched from `https://s3.dockerproject.org/darwin/v2/...` (this S3 bucket is dead today — the Dockerfile no longer builds as-is) targeting `x86_64-apple-darwin15`, min macOS 10.7.
  - LuaJIT is cloned from **git master** (`git clone https://github.com/LuaJIT/LuaJIT.git`) — an unpinned rolling checkout — and built three times: `make BUILDMODE=dynamic` (linux → `libluajit-5.1.so.2`), `mingw64-make HOST_CC="gcc" CROSS="x86_64-w64-mingw32-" TARGET_SYS=Windows BUILDMODE=dynamic` (→ `lua51.dll`), `make HOST_CC="gcc" CC="cc" CROSS="x86_64-apple-darwin15-" TARGET_SYS=Darwin BUILDMODE=dynamic` (→ `libluajit-5.1.2.dylib`). **No `LUAJIT_ENABLE_LUA52COMPAT` (or any XCFLAGS) is passed** — an OC-oriented rebuild should add it.
  - JNI headers come from a vendored copy (`vereena0x13/jni-headers`), so no JDK is needed in the container.
- **Shim library** (`src/main/cpp/Makefile`): one C++ JNI file (`LuaJITMachine.cpp`) compiled per platform: linux `clang ... -L LuaJIT/bin/linux -l:libluajit-5.1.so.2 -shared -fPIE` → `cclj.so`; windows `x86_64-w64-mingw32-c++ ... -l:lua51.dll -shared -Wl,--kill-at` → `cclj.dll`; macOS `x86_64-apple-darwin15-c++ -single_module -undefined dynamic_lookup` → `cclj.dylib` (LuaJIT symbols resolved at runtime because the JVM `System.load`s libluajit first).
- **Packaging** (`build-natives.sh`): `docker cp`s the 3 shim libs + 3 LuaJIT libs into `src/main/resources/natives/`, then `gzip -9`s them. Only **3 platforms** (win x64, linux x64 glibc, macOS x64) — no aarch64/arm/musl/mac-arm64.
- **Runtime loading** (`LuaJITMachine.java` lines 57–101): resource `/natives/<name>.gz` → `GZIPInputStream` → extracted into `Files.createTempDirectory("cclj-natives")`, `deleteOnExit()`, then `System.load(luajit)` **before** `System.load(cclj)`. OS picked via `os.name` only (`OS.java`); no arch check at all (implicit x64-only).
- **One `lua_State` per computer**: `LuaJITMachine.cpp` line 689 `lua_State *L = luaL_newstate();` per machine, opening only `base, math, string, table, bit` (lines 692–696), `lua_close(L)` on destroy (line 736). This is the direct precedent for OC's one-state-per-computer model on LuaJIT.

## 3. How GTNH OpenComputers ships JNLua natives

Verified from https://github.com/GTNewHorizons/OpenComputers (default branch `master`):

- `dependencies.gradle`: `shadowImplementation name: 'OC-LuaJ', version: '20220907.1'`, `'OC-JNLua', version: '20230530.0'`, `'OC-JNLua-Natives', version: '20220928.1'` — resolved from an **ivy repo** declared in `repositories.gradle` with pattern `http://asie.pl/javadeps/[module]-[revision](-[classifier]).[ext]`, and shadowed into the OC jar (`usesShadowedDependencies = true` in gradle.properties).
- I downloaded `OC-JNLua-Natives-20220928.1.jar` (5.2 MB) and listed it: **32 libraries under `assets/opencomputers/lib/`**, the full matrix being `libjnlua{52,53,54}-{platform}` for platforms: `linux-x86`, `linux-x86_64`, `linux-aarch64`, `linux-arm` (32-bit, 52/53/54), `windows-x86`, `windows-x86_64`, `darwin-x86_64`, `darwin-aarch64`, plus `freebsd-x86_64` (52/53/54; note the jar has no darwin-x86 and only x86_64 for freebsd; exact count 3 Lua versions × ~10-11 combos = 32 files).
- **No musl variants exist** — neither in the jar nor in the loader: I read the entire GTNH `LuaStateFactory.scala` (460 lines, saved locally) and the upstream `master-MC1.12` version; neither contains any musl detection. `strings` on the shipped libs shows they are **glibc-linked** with old baselines (`GLIBC_2.2.5/2.3/2.14` for linux-x86_64, `GLIBC_2.17` for linux-aarch64) — broadly compatible across glibc distros, but Alpine/musl servers get "Unsupported platform" and must self-build + use the `forceNativeLibPathFirst` config escape hatch.
- **Loader mechanics** (`src/main/scala/li/cil/oc/server/machine/luac/LuaStateFactory.scala`, quotes): name = `"libjnlua" + version + "-" + platformName + libExtension` where platform = `{freebsd|netbsd|openbsd|solaris|linux|darwin|windows}-{aarch64|arm|x86_64|x86}` (arch from `os.arch` prefixes, incl. `amd64`→x86_64, `i386`→x86); resource path `s"/assets/${Settings.resourceDomain}/lib/$libraryName"`; copied to `java.io.tmpdir` (or `./`) as `OpenComputersMod-<version>-<luaVersion>-<libName>` with byte-compare against an existing copy, `deleteOnExit`, permissive chmod; then `LuaStateFactory.synchronized { System.load(currentLib); create().close() }` as an availability probe; per-arch factories `Lua52/Lua53/Lua54` open `BASE, BIT32/UTF8, COROUTINE, DEBUG, ERIS, MATH, STRING, TABLE`; memory limiting via `create(Some(Int.MaxValue))` when `Settings.get.limitMemory` (JNLua's memory-limited `LuaState(int)` constructor). Config knobs relevant to an addon: `forceNativeLibPlatform`, `forceNativeLibPathFirst`, `nativeInTmpDir`, `alwaysTryNative`, `logFullLibLoadErrors`, `forceLuaJ`, `registerLuaJArchitecture`.
- A LuaJIT addon should clone this exact pattern (per-platform resource name, tmp-dir extraction with version-stamped filename, synchronized probe load, graceful fallback to "not available" so OC's LuaJ/JNLua architectures still work).

## 4. LuaJIT-specific build considerations (verified against LuaJIT/LuaJIT `v2.1` branch source)

- **Rolling releases**: luajit.org/download.html — "LuaJIT uses rolling releases. There are no release tarballs available for download"; consume by pinning a git commit of the `v2.1` branch (do NOT do what CCLuaJIT's Dockerfile does — unpinned `git clone` master).
- **LUA52COMPAT** (`src/Makefile` lines 97–101, verbatim): "Features from Lua 5.2 that are unlikely to break existing code are enabled by default. Some other features that *might* break some existing code (e.g. `__pairs` or `os.execute()` return values) can be enabled here. Note: this does not provide full compatibility with Lua 5.2 at this time. `#XCFLAGS+= -DLUAJIT_ENABLE_LUA52COMPAT`". Unconditional 5.2 features include `goto`/labels, hex/`\z` escapes, `load`/`loadfile` mode+env params, `string.rep` sep, `package.searchpath`, etc.; the flag additionally enables `__pairs`/`__ipairs`, `table.pack`/`unpack`, `coroutine.running` 2 results, `string.find` fixes, `package.searchers`, `io.write` returning the file, `goto` as reserved word (per luajit.org/extensions.html). OC's `machine.lua` sandbox assumes 5.2/5.3 semantics (e.g. it uses `bit32`/`utf8`, sandboxed `pairs` metamethods), so the addon build **must** set `XCFLAGS+=-DLUAJIT_ENABLE_LUA52COMPAT` and will still need Lua-side shims (no `bit32` table in LuaJIT — only `bit`; no integer division semantics of 5.3; `string.pack`/`utf8` absent).
- **GC64 is now the default**: `doc/install.html` (v2.1): "All LuaJIT 64 bit ports use 64 bit GC objects by default (LJ_GC64). For x64, you can select the old 32-on-64 bit mode by adding XCFLAGS=-DLUAJIT_DISABLE_GC64". `src/lj_arch.h`: x64 `#ifndef LUAJIT_DISABLE_GC64 → #define LJ_TARGET_GC64 1` (line 216–217), with `#error "macOS requires GC64 -- don't disable it"`; ARM64 defines `LJ_TARGET_GC64 1` unconditionally (line 303). Consequences: the old x64 limit — allocations forced into the low 2GB (`lj_alloc.c`: `MAP_32BIT` "Apparently 0 gives us full 64 bit addresses and 1 gives us the lower 2GB", "This only allows 1GB on Linux. So fallback to probing to get 2GB"), shared by **all** states in the process — is gone by default; GC64 uses full 47-bit addressing.
- **Custom allocator / per-computer memory accounting**: `src/lj_state.c` line 246: `#if LJ_64 && !LJ_GC64 ... lua_State *lj_state_newstate(...)` `#else` `LUA_API lua_State *lua_newstate(lua_Alloc allocf, void *allocd)` — i.e. in **GC64 mode `lua_newstate` with a user allocator is a real exported API again** (in 64-bit non-GC64 it prints "Must use luaL_newstate() for 64 bit target" and returns NULL, `lib_aux.c` line 395). So an OC-style JNLua counting allocator (per-state memory ceiling) is implementable on modern LuaJIT x64/aarch64 builds. Caveat: JIT machine code is **not** routed through `lua_Alloc` — `lj_mcode.c` allocates mcode areas directly via `mmap`/`VirtualAlloc` (`mcode_alloc_at`, lines 86/135) — but it is bounded per state by the JIT params in `lj_jit.h`: `sizemcode 64` KB per area, `maxmcode 2048` KB total, `maxtrace 1000` (tunable at runtime via `jit.opt.start("maxmcode=256")` etc. for tighter per-computer bounds).
- **Multiple states**: fully supported and the intended embedding model — each `lua_State` from `lua_newstate`/`luaL_newstate` is an independent `GG_State` with its own allocator arena, GC, string table and JIT/trace cache (`lj_state.c` 249–315); CCLuaJIT already runs one state per computer. Baseline per-state footprint is small (the `GG_State` plus stdlib tables, on the order of tens of KB before user code), but note each state JIT-compiles its own copies of hot code, so N computers can each grow up to `maxmcode` (default 2 MB) of machine code plus trace metadata — worth lowering via `jit.opt` for OC's many-small-computers workload.
- **Per-platform build matrix for the addon**: win-x86_64 (mingw-w64 cross, `TARGET_SYS=Windows`), linux-x86_64 + linux-aarch64 (glibc; build on old-baseline distro or with zig cc for portable glibc floor; aarch64 needs a cross toolchain and, per LuaJIT's build rules, a `HOST_CC` matching target pointer width), optional linux-musl variants (would need an OC-side loader tweak since OC's naming scheme has no musl axis), macOS x86_64 + arm64 (osxcross with a newer SDK — the 10.11 SDK URL in CCLuaJIT's Dockerfile is dead; arm64 requires GC64 which is default). 32-bit x86/arm are optional legacy (LuaJIT supports them, but non-GC64 32-bit has the 1–2 GB space and GTNH itself needs 64-bit Java).

## 5. JNI on Java 8 vs GTNH's modern JVMs (lwjgl3ify)

- GTNH runs 1.7.10 on modern Java via **lwjgl3ify** (https://github.com/GTNewHorizons/lwjgl3ify): README — "Change the instance java version to 17.0.6, 19.0.2, 20 or 21 (or newer), these are the currently supported versions", using RetroFuturaBootstrap (`-Djava.system.class.loader=com.gtnewhorizons.retrofuturabootstrap.RfbSystemClassLoader`) plus a long list of `--add-opens` flags. Those flags concern reflection into JDK internals, **not JNI**.
- `System.load`/`loadLibrary` behave identically on Java 8, 17 and 21 for classpath (unnamed-module) code — no module-system restriction applies; OC's JNLua natives already load fine on GTNH Java 17/21 today, which is the existence proof for the addon's natives.
- From **JDK 24** (JEP 472, "Prepare to Restrict the Use of JNI"), `System.load`/`loadLibrary` are `@Restricted` and the default `--illegal-native-access=warn` prints a one-time-per-module warning; silenced with `--enable-native-access=ALL-UNNAMED` (classpath code). Warning only — not an error — until a future release flips the default. Sources: [JEP 472](https://openjdk.org/jeps/472), [Inside.java heads-up](https://inside.java/2024/12/09/quality-heads-up/), [InfoQ](https://www.infoq.com/news/2024/07/jep-472-restrict-jni-jdk-24). If GTNH moves past Java 21 (lwjgl3ify says "or newer"; ExampleMod's `.java-version` is already 25 for Gradle), the addon's docs should recommend adding `--enable-native-access=ALL-UNNAMED` to the instance args; lwjgl3ify's argument templates are the natural place for it.
- One 1.7.10-specific gotcha CCLuaJIT sidesteps and the addon should too: load natives from a **temp-dir absolute path via `System.load`** (as both OC and CCLuaJIT do), never `System.loadLibrary` through LaunchClassLoader, because a JNI library can only be bound to one classloader at a time and 1.7.10's classloader duplication causes `UnsatisfiedLinkError: already loaded in another classloader` on reload otherwise.

## 6. Synthesis — recommended build pipeline for the addon

1. Clone ExampleMod1.7.10; set `modId`, `coreModClass` empty, `usesMixins=false`; `dependencies.gradle`: `compileOnly("com.github.GTNewHorizons:OpenComputers:1.12.38-GTNH:dev") { isTransitive = false }` + `runtimeOnlyNonPublishable(...)` for dev runs.
2. Build natives out-of-band (CI or Docker, CCLuaJIT-style but modernized): pinned LuaJIT v2.1 commit, `XCFLAGS="-DLUAJIT_ENABLE_LUA52COMPAT"`, `BUILDMODE=static` into the JNI shim (simpler than CCLuaJIT's two-library scheme — one `libocluajit-<platform>` per target, statically embedding LuaJIT, mirroring how JNLua natives statically embed Lua+Eris in a single ~0.3–0.8 MB lib) for: windows-x86_64, linux-x86_64, linux-aarch64, darwin-x86_64, darwin-aarch64 (matching OC's naming convention `-<os>-<arch>` so `forceNativeLibPlatform` semantics carry over).
3. Commit/attach the natives under `src/main/resources/assets/<modid>/lib/` (or gzip them like CCLuaJIT to shave jar size; OC ships ~13 MB of natives uncompressed at 5.2 MB jarred); RFG's normal `jar` task packs resources — no need for CCLuaJIT's `jar.dependsOn buildDynamicLibrary` docker exec inside Gradle, which would break Windows devs and CI.
4. Runtime: port `LuaStateFactory`'s extraction/probe logic; register the architecture via OC's `Machine.add`; use `lua_newstate` + counting allocator (GC64) for `limitMemory` parity, and clamp `jit.opt` mcode limits per state.

VERDICT: confirmed
EVIDENCE: All load-bearing assertions check out against primary sources; one framing detail deserves a correction that actually strengthens the conclusion (see correction). (1) lwjgl3ify README (raw.githubusercontent.com/GTNewHorizons/lwjgl3ify/master/README.MD) says verbatim: "Change the instance java version to 17.0.6, 19.0.2, 20 or 21 (or newer), these are the currently supported versions." (2) JDK 21 GA source (raw.githubusercontent.com/openjdk/jdk/jdk-21-ga/.../java/lang/Runtime.java): load0/loadLibrary0 perform only the (deprecated, off-by-default) SecurityManager.checkLink — no @Restricted annotation, no ensureNativeAccess call — so JNI library loading is unrestricted and warning-free through JDK 21; JDK 17 GA hotspot arguments.cpp accepts --enable-native-access= (JEP 412) and has no --illegal-native-access at all. (3) JDK 24 GA source: Runtime.load/loadLibrary (lines ~753-815) are @Restricted and call Reflection.ensureNativeAccess; Module.ensureNativeAccess warns and sets a flag "so that only one warning is reported per module", or throws IllegalCallerException under DENY; ModuleBootstrap.addIllegalNativeAccess returns "IllegalNativeAccess.WARN; // default" when no flag is given. (4) JEP 472 text itself (openjdk.org/jeps/472, fetched directly with curl after WebFetch 403): Status Closed/Delivered, Release 24; warn "mode is the default in JDK 24"; "At most one warning per module is issued"; the sample warning is precisely for System::load; --enable-native-access=<module|ALL-UNNAMED> avoids it; deny "will become the default in a future release". (5) JDK 25 GA ModuleBootstrap.java still defaults to WARN, so hard errors remain deferred beyond JDK 25. Also confirmed the flag targets the right thing for a Forge mod: classpath/LaunchClassLoader code lives in unnamed modules, and JDK 24 Module.moduleForNativeAccess maps all unnamed modules to ALL_UNNAMED_MODULE, so ALL-UNNAMED covers OC-LuaJIT's System.load calls.
CORRECTION: Nuance (framing, not the core fact): the parenthetical "the --add-opens args concern reflection, not JNI" is literally true of the --add-opens flags, but lwjgl3ify's stock launch configuration is NOT silent on native access — its recommended MultiMC/Prism client argument block (README, 3.x arguments) and its server-side java9args.txt BOTH already begin with "--enable-native-access ALL-UNNAMED" ahead of the --add-opens list. So the "single flag needed for future JDK 24+ cleanliness" already ships in lwjgl3ify's documented launch args (valid since JDK 17 via JEP 412, so it parses on every supported version): instances following the standard GTNH/lwjgl3ify setup will be warning-free even on JDK 24/25 with zero additional action. Remaining pedantry: "(or newer)" in the README's supported-versions sentence technically includes JDK 24+, where loading is not warning-free absent that flag — but since the flag is in the stock args, this has no practical effect. Note the JEP 472 warn->deny flip had not happened as of JDK 25 GA (default still WARN in source).
