# MineOS census: is the shape-category list complete?

Third OS sample, chosen because it differs from both prior ones: a built-in GUI
layer, a multitasking model, and multiple user profiles. The question was not
coverage but COMPLETENESS -- does a structurally different OS produce a NEW
category, or only new instances of known ones? "Only instances" was an
acceptable answer and was told to be reported as such. 2026-09-01.

Prior samples: QuickOS (OpenOS-derived) and axis-os (from scratch). See
[os-shape-census.md](os-shape-census.md) for the category list this tests.

## The completeness answer

NO NEW LUA-SHAPE CATEGORY. That is the headline and it is the converging answer. Across four arms, MineOS produced ~20 distinct shapes and every single one landed in existing sections A, B, C, D or E. Two arms independently reached "no new category" outright (tasks, harness on the shape question); the other two produced category CLAIMS that I am deflating below rather than accepting.

WHAT I AM DEFLATING. Two arms each claimed one new category, and I do not think either stands as a category, because THEY ARE THE SAME THING SEEN FROM TWO SIDES. Both are consequences of one architectural feature MineOS has and neither prior OS could have: Screen.lua keeps a complete Lua-side double buffer of the display (six flat arrays of bufferWidth*bufferHeight, Screen.lua:31-36/95-116/874-895), and renders only the diff. QuickOS and AxisOS write straight through to the GPU and keep no mirror.
 - the gui arm read the SIZE consequence and called it "the save is correct but does not fit" (resource exhaustion at save time);
 - the harness arm read the SEMANTIC consequence and called it "VM-side mirror of host state" (the blob and the host component NBT must be captured and restored from the same instant);
 - the tasks arm saw the second one, flagged it as a candidate E-split, and correctly declined to claim it because it had not measured it.
One feature, two consequences. So the honest result is ONE NEW AXIS ON THE CENSUS, carrying TWO ROWS -- not two new categories, and definitely not a new shape category.

THE AXIS: what the census has never had a column for is COST AND PAIRING OF THE SAVE ITSELF, as distinct from the correctness of the graph. Sections A-D classify values; section E classifies non-shape facts that DOOM a correct blob (pointer identity, absolute time, perms nondeterminism). Both new rows are non-shape, so E is where they belong, but neither is E's existing kind ("a process-local fact a serializer is guaranteed to break"). They are:

 ROW E4 -- THE SAVE MAY NOT FIT. Every value HANDLED, blob correct, machine still comes back off, because producing the blob exceeds the machine's RAM ceiling. eris_lj.c:233-238 grows the write buffer through the HOST allocator (doubling to a power of two) and eris_lj.c:2477 then lua_pushlstring copies the whole buffer again, so the peak is live + buffer + blob. Invisible to every shape-level test; its fix space (stream the writer, drop the second copy, budget against totalMemory, refuse early with a size diagnostic) is disjoint from everything else in the census; and it is the only row in the whole census whose fix is in OUR C code rather than in machine.lua, the Java flattener, or an OS. See blobSize for why it is CONTESTED and what decides it.

 ROW E5 -- MIRRORED HOST STATE IS AN ATOMICITY OBLIGATION ON THE ARCHITECTURE. currentFrame* is not data, it is a cached belief about what the screen component currently displays, used to SUPPRESS work. The Lua half round-trips perfectly. The failure mode only exists if the two halves are captured or restored from different instants, and then the program never notices, never errors and never repairs, precisely because the mirror's job is to skip work when it says nothing changed. Measured by deliberately breaking the pairing (restore the real blob, blank only the host text buffer): ink 275 -> 0, recovers to ~100 and stays there permanently, ~64% of the desktop missing forever, machine.isRunning=true, crashes=0, lastError=null, re-saves cleanly. Control with pairing intact held 265-275. This is NOT a defect today -- stock OC and ocelot-brain satisfy it by construction (Machine.save and Machine.run share a lock, both halves go in the same NBT), which is exactly why no amount of reading OpenOS surfaces it. It is a written CONSTRAINT the LuaJIT architecture must not break: one lock, one instant, never restore one half without the other, never leave a stale component NBT paired with a fresh blob after a failed or retried save. It becomes live the moment anyone snapshots asynchronously, retries half a save, or migrates a blob onto a machine whose screen came from elsewhere.

ONE CHANGE TO THE CLASSIFICATION SCHEME, also not a shape. The census has four outcome classes (HANDLED / SEMANTICS-CHANGE / REFUSED / SILENT-GAP). MineOS forced a FIFTH, measured: THE CONSTRUCT IS ILLEGAL AT RUNTIME -- `attempt to yield across C-call boundary`, coroutine dead, serializer never invoked, and the program cannot run with or without a save. Reached via MineOS's table.sort comparator that performs a component call (Filesystem.lua:455-460, on the desktop's file-list path), which the census currently files under C's "CANNOT OCCUR". Identical after JIT warmup, so not an interpreter artifact; an enclosing xpcall does catch it.

TWO EXISTING ROWS NEED THEIR WORDING WIDENED OR NARROWED (both measured, both in changesRanking).

THE CAVEAT I WILL NOT BURY. The convergence evidence is strong for A, D and E and WEAK for B. MineOS has no scheduler: `coroutine.` appears 4-6 times in 102 .lua files, all in one application (MineCode IDE), and `coroutine.wrap` zero times repo-wide. Live coroutines at a save point: zero. So the third sample barely tested the thread half of our contract -- the hardest half. It did stress B's FRAME axis hard (re-entrant nested workspace:start(), measured to depth 8 with ~40 open upvalues per activation aliasing its own live frame, and a 14-frame chain spanning two event loops, two tree walks, an xpcall and a load()ed chunk, all round-tripping). But "three structurally different OSes and section B did not move" overstates it: two of the three exercised B's threads, and the third did not.

## New instances

Instance-level, MineOS gave five things the other two could not, plus one negative result and two arm-vs-arm corrections.

1. HASH-ORDER DEPENDENCE WITH NO CURSOR AND NO SUSPENSION. System.lua:2735-2739: `for w in pairs(icon.windows) do topmostWindow = w end; topmostWindow:focus()`, over a set keyed BY THE WINDOW TABLE (built at 2248-2250, torn down at 2189). "Topmost" means "whatever pairs() yields last". No yield in the body: the loop COMPLETES, nothing suspends, the replay iterator never sees it, and the meaning is read out of hash order after the restore. Measured cross-process, 40 round trips at each of 2/3/4/8/16 windows: the focused window changed 40/40 EVERY time and full iteration order differed 40/40, while membership was always exact. Three controls carried: in-process stability (200/200 same answer plus 20 fresh in-process rebuilds all agreeing, so the invariant MineOS relies on is real), a same-blob same-run ARRAY negative control (16/16 unchanged while pairs-last changed 16/16, isolating hash order as the cause), and divergence already at pad=0 (every restore, not an unlucky layout). This is the single most valuable instance of the session: it is a class of breakage our entire for-in fix is structurally irrelevant to.

2. THE MATCHED PAIR THAT NARROWS CATEGORY D'S SILENT-GAP RULE. MineOS is the first system to supply BOTH sides. Its own hand-written closure-over-next iterator, filesystem.mounts (Filesystem.lua:113-121, two mutable upvalues), driven as a for-in with a yielding body (Finder.app/Main.lua:324-332, proxy.getLabel()): 20/20 pads EXACT and ORDER-EXACT at N=12, N=4 and N=3, checked against an independent full-traversal `.order` sidecar. machine.lua's structurally identical component.list iterator, same harness: 0/20 exact at N=12, order diverged 20/20, three distinct realisations including silent truncation. Holding iterator and body fixed and varying only whether the walked table is array-backed or hash-backed reproduces the split (20/20 vs 1/20). So the rule is not "an iterator wrapping next" -- it is "an iterator wrapping next OVER A HASH-KEYED TABLE", which is narrower, statically checkable, and means MineOS's own iterator is safe by construction (table.insert/table.remove keep mountedProxies dense) rather than safe by luck.

3. THE REPLAY ITERATOR HOLDS OVER ADDRESS-HASHED TABLE KEYS. Both prior OSes only had string-keyed pairs() in their hot paths; string keys carry an interned sid, table keys hash on ADDRESS, which no fresh process reproduces -- a different mechanism needing its own measurement. MineOS's whole event loop is that shape: Event.lua:34 `handlers[handler] = true` with anonymous-table handlers, pairs() walks at :66 and :76, the pullSignal save point at :73 BETWEEN them, arbitrary callbacks invoked inside the walk at :89, deletion during the walk at :92. Measured cross-process over 10 pads 0..1500: 10/10 exact key multiset, walk completes, delete-during-walk fine. Matched negative control (same table-keyed set carrying an explicit (next,t,key) cursor): 10/10 DIVERGED, losing 5-8 of 14 handlers and duplicating others. Technique note worth keeping: forin.lua's string ballast is INERT against table keys -- you must allocate and RETAIN throwaway tables to rotate address-hashed layout.

4. AN OS THAT ESTABLISHES APPLICATION IDENTITY BY WALKING ITS OWN CALL STACK, and the positive result nobody had checked. `system.getCurrentScript()` walks debug.getinfo until `info.what == "main"` and returns info.source (System.lua:133-147, drives every app's localization); `system.addWindow` walks getinfo for a frame whose source ends `.app/Main.lua` and THAT is how a window is bound to its dock icon (System.lua:2226-2241); the xpcall handler gmatch-parses debug.traceback() TEXT (System.lua:270-274). This makes prototype DEBUG-INFO FIDELITY load-bearing for the dock, window ownership and localization. Two arms measured it independently over restored suspended stacks: byte-identical debug.getinfo views from outside and inside, identical what/source/linedefined/lastlinedefined per frame, identical getCurrentScript() result, identical traceback text including line numbers, on an 8-frame and a 14-frame MineOS-shaped stack. This is structurally the AxisOS PatchGuard move -- deriving identity from runtime introspection -- but it reads a chunkname, not an address, so it lands on the SAFE side. Category E has benign members, and this one should become an explicit written guarantee in the contract (see changesRanking).

5. THE gmatch REFUSAL ESCAPING THROUGH A LIBRARY'S PUBLIC API. FTP.lua:66-68 `function FTP.lines(data) return data:gmatch("([^\r\n]+)\r\n") end`, consumed at FTP.lua:493/508/915 inside flows that reach event.pull. Measured REFUSED: "eris-lj: cannot persist a C function by value; put it in the perms table"; adding BOTH native string.gmatch and machine.lua's replacement to perms does not help (the live iterator is a distinct runtime-minted C closure); the while-iter() form with no for-in control slot is refused identically, so it is the VALUE, not the loop form. New only in that an auditor grepping for `:gmatch(` inside for-in headers would MISS every call site. Both sides of the 500-byte threshold measured on the same source line at IRC.app/Main.lua:591-593: #data=150 refused, #data=830 takes machine.lua's Lua-closure arm and round-trips exact 24/24 lines in order.

6. package.loaded ITSELF MADE WEAK-VALUED, as a user-selectable setting (System.lua:307-327, toggled from Settings.app 8_System:62). Existing A/SEMANTICS-CHANGE, but the sharpest instance yet: on the first post-restore GC every unreferenced module is dropped at once, a different eviction schedule than the machine had before the save. Measured at pads 0/17/257, with the collector both running and stopped around the persist: 11 entries at the save point -> 11 at restore -> weakness resumes correctly with __mode='v' intact. Benign in MineOS specifically, because every module is also held as an upvalue of the closures that required it.

7. THE NEGATIVE RESULT, which is what makes "only instances" credible. MineOS has no userdata anywhere on the GUI path (file handles are plain tables `{proxy=,stream=<numeric OC handle>,position=,buffer=}`, images are flat Lua arrays); ZERO metatables in 4600 lines of GUI.lua (so no __pairs/__call iterator of its own making -- "inheritance" is field copying, which is why the graph is wide and field-heavy, ~25 own fields per widget where a metatable framework would write ~6); zero setfenv/getfenv/_ENV/load-with-env/debug.setupvalue/debug.upvalueid repo-wide, so our function-environment support is UNUSED by MineOS while our upvalue-identity guarantee is load-bearing; no debug.sethook, newproxy, __gc, rawequal or tostring(f) fingerprinting -- nothing in the PatchGuard family; and every scrolling cursor in every widget is an ARRAY index or a stable path string (tree.fromItem, tree.selectedItem=<path>, textBox.fromLine, scrollBar.value, animationIndex over an array with table.remove). Which is exactly why the one hash-order dependence at System.lua:2735 stands out as deliberate rather than pervasive.

TWO ARM-VS-ARM CORRECTIONS I AM RESOLVING IN FAVOUR OF THE MEASUREMENTS. (a) The gui arm reported "MineOS does NOT hit the gmatch refusal". That is TRUE ON THE DESKTOP/GUI PATH and FALSE OS-WIDE: two other arms measured the refusal firing in FTP and IRC. MineOS's refusals live in its APPLICATIONS, not its OS -- which is itself a finding about where to look next. (b) The harness arm's first-pass reachability claims were wrong at three sites and it corrected them against source rather than quietly keeping the citations: Filesystem.lua:671-673 cannot suspend (filesystem.mount is pure Lua, component.proxy uses pcall over the raw host API), and Text.lua:207 / GUI.lua:2668 / GUI.lua:2699 all have non-yielding bodies (Text.wrap measured NO-YIELD). The shapes all reproduce; the claims about where they were reachable did not, and each was relocated to a site that genuinely yields.

## Changes to the ranked list and constraints

YES -- five changes to the ranked fix list, two changes to sandbox constraints, and one addition to the written contract. Ordered by how much they move.

A. REWRITE ITEM #5 (unrebased computer.uptime deadlines). THE MODEL IN THE CENSUS IS WRONG, and this is the sharpest correction of the session. The census assumes a bimodal failure: "if uptime advances, every wait fires at once; if it resets to zero, every waiter hangs forever". Read from OC source: Machine.scala:89 uptime is a tick counter, :525 increments it, :182 upTime() = uptime/20.0, :886 nbt.setLong("uptime", uptime) SAVED, :799 nbt.getLong("uptime") RESTORED, and it is zeroed only at machine START (:239) and STOP (:948). So across a world reload uptime FREEZES and resumes from the saved value -- it does NOT reset and does NOT jump. In-flight deltas therefore survive approximately correctly and the bimodal framing is largely dead. What is NOT dead, and is now the whole of item #5, is state that mixes uptime with REAL time: MineOS's System.lua:3304-3311 seeds bootRealTime from a tmpfs file's mtime once at boot and :52-54 computes `system.getTime() = bootRealTime + computer.uptime() + timezone`, so after a reload the OS clock silently loses every second of real-world time the world was unloaded and is painted on the menu bar (measured '24 Aug 2025 05:46:40' -> '04:46:40' in the reset model, and a fixed backwards skew in the frozen model). Rewrite the row as "absolute time that mixes a persisted uptime with a non-persisted real-world epoch"; keep both models side by side, because which one holds is a host fact and the ranking depends on it. Net effect: probability stays ~1, badness DROPS from "machine hangs / storms" to "the machine's clock is wrong", so #5 should move DOWN the list. Two arms modelled the reset case as primary and both should be re-read with this correction applied; the gui arm's "permanent 100%-CPU wedge" (animation position going to -7499.8, never reaching 1, workspace busy-spinning with event.pull(0) and a full redraw every pass, GUI.lua:241/486/524) is a REAL and nasty failure mode but it is CONDITIONAL ON THE RESET MODEL, which Machine.scala says does not occur in stock OC. Keep it as the documented consequence of ever breaking uptime continuity -- it is the strongest argument for "if we freeze or rebase uptime, do it deliberately, and never let it go backwards."

B. CONFIRM AND SHARPEN #1 (component.list's __call-over-next). Third independent OS inherits it; measured 0/20 pads exact at N=12 with silent truncation among the realisations. Unchanged at rank 1. But NARROW THE RULE using the matched pair: the silent-gap condition is "an iterator wrapping next OVER A HASH-KEYED TABLE", not "an iterator wrapping next". MineOS's own filesystem.mounts closure-over-next is 20/20 exact and order-exact because mountedProxies is kept dense. This makes the audit rule statically checkable and shrinks the set of things #9's proposed save-time diagnostic would have to warn about. Caveat carried from the arm: the green verdict on filesystem.mounts rests on a code-reading argument that no path creates a hole in mountedProxies, not on a measurement.

C. WIDEN #9 / the D silent-gap row to cover HASH ORDER WITH NO CURSOR AND NO SUSPENSION. Current wording ("an OS's own Lua-closure-over-next iterator", "a hash-order-dependent CURSOR kept in ordinary program state") excludes MineOS's System.lua:2735 `for w in pairs(icon.windows) do topmostWindow = w end`, which has no cursor, never suspends, and runs entirely after the restore -- yet picks a different window 40/40 times at every set size from 2 to 16. Restate as: ANY program behaviour that reads meaning out of hash iteration order, cursor or not, suspended or not. This matters because it defines the limit of our for-in work: the replay iterator is structurally incapable of helping here, so this row is permanently a documentation-and-diagnostic item, not an engineering one.

D. ADD A NEW ITEM: SAVE-TIME MEMORY COST (row E4 above). Rank provisionally around #4-6, and mark it BLOCKED ON ONE MEASUREMENT (see blobSize) because two arms disagree about whether it fires. Badness is maximal (refusal, computer comes back off, with an opaque OOM rather than a diagnostic). It is the only item in the entire ranked list whose fix lives in our own C: stream the writer instead of buffering (eris_lj.c:233-238), drop or avoid the second full copy at eris_lj.c:2477, budget the save against computer.totalMemory(), and refuse EARLY with a size diagnostic rather than late with an allocator failure. Even if the ceiling turns out not to bite, "refuse with a number instead of an OOM" is cheap and should ship.

E. ADD A NEW ARCHITECTURAL OBLIGATION (row E5 above): the LuaJIT architecture must capture the Lua blob and the component NBT under one lock at one instant, must never restore one half without the other, and must never leave a stale component NBT paired with a fresh blob after a failed or retried save. Not a ranked defect -- a design constraint to write into the architecture doc before anyone implements async snapshotting, partial-save retry, or blob migration.

F. CORRECT SECTION C's REASONING (verdict survives, justification does not). The census lists "yield inside table.sort's comparator" under "CANNOT OCCUR (so the matching refusals are correct backstops, not live risk)". MineOS SHIPS that construct on the desktop's file-list path (Filesystem.lua:455-460, reached from System.lua:1436 on every desktop/Finder refresh when sorting by date). It does not fire only because FileSystem.scala:110 annotates lastModified `@Callback(direct = true)` and Callback.java:88 defaults limit to Integer.MAX_VALUE, so Machine.scala:391's consumeCallBudget costs ~4.7e-10 and machine.lua:1093's yield fallback is never taken. So the set of Lua constructs an OS may legally write is not a language fact and not a serializer fact -- it is a per-method JAVA ANNOTATION the OS author cannot see. Restate as "DOES NOT OCCUR TODAY, GATED BY A HOST ANNOTATION", and enumerate the annotations it depends on. Change lastModified to indirect (as list/makeDirectory/remove already are), or give it a limit (as open=4, read=15 have), and MineOS's file manager becomes a hard crash. Add the fifth outcome class alongside it.

G. ADD A POSITIVE GUARANTEE TO serializer/README.md's contract, which nobody had reason to state before: DEBUG-INFO FIDELITY OVER RESTORED FRAMES. Frame identity, `what`, `source`, `linedefined`, `lastlinedefined` and current line survive a round trip, so debug.getinfo and debug.traceback over restored frames are sound and their text is stable including line numbers. Measured independently by two arms on 8-frame and 14-frame suspended stacks. This is load-bearing for MineOS's dock, window ownership and every app's localization, and it is the benign counterweight to E's PatchGuard row: introspection over CHUNKNAMES is stable, introspection over ADDRESSES is not. State both together so an OS author can tell which side of the line they are on.

SANDBOX CONSTRAINTS -- two changes.
 1. UNCHANGED AND RECONFIRMED: libcomponent.list should return `next, list, nil`; componentProxy.__pairs should return `next, self, nil` or be deleted in favour of pre-flattened fields. Third OS, same finding.
 2. RAISE THE PRIORITY of "put the pure-Lua gmatch on the sandbox unconditionally, or set SHORT_STRING to 0" (census #4). Previously justified by AxisOS's source-level preemption, which MineOS does not have -- so on the old reasoning MineOS would have lowered this item. It does the opposite, for a new reason: MineOS hands raw native gmatch iterators OUT OF A LIBRARY'S PUBLIC API (FTP.lua:66-68 FTP.lines), so the refusal is reachable at call sites that contain no `gmatch` token at all. Static audit cannot find these. Unconditional Lua gmatch is the only complete fix, and it also removes the untestable-by-inspection 500-byte cliff where the same source line succeeds or refuses depending on data length.
 3. NEW, section F not the ranked list: on this LuaJIT, `debug.sethook(co, f, "", n)` is VM-GLOBAL, not per-thread -- measured 11 hook hits on the MAIN thread while the hook was nominally on `co`. machine.lua:858/861 arms and disarms exactly that around EVERY nested coroutine.resume, and MineCode IDE (Main.lua:745-797) is the first censused OS code that reaches it. So debugging a script silently hooks and then unhooks the whole VM. That is watchdog territory, not serializer territory, but it belongs in F next to "the CHECKHOOK armed state is not preserved".

## Blob size

NUMBERS EXIST, from two independent harnesses, and they DISAGREE BY 2x in a way that is explainable and that leaves the ceiling question genuinely open. I am reporting both rather than picking one.

THE REAL MEASUREMENT (harness arm, ocelot-brain, stock semantics: PUC Lua 5.2 + real Eris, NativeLua52Architecture asserted at every entry point):
 - live MineOS desktop kernel blob: 1,629,411 bytes (1.63 MB)
 - bare OpenOS shell: ~58 KB -> MineOS is ~28x
 - OpenOS mid-boot: 149,782 bytes -> ~11x
 - growth curve: 65 KB at the bootloader, 1.23 MB by tick 84, plateau 1.63 MB
 - ~1.4 MB of the 1.63 MB IS the Screen.lua framebuffer mirror
 - save cost 32 ms; load ~330 ms in a fresh JVM
 - gzipped workspace NBT actually written: 317,824 bytes -- a ~5:1 compression ratio, because a framebuffer mirror is extremely repetitive
 - 300 dense save attempts every 4 ticks from cold boot through desktop, with touch/key signals injected: 300 ok, 0 refused, 0 crashes

THE MODELLED MEASUREMENT (gui arm, against our real eris_lj.c on libluajit_stock.a, with a COUNTING, CAPPING lua_Alloc installed via lua_newstate the way OC's host does -- which is what makes "does the save fit" measurable rather than arithmetic; its used() tracked collectgarbage('count') to within 3 bytes on an empty state):
 - MineOS-shaped desktop (30 icons, 8 windows x 60 widgets): 2560 tables, 1610 KB live Lua heap, 772 KB blob, save 11 ms, load 7 ms
 - peak during save 3406 KB = live + a 1024 KB write buffer + a second 772 KB copy
 - MineOS's own installer declares the floor as 2048 KB (Installer/Main.lua:151-152)
 - pinned boundary: 160x35 saves, 160x36 fails

DOES IT THREATEN THE MEMORY CEILING? UNRESOLVED, AND THIS IS THE ONE MEASUREMENT I WOULD RUN NEXT. The arithmetic says yes: eris_lj.c:233-238 grows the write buffer through the HOST allocator (doubling to a power of two, so it is charged to the machine's ceiling by explicit design -- the source comment says "the memory is inside the host's accounting"), and eris_lj.c:2477 then lua_pushlstring copies the whole buffer again. On the real 1.63 MB blob that is roughly 1.4 MB live + 2 MB buffer + 1.63 MB string, which cannot fit a 2048 KB machine by a wide margin. Yet the harness arm produced that blob 300 times out of 300 on real ocelot-brain with zero refusals. The two are only reconcilable if ocelot-brain was configured well above the T3.5x2 floor, or does not enforce the RAM cap on the persist path the way stock OC does. THE DECIDING EXPERIMENT: re-run the ocelot-brain MineOS boot with the machine's RAM set to exactly MineOS's declared floor and try to save. That is a one-run answer and it either promotes E4 to a ranked defect or retires it.

WHAT I TRUST AND WHAT I DO NOT.
 - The 1.63 MB is a real blob from a real Eris on a real booted MineOS. Trust it.
 - The 772 KB model UNDER-COUNTS: its object tree is 305 tables against the real 2560, so it under-models the widget count roughly 8x. Direction is safe (flat arrays dominate the byte total) but its 160x36 boundary is an UPPER BOUND on what a real MineOS can save -- a richer tree fails sooner, never later. Read it as "no worse than 160x36".
 - The "even a perfect single-copy buffer would not fit" claim is ARITHMETIC, not a measurement; no exactly-sized-buffer variant was built.
 - The dependence of the whole ceiling story on the eris write buffer being charged to the host allocator is true by design and true in the harness by construction, but has NOT been run against a real OC/JNLua allocator. If some host allocated it outside its accounting, E4 evaporates.

THE NBT PATH: NOT A HARD LIMIT, BUT A REAL WORLD-SAVE COST. 317,824 gzipped bytes per computer, written on every world save, and the 1.63 MB uncompressed byte array must exist in JVM heap at save time. No NBT tag limit is anywhere near being hit. The exposure is multiplicative -- N computers per chunk, every autosave -- and it is a Minecraft-side cost the census had no reason to consider when a bare shell was 58 KB. The useful engineering fact buried in it: gzip crushes framebuffer mirrors 5:1, so any size budget should be stated on the compressed figure for the NBT path and on the UNcompressed figure for the RAM path, because those differ by 5x and only one of them is the ceiling question.

WHY THIS RISK IS SPECIFIC TO GUI OSes AND WAS UNMEASURABLE BEFORE: a text OS leaves the framebuffer in the GPU and touches it through component calls. A GUI framework that owns its own double buffer necessarily holds the whole screen as Lua tables (Screen.lua:100-116, six flat arrays of bufferWidth*bufferHeight -- 48000 slots at 160x50; Image.lua:77-87 stores every picture including the full-screen wallpaper as ONE flat array of 2+4*w*h, 32002 slots). That single architectural choice is worth roughly an order of magnitude of blob over anything previously censused, and it is exactly the part of MineOS with no analogue in QuickOS or AxisOS.

## The stock-OpenComputers baseline

YES. MineOS BOOTS AND A LIVE DESKTOP SURVIVES SAVE AND RESTORE ON STOCK OPENCOMPUTERS SEMANTICS -- PUC Lua 5.2 plus real Eris, not LuaJ. This is the reference result the project did not have for any GUI OS, and it means a MineOS desktop is inside what the platform already delivers, so anything we fail to persist is OUR defect, not an inherited bound.

WHAT WAS ACTUALLY RUN (harness arm, ocelot-brain commit e98a5b2, v0.24.2, sbt 2.0.7 + JDK 17):
 - Getting an arbitrary OS onto a virtual disk turned out to need no installer: DiskManaged.customRealPath (DiskRealPathAware.scala:26-41) points an HDDManaged at any real directory, and ocelot-brain already SHIPS a MineOS boot ROM -- Loot.MineOSEFIEEPROM = new EEPROMFactory("MineOS EFI", "mineosEFI.lua") (loot/Loot.scala:63). The EFI scans filesystems for /OS.lua, setData()s the boot address and loads it. The repo laid out as an installed root (OS.lua + Libraries/Applications/Icons/Localizations/Wallpapers + Extensions/Mounts/Temporary + one passwordless /Users/root/) is 2.49 MB and fits a T3 HDD.
 - CROSS-PROCESS, which is the part that matters: process A boots to desktop and writes the gzipped workspace NBT (317,824 bytes); a FRESH JVM -- fresh LuaState, fresh PUC-Lua string-hash seed -- loads it in ~330 ms, resumes, runs 600 more ticks with crashes=0 and lastError=null, keeps animating the wallpaper and ticking the clock, restores the screen identically on 50/50 lines, and re-saves cleanly.
 - REFUSAL PRESSURE: 300 dense save attempts every 4 ticks from cold boot through desktop, with touch and key signals injected: 300 ok, 0 refused, 0 crashes.
 - The LuaJ guard was honoured at every entry point (assert NativeLuaArchitecture or die); every run printed NativeLua52Architecture and _VERSION = "Lua+Eris 5.2". No result here is a LuaJ vacuum.

THE CAVEAT, STATED PLAINLY BECAUSE IT BOUNDS THE CLAIM: the injected touch and key coordinates were guesses and NO APPLICATION WINDOW WAS EVER CONFIRMED OPEN. Every sampled save was of a desktop plus wallpaper animation, not of a desktop with a running app mid-draw. So the baseline covers "MineOS idle at the desktop", not "MineOS with Finder open scrolling a directory listing". A window-open save point is untested and is the obvious next run -- and it is not a formality, because three of the four most interesting MineOS shapes (the dock's topmost-window pairs() walk, the nested re-entrant workspace:start(), the in-flight button animation) only exist once a window is open.

TWO THINGS THE BASELINE DOES NOT SAY. (1) It is not evidence of "no refusals in MineOS". The gmatch refusals measured by two other arms are real MineOS code (FTP.lua:66-68 consumed at :493/:508/:915; IRC.app/Main.lua:591-593 measured refused at #data=150 and accepted at #data=830) -- they simply are not on the sampled desktop path, because they live in network APPLICATIONS. A 300/300 clean sample of the desktop is exactly consistent with a refusal waiting in the FTP client. (2) It does not settle the memory-ceiling question, because the machine's RAM configuration was not pinned at MineOS's declared floor -- see blobSize for the deciding experiment.

WHAT THE BASELINE DOES SETTLE, AND IT IS WORTH SAYING: stock Eris on stock PUC Lua handles a live GUI desktop's object graph -- 1.63 MB, deep widget trees with two back-references per node and a window<->dockIcon cycle, weak-valued package.loaded, and a suspended kernel coroutine -- correctly and repeatedly across a fresh process. Every shape in that graph is one we already accept. So the bar for the LuaJIT architecture on this OS is "match a thing that demonstrably works", and each of our REFUSALS is a regression against a working baseline rather than a limitation of the idea.

## Would a fourth OS be worth censusing?

MY RECOMMENDATION: STOP SAMPLING OPERATING SYSTEMS. Not because nothing plausible exists, but because the marginal finding per OS has collapsed while the marginal finding per HOST-SOURCE-READ and per APPLICATION-READ has not. Three structurally maximal-distance samples produced zero new Lua-shape categories. The third sample was chosen precisely for distance -- no scheduler at all, a 161 KB GUI layer, multiple user profiles, an in-OS debugger -- and it still landed entirely inside the fence. A fourth would have to be weirder than "from scratch, no coroutines, owns its framebuffer", and I cannot name one that is.

THE EVIDENCE THAT THE PAYOFF HAS MOVED ELSEWHERE. The three highest-value findings of this session did NOT come from reading an OS:
 - the uptime model correction came from Machine.scala:89/182/525/799/886/239/948;
 - the "CANNOT OCCUR" refutation came from FileSystem.scala:110 and Callback.java:88;
 - the two dangerous iterators were already known to ship with machine.lua, not with any OS.
And MineOS's own REFUSALS live in its applications (FTP, IRC), not its OS. So the two corpora that are still paying are the HOST and the APPLICATION LAYER, and neither has been censused as a first-class target.

WHAT I WOULD SPEND THE NEXT UNIT ON, in order:
 1. THE HOST AS A CENSUS TARGET. Enumerate every @Callback annotation and its direct/limit setting, because that table -- not the Lua language and not our serializer -- decides which constructs an OS may legally write. Today that is an invisible, undocumented, per-method contract that can turn a working file manager into a hard crash with a one-word Scala change.
 2. THE TWO OPEN MEASUREMENTS from this session, both one-run answers: save a real booted MineOS at its declared RAM floor on ocelot-brain (decides whether E4 is a ranked defect or retires), and capture a save point with an application WINDOW open (the only untested region of the stock baseline, and where three of MineOS's four interesting shapes live).
 3. AN APPLICATION CORPUS rather than a fourth OS -- say the top downloads from MineOS's own App Market. Cheap per sample, and it targets where the refusals actually are.
 4. THE OPEN F-SECTION ITEM that no OS can answer: whether OC mints a FRESH Java Value userdata per call, which would make perms as useless for userdata as it is for gmatch iterators. That is a one-hour read of the Java side and it should happen before anyone relies on perms for userdata.

IF SOMEONE INSISTS ON A FOURTH OS, exactly one profile would be worth it, and it is the one gap all three samples share: AN OS WHOSE SCHEDULER DOES NOT HAND-PUMP. Every OS so far preserves the yield-pump invariant (no thread mid-resume at a save), and each does so for the same forced reason -- OC yields do not cross coroutine boundaries -- so QuickOS, AxisOS and machine.lua all re-implement it independently, and MineOS reaches the same place by having no scheduler to break it with. That makes it a designed property we can state as a contract. But it is also the only structural assumption in our whole contract that a single OS could falsify, and the loaded gun is already visible: AxisOS's kernel_host_yield (kernel.lua:2548), exposed to rings 0/1 and called by nothing. An OS that CALLS something like it would produce a live cframe != NULL thread at a save point -- our most fundamental refusal -- and would be the only genuinely new data point available. I do not believe such an OS exists today. So: watch for one, do not go looking.

AND THE ONE PLACE THE SAMPLING IS HONESTLY NOT DONE, which I would not paper over: section B, THREADS. MineOS exercised frames hard (14-frame chains, nesting depth 8, ~40 open upvalues per activation) and threads not at all -- 4-6 `coroutine.` references in 102 files, all in one application, zero `coroutine.wrap` repo-wide, zero live coroutines at a normal save point. So "three OSes and the list did not move" is fully earned for A, D and E and only two-thirds earned for B. If a fourth sample is taken for any reason, the selection criterion should be "has a coroutine-based scheduler under load", not "has a novel UI".
