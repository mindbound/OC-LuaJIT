## 1. The Architecture interface contract and threading guarantees

**File: `src/main/java/li/cil/oc/api/machine/Architecture.java`** (186 lines). Full contract:

- `boolean isInitialized()` (L34) — false suppresses `component_added` signals and disables direct-call limits ("allows a quick boot phase... before switching to business-as-usual", L28-30). Machine.scala checks it in `consumeCallBudget` (L287) and `processAddedComponents` (L722).
- `boolean recomputeMemory(Iterable<ItemStack> components)` (L47) — return value = "whether any memory is present at all"; result gates startup (`hasMemory`, Machine.scala L155, L228-232 → crash `gui.Error.NoRAM`).
- `boolean initialize()` (L64) — called on machine start; may be called before the machine is connected to a network (load path); returning false fails startup.
- `void close()` (L70) — cleanup (Lua state destruction).
- `void runSynchronized()` (L86) — javadoc: "invoked from the main server thread, meaning it is safe to interact with the world without having to perform manual synchronization." Must leave state ready for `runThreaded(true)`.
- `ExecutionResult runThreaded(boolean isSynchronizedReturn)` (L112) — "expected to return within a very short time... at the latest when the Settings.timeout is reached (in which case it forces the state to crash)" (L98-101). Should consume one signal per call; no signal on synchronized return.
- `void onSignal()` (L128) — "may be called from any random thread" (L124-126); optional hook for reacting mid-`runThreaded`.
- `void onConnect()` (L137) — called when the machine node joins the component network (for e.g. connecting ROM filesystems).
- `void load(NBTTagCompound)` / `void save(NBTTagCompound)` (L147, L158) — persistence; javadoc explicitly names Eris for native Lua (L151-152). Tag compound is shared with the Machine.
- Nested annotations: `@Architecture.Name(String value)` (L166-170, RUNTIME retention) for display name, and `@Architecture.NoMemoryRequirements` (L182-185, `@Inherited`) allowing machines (e.g. microcontrollers) to assemble/run without RAM sticks.

**Threading model (`src/main/scala/li/cil/oc/server/machine/Machine.scala`, 1137 lines):**
- Executor: `private val threadPool = ThreadPoolFactory.create("Computer", Settings.get.threads)` (Machine.scala L1136); `ThreadPoolFactory.create` is `Executors.newScheduledThreadPool(threads, ...)` (`src/main/scala/li/cil/oc/util/ThreadPoolFactory.scala` L26). Default `computer.threads: 4`, `computer.timeout: 5.0`, `computer.executionDelay: 12` (ms) in `src/main/resources/application.conf` L125, L132, L207.
- `Machine` implements `Runnable`; `switchTo(Yielded | SynchronizedReturn)` schedules `this` on the pool with `executionDelay` ms delay (Machine.scala L966-969). The pool thread's `run()` takes `Machine.this.synchronized` ("really high level lock that we only use for saving and loading", L982-983), flips state to `Running`, and calls `architecture.runThreaded(isSynchronizedReturn)` (L1000). Result handling (L1003-1059): `Sleep` → `Sleeping` state with `remainIdle` ticks (interrupted early if signals queue, L1008-1017); `SynchronizedCall` → `SynchronizedCall` state; `Shutdown(reboot)` → `Restarting`/`Stopping`; `Error` → `crash(message)`.
- `runSynchronized` is invoked from `update()` — the server-tick method — when state is `SynchronizedCall` (L597-629), wrapped with `inSynchronizedCall = true` so `consumeCallBudget` is bypassed (L286-294, L602-604). After it returns, state becomes `SynchronizedReturn`, which reschedules the worker with `runThreaded(true)`.
- `save`/`load` are `Machine.this.synchronized(state.synchronized{...})` (L753, L821), and `save` bails if `isExecuting` (L826) and force-pauses 0.05s (L833) — so architecture `save()` never races `runThreaded`.
- Signal queue is bounded by `maxSignalQueueSize` (L110, L339); `signal()` may be called from any thread and calls `architecture.onSignal()` (L367).
- Per-tick: `update()` resets `callBudget = maxCallBudget` (L532), consumes energy, handles state transitions (Starting→Yielded, Restarting→close/start, Sleeping wake-up, Paused countdown) (L569-631).

## 2. Native Lua persistence (Eris)

**`src/main/scala/li/cil/oc/server/machine/luac/NativeLuaArchitecture.scala`** (438 lines):
- `save(nbt)` (L396-437): unlimits memory, asserts kernel thread at Lua stack index 1, then `SaveHandler.scheduleSave(machine.host, nbt, machine.node.address + "_kernel", persistence.persist(1))` (L407). If machine state contains `SynchronizedCall`/`SynchronizedReturn`, also persists stack index 2 (the pending sync-call closure or its result table) to `"_stack"` (L410-413). Saves `kernelMemory` (L415). **On persist failure** (`LuaRuntimeException`/`LuaGcMetamethodException`) it logs "Could not persist computer @ ..." and `nbt.removeTag("state")` (L426-432) — wiping the state stack so the machine loads as stopped.
- `load(nbt)` (L349-394): no-op unless `machine.isRunning`; clears stack, `persistence.unpersist(SaveHandler.load(nbt, address + "_kernel"))`, verifies `lua.isThread(1)` (L362-367); conditionally unpersists `"_stack"` and verifies function vs table depending on sync-call state (L368-375).
- **Yielded coroutines**: the *entire kernel coroutine* (the `LuaThread` created at `initialize()` L322 from `machine.lua`) is persisted as one Eris object from stack index 1; every user coroutine (bios, OpenOS threads) is reachable from it, so Eris serializes the whole coroutine graph including instruction pointers and upvalues. There is no per-coroutine handling in Java.

**`src/main/scala/li/cil/oc/server/machine/luac/PersistenceAPI.scala`** (177 lines):
- Gated everywhere by `Settings.get.allowPersistence` (= `!debug.disablePersistence`, Settings.scala L457).
- `initialize()` (L15-91): sets a global `persistKey` function returning `"__persist" + UUID` (L13, L17-21); then builds **perms/uperms tables** by recursively flattening everything reachable from `_G` (functions and tables only, deterministic sorted key order, dotted-path names like `"_G.component.invoke"`), storing `perms[value]=name` and `uperms[name]=value` in the Lua **registry** (L83-89). This is why "Persistence has to go last to ensure all other APIs can go into the permanent value table" (NativeLuaArchitecture.scala L56) — all C-function callbacks must be in perms because Eris cannot serialize C functions.
- `persist(index)` (L121-152): `configure()` sets `eris.settings("spkey", persistKey)` and `eris.settings("path", debugPersistence)` (L105-119); stops GC, calls `eris.persist(perms, obj)`, returns the byte array. `unpersist(bytes)` (L154-176) calls `eris.unpersist(uperms, str)`.
- The `spkey` ("special persistence key") mechanism is used in `machine.lua`: userdata proxy tables carry a method literally named by `persistKey()` (machine.lua L1061, L1134: `[persistKey and persistKey() or "LuaJ"] = function() ... end`) that Eris invokes to reconstruct unpersistable userdata on load.
- Eris is opened as a JNLua library: `state.openLib(jnlua.LuaState.Library.ERIS)` for 5.2/5.3/5.4 (LuaStateFactory.scala L68, L85, L103) — i.e. Eris is compiled *into* the shipped native Lua, not a separate lib.
- Persisted blobs go through `SaveHandler.scheduleSave` to external per-address files (not inline NBT), `src/main/scala/li/cil/oc/common/SaveHandler.scala`.

## 3. CRITICAL — LuaJ / non-persisting architectures: "reboot on chunk reload" IS a first-class supported mode

**`src/main/scala/li/cil/oc/server/machine/luaj/LuaJLuaArchitecture.scala`** (262 lines, `@Architecture.Name("LuaJ")` L24):

```scala
override def load(nbt: NBTTagCompound) {
    if (machine.isRunning) {
      machine.stop()
      machine.start()
    }
}
override def save(nbt: NBTTagCompound) {}
```
(L254-261). That is the **entire** persistence implementation: `save` is a no-op; `load` reboots the computer if the saved state says it was running. Machine.scala's generic load still restores components, signal queue, uptime, users, etc. (L753-819) — only the Lua execution state is lost.

- **Warning to players**: yes. On player login, if natives are unavailable and LuaJ wasn't explicitly requested: `player.addChatMessage(Localization.Chat.WarningLuaFallback)` (`src/main/scala/li/cil/oc/common/EventHandler.scala` L192-199). The string (`src/main/resources/assets/opencomputers/lang/en_US.lang` L219): *"Native Lua libraries are not available, computers will not be able to persist their state. They will reboot on chunk reloads."* Also a log warning at LuaStateFactory.scala L339-341: "Unsupported platform, you won't be able to host games with persistent computers."
- **Settings** (`src/main/scala/li/cil/oc/Settings.scala`): `forceLuaJ` (L455, `debug.forceLuaJ`, default false — application.conf L1529), `allowPersistence = !debug.disablePersistence` (L457, conf L1545-1549: "computers will automatically be rebooted when loaded after being unloaded... Only relevant when using the native library"), `registerLuaJArchitecture` (L485, conf L1640-1643: register LuaJ *alongside* natives so players can cycle to it).
- Registration logic (`src/main/scala/li/cil/oc/common/Proxy.scala` L74-91): natives registered if available (`Lua53`, `Lua54`, `Lua52` in that order, gated by `enableLua53/54` and `!forceLuaJ`); LuaJ registered if `LuaStateFactory.includeLuaJ` (= `!isAvailable || forceLuaJ || registerLuaJArchitecture`, LuaStateFactory.scala L33-35). `api.Machine.LuaArchitecture` = LuaJ if forced, else first registered arch (Proxy L89-91).
- The stock kernel itself branches on persistence availability: `if persistKey then -- otherwise we're in LuaJ` (`src/main/resources/assets/opencomputers/lua/machine.lua` L1524) and `[persistKey and persistKey() or "LuaJ"]` (L1061, L1134). Even native-arch persistence can silently fail per-save (unpersistable value) and OC degrades to a stopped/rebooting computer (NativeLuaArchitecture.scala L426-432).

**Conclusion for LuaJIT feasibility**: a `save` that writes nothing plus a `load` that does `machine.stop(); machine.start()` is exactly what the shipped LuaJ architecture does, and OC's machinery (state-tag removal, login warning, kernel branch) treats non-persistence as a supported degraded mode.

## 4. CPU item → architecture mapping

- **API entry point**: `li.cil.oc.api.Machine.add(Class<? extends Architecture>)` (`src/main/java/li/cil/oc/api/Machine.java` L33-35); javadoc: "Registering an architecture will make it possible to configure CPUs to run that architecture. This allows providing architectures without implementing a custom CPU item" (L27-29). Impl `object Machine extends MachineAPI` validates the class has a `(li.cil.oc.api.machine.Machine)` constructor and stores it in a `LinkedHashSet` preserving registration order (Machine.scala L1072-1086). `getArchitectureName` reads the `@Architecture.Name` annotation, falling back to simple class name (L1090-1094). Addon mods must call this in init or later, not pre-init (api/Machine.java L19-21).
- **Item NBT**: `DriverCPU` (`src/main/scala/li/cil/oc/integration/opencomputers/DriverCPU.scala`, implements `api.driver.item.MutableProcessor` + `CallBudget`): `architecture(stack)` reads `stack.getTagCompound.getString("oc:archClass")` and `Class.forName`s it; defaults to `api.Machine.architectures.headOption` (first registered) (L43-60). `setArchitecture` writes `archClass`/`archName` NBT (L62-67). `allArchitectures = api.Machine.architectures.toList` (L41) — so an addon-registered architecture automatically appears in cycling.
- **Shift+right-click cycling**: `src/main/scala/li/cil/oc/common/item/traits/CPULike.scala` L28-48 — on sneaking right-click (server side), cycles `driver.allArchitectures` with `(currentIndex + 1) % length`, calls `driver.setArchitecture`, and chat-messages the new `Architecture.Name`. Tooltip shows current arch (L24-26).
- **Instantiation**: `Machine.onHostChanged()` (Machine.scala L114-156) finds the CPU stack (Processor driver, `Slot.CPU`), gets `driver.architecture(stack)`, and instantiates it via `clazz.getConstructor(classOf[machine.Machine]).newInstance(this)` (L134); calls `onConnect()` if the network is up (L153) and `recomputeMemory` (L155).

## 5. Timeouts and call budgets — where enforcement lives

**Split across three layers:**
- **Direct-call budget: enforced in Machine.scala.** `consumeCallBudget(cost)` (L286-294) throws `LimitReachedException` when `cost > callBudget`; skipped while `!architecture.isInitialized` (boot phase) or `inSynchronizedCall`. `invoke(address, method, args)` (L385-402) charges `1.0 / annotation.limit` for `direct` callbacks; identical for `Value` callbacks (L404-415). `callBudget` is reset to `maxCallBudget` once per server tick in `update()` (L532); `maxCallBudget` is the *average* of all installed `CallBudget` drivers (L123-126); CPU budgets per tier are `Settings.callBudgets` `[0.5, 1.0, 1.5]` (Settings.scala L71-77, `DriverCPU.getCallBudget` L69).
- **Architecture's reaction to the budget limit**: `LimitReachedException` is caught by the arch's callback wrapper and turned into *zero results* (NativeLuaArchitecture.scala L76-77; LuaJ L60-61); the kernel's `invoke` in machine.lua (L1080-1103) treats 0 results as "limit for direct calls reached" and falls back to yielding a closure → `ExecutionResult.SynchronizedCall` → executed next server tick via `runSynchronized`. Indirect (non-direct) callbacks always take that synchronized path (1 call/tick).
- **Execution timeout (`Settings.timeout`, default 5.0s): enforced inside the sandbox kernel, on the worker thread — NOT in Machine.scala.** `SystemAPI` exposes `system.timeout()` returning `Settings.get.timeout` (`luac/SystemAPI.scala` L42-47). `machine.lua`: calibrates a `hookInterval` via bogomips (L1-40), defines `checkDeadline` which `error(tooLongWithoutYielding)` once `computer.realTime() > deadline` (L42-54); the main loop sets `deadline = computer.realTime() + system.timeout()` and `debug.sethook(co, checkDeadline, "", hookInterval)` around every `coroutine.resume` (L1518-1533). The resulting "too long without yielding" error propagates out as `ExecutionResult.Error`. Machine.scala merely reports/crashes on the result — it never kills the worker thread, so **a custom architecture must implement its own timeout** (the Architecture javadoc only *expects* return "at the latest when Settings.timeout is reached", Architecture.java L98-101). For LuaJIT this is the key constraint: LuaJIT's JIT-compiled code does not run debug hooks reliably (hooks only fire in the interpreter), so an OC-style `debug.sethook` watchdog would need JIT-off sections, `lua_sethook` from a watchdog thread (which aborts JIT traces), or instruction-count patching.

## 6. Native library shipping/extraction — precedent for LuaJIT natives

**`src/main/scala/li/cil/oc/server/machine/luac/LuaStateFactory.scala`** (460 lines):
- Natives are **shaded into the mod jar** from a separate artifact: `dependencies.gradle` L4-6: `shadowImplementation name: 'OC-LuaJ' 20220907.1`, `'OC-JNLua' 20230530.0`, `'OC-JNLua-Natives' 20220928.1` (the BlueAmulet builds). The repo tree contains no `assets/opencomputers/lib/` — it comes from the natives jar at build time.
- Library naming: `"libjnlua" + version + "-" + platformName + libExtension` where platform = `{windows|linux|darwin|freebsd|...}-{x86_64|x86|arm|aarch64}` and extension `.dll/.so/.dylib` (L133-167). Three factories: `Lua52/Lua53/Lua54` (L58-110), each `openLib(...ERIS...)`.
- Extraction (`init()`, L183-335): looks up `classOf[Machine].getResource(s"/assets/${Settings.resourceDomain}/lib/$libraryName")` (L213); copies to `${java.io.tmpdir}` (or `./` if `nativeInTmpDir=false`) as `OpenComputersMod-<modVersion>-<luaVersion>-<libName>` (L219-227); byte-compares an existing file and deletes mismatches (L243-282); sets rwx for all users (L292-295); `System.load(currentLib)` + creates and closes a test state under `LuaStateFactory.synchronized` (L317-324); sets `haveNativeLibrary`. Failure → warn + delete (L325-334). Overrides: `debug.forceNativeLibPathFirst` (load from disk path, L201-210), `debug.forceNativeLibPlatform`, `debug.alwaysTryNative` (Windows XP/2003 refusal, L188-198). `createState()` re-`System.load`s per state, applies `limitMemory` cap, opens libs, sandboxes (removes `dofile/loadfile/unpack/loadstring`, replaces `math.random` with per-state `java.util.Random`, `os.setlocale("C")`) (L347-441).
- This is a direct, reusable template for shipping LuaJIT `.dll/.so/.dylib` per platform inside an addon jar: resource lookup → tmp-dir extraction with version-stamped name → `System.load` → probe. Caveat vs LuaJIT specifically: OC's JNLua natives embed Eris and a custom allocator for `setTotalMemory` memory limiting (`limitMemory`, NativeLuaArchitecture.scala L152-163 with `ramScaleFor64Bit`); LuaJIT has neither Eris persistence nor jnlua's allocator hooks out of the box, and on 64-bit its GC arena constraints differ — so the natives-shipping precedent transfers, while the persistence and memory-limit features do not.

## Direct answers to feasibility-relevant facts
1. A LuaJIT addon architecture only needs: a public class implementing `Architecture` with a `(api.machine.Machine)` constructor, `@Architecture.Name("LuaJIT")`, registered via `api.Machine.add(...)` in init — it then appears automatically on shift-right-click CPU cycling.
2. OC-grade persistence (Eris) is a property of OC's patched native Lua + JNLua, not of the framework; the framework fully supports the LuaJ-style alternative (no-op save, reboot-on-load), including a built-in user-facing warning pattern.
3. Timeout/watchdog must be self-implemented inside the LuaJIT arch (OC does it with Lua debug hooks in `machine.lua`); direct-call budgeting comes for free via `machine.invoke`/`LimitReachedException` as long as the arch maps the exception to the "retry as synchronized call" protocol.
4. Memory limiting (`recomputeMemory`) is advisory for the framework (only its boolean return is used, to require RAM); actual byte-limiting is arch-internal (JNLua `setTotalMemory`); LuaJ ships with no memory enforcement at all (`LuaJLuaArchitecture.recomputeMemory` L100-103 just stores the number).

# KEY CLAIMS
- [high] In the GTNH OpenComputers fork, LuaJLuaArchitecture implements persistence as: save(nbt) is an empty no-op and load(nbt) calls machine.stop() then machine.start() if the machine was running — i.e. computers on a non-persisting architecture simply reboot on chunk/world reload, and OC warns players at login ('Native Lua libraries are not available, computers will not be able to persist their state. They will reboot on chunk reloads.', en_US.lang L219, sent from EventHandler.scala L197-199).
- [high] The Architecture plugin API is public and addon-friendly: li.cil.oc.api.Machine.add(Class) registers any class implementing Architecture with a constructor taking api.machine.Machine (validated in server/machine/Machine.scala L1076-1086); DriverCPU.allArchitectures returns api.Machine.architectures, so registered addon architectures automatically appear in shift+right-click CPU cycling (CPULike.scala L28-48) and are stored per-CPU-item as the 'oc:archClass' NBT string (DriverCPU.scala L43-67).
- [high] Native-Lua persistence is implemented entirely inside the architecture: PersistenceAPI builds perms/uperms tables by recursively flattening every function/table reachable from _G (PersistenceAPI.scala L15-91), and NativeLuaArchitecture.save persists the whole kernel coroutine at Lua stack index 1 (plus the pending synchronized-call value at index 2) via eris.persist to external save files through SaveHandler.scheduleSave (NativeLuaArchitecture.scala L396-437); Eris is a library compiled into OC's patched natives (LuaState.Library.ERIS, LuaStateFactory.scala L68/85/103), so it does not exist in stock LuaJIT.
- [high] Execution timeout (Settings.timeout, default 5.0s) is enforced inside the sandboxed Lua kernel (machine.lua L42-54, L1518-1533) via debug.sethook + a checkDeadline hook using system.timeout() (SystemAPI.scala L42-47) — Machine.scala never kills a runaway worker thread; whereas the direct-call budget IS enforced by Machine.scala (consumeCallBudget throwing LimitReachedException, L286-294, budget reset each tick at L532), with the architecture expected to convert that exception into a fall-back synchronized call (machine.lua invoke L1080-1103). runSynchronized runs on the main server thread from Machine.update() (L597-629); runThreaded runs on a shared ScheduledExecutorService pool of Settings.threads (default 4) workers (Machine.scala L968, L1136; ThreadPoolFactory.scala L26).
- [high] OC's natives are shipped by shading a separate natives jar (OC-JNLua-Natives 20220928.1, dependencies.gradle L4-6) into the mod jar and extracting /assets/opencomputers/lib/libjnlua{52,53,54}-<os>-<arch>.{dll,so,dylib} at runtime to java.io.tmpdir (version-stamped filename, byte-compare update, chmod, System.load, test-instantiate) in LuaStateFactory.init/createState (LuaStateFactory.scala L133-167, L183-341, L347-441).
