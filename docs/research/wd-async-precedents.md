Scratchpad path prefix `SP` = `C:\Users\astro\AppData\Local\Temp\claude\C--Users-astro-Downloads-OC-LuaJIT\b355bc57-105f-4f62-a48e-26f24e7e01db\scratchpad`.

## 1. LuaJIT's own CLI Ctrl-C handler — the canonical author-endorsed pattern

Fetched `luajit.c` from v2.1 to `SP\luajit_cli.c`. The pattern (lines 59–75, 128–140):

```c
static void lstop(lua_State *L, lua_Debug *ar)
{
  (void)ar;  /* unused arg. */
  lua_sethook(L, NULL, 0, 0);
  /* Avoid luaL_error -- a C hook doesn't add an extra frame. */
  luaL_where(L, 0);
  lua_pushfstring(L, "%sinterrupted!", lua_tostring(L, -1));
  lua_error(L);
}
static void laction(int i)
{
  /* Terminate process if another SIGINT happens (double CTRL-C). */
  signal_set(i, SIG_DFL);
  lua_sethook(globalL, lstop, LUA_MASKCALL | LUA_MASKRET | LUA_MASKCOUNT, 1);
}
```
`docall` installs `laction` on SIGINT only around `lua_pcall` and restores SIG_DFL after (`SP\luajit_cli.c:134-140`). Key properties:
- **Masks**: `CALL|RET|COUNT` with `count=1` → hook fires at the very next bytecode instruction, call, or return. No `MASKLINE` (PUC 5.4 `lua.c` adds `LUA_MASKLINE` too, `SP\puc_lua.c:76-80`; PUC 5.1 `lua.c` uses the same four-mask form). Note for our design: **the CHECKHOOK trace guard only tests `LUA_MASKLINE|LUA_MASKCOUNT`** (`SP\lj_record.c:2970`), so `MASKCOUNT` must be in the injected mask or compiled traces will not exit.
- **`lstop` semantics**: one-shot — clears the hook first, then raises a plain, *catchable* string error `"<where>interrupted!"` via `lua_error`. LuaJIT deliberately avoids `luaL_error` because a C hook doesn't add a stack frame (comment at line 64). PUC 5.4's `lstop` just uses `luaL_error(L, "interrupted!")` (`SP\puc_lua.c:63-67`).
- **Escalation**: resetting SIGINT to `SIG_DFL` means a second Ctrl-C kills the process — a two-stage soft/hard design in miniature. (In stock builds without `LUAJIT_ENABLE_CHECKHOOK`, Ctrl-C on a *compiled* infinite loop only works via the second, process-killing Ctrl-C.)
- **Thread-safety**: `lua_sethook` in LuaJIT carries the comment `/* This function can be called asynchronously (e.g. during a signal). */` (`SP\lj_dispatch.c:336-348`). It only writes `g->hookf`, `g->hookcount/hookcstart`, `g->hookmask`, calls `lj_trace_abort(g)` (aborts any in-progress trace *recording*) and `lj_dispatch_update(g,0)` (swaps interpreter dispatch tables). All state lives in **`global_State`, not per-coroutine** — so injecting on the main `lua_State` interrupts whichever coroutine is currently running in that VM (unlike PUC, where hooks are per-thread; this retroactively fixes a would-be weakness of CCLuaJIT arming only `mainRoutine`). PUC's 5.4 `lua.c` comment states the same rationale: a C signal "cannot just change a Lua state... this function only sets a hook" (`SP\puc_lua.c:70-80`).
- Cross-thread (rather than same-thread-signal) use is exactly what Mike Pall documents (§2) and what agentzh recommends (§3); memory-model propagation is eventual (plain stores read per-dispatch by the interpreter and per-iteration by CHECKHOOK traces via a volatile XLOAD). A fence/volatile handoff on the Java side is cheap hygiene.

## 2. Mike Pall / mailing-list statements

- **The CHECKHOOK charter, verbatim** (`SP\lj_record.c:2953-2972`, end of `lj_record_setup`): "*Regularly check for instruction/line hooks from compiled code and exit to the interpreter if the hooks are set. This is a compile-time option and disabled by default, since the hook checks may be quite expensive in tight loops. Note this is only useful if hooks are \*not\* set most of the time. Use this only if you want to \*asynchronously\* interrupt the execution. You can set the instruction hook via lua_sethook() with a count of 1 from a signal handler or another native thread. Please have a look at the first few functions in luajit.c for an example (Ctrl-C handler).*" The emitted IR is a **volatile `XLOAD` of `g->hookmask`, `BAND` with `MASKLINE|MASKCOUNT`, guarded `EQ 0`** — the volatile flag keeps it in the variant (per-iteration) part of loop traces, which is both why it works and why it costs (load+and+guard per iteration).
- **Hooks don't fire in compiled code**: freelists thread "Debug hooks and JIT" ([narkive mirror](https://luajit.freelists.narkive.com/lexU9r0S/debug-hooks-and-jit)) — Pall: "compiled code doesn't call any hooks"; "This doesn't work if some piece of code has been compiled before you've set the hook"; "You need to turn it off at the start if you plan to receive reliable hook calls"; hooks are "zero-cost, if not enabled" because dispatch tables are swapped instead of checked.
- **The CHECKHOOK miscompile and its fix**: freelists thread ["Infinite loop with LUAJIT_ENABLE_CHECKHOOK in v2.1"](https://www.freelists.org/post/luajit/Infinite-loop-with-LUAJIT-ENABLE-CHECKHOOK-in-v21) (Myria, 2022-06-01): with CHECKHOOK on and **no hook ever set**, JITted x64 code hung in a two-instruction self-loop `test [g->hookmask],0x0C / je self` — a degenerate trace whose only body was the hook check. Mike Pall replied next day: "Fixed. Thanks!" → commit **`d4b6bb80ea3b` 2022-06-02 "Fix ITERN loop detection when hook checks are enabled"** (verified via GitHub commits API). The fix is the `#ifdef LUAJIT_ENABLE_CHECKHOOK ref += 3` in `rec_itern`'s own-loop detection (`SP\lj_record.c:688-700`) — present in our local v2.1 copy, so **building from current v2.1 HEAD includes the fix**. Takeaway: CHECKHOOK is a rarely-exercised configuration; test `pairs()` loops and keep the hook window short.
- **Process isolation for truly untrusted code**: Pall on lua-l, 2011-02-21 ([lua-users.org/lists/lua-l/2011-02/msg01106.html](https://lua-users.org/lists/lua-l/2011-02/msg01106.html)): "The only reasonably safe way to handle untrusted Lua scripts is to isolate them in a process context and to make use of per-process quotas/limits provided by the operating system" — noting `string.find`/`string.rep` and other C functions can run forever or allocate unboundedly in both Lua and LuaJIT. (OC already mitigates the pattern-matching case specifically: machine.lua re-implements Lua pattern matching *in Lua* "so that timeouts also apply while matching stuff" — `SP\machine.lua:86-91`.)
- Community consensus per [lua-l 2015 "lua_sethook() thread safety"](http://lua-users.org/lists/lua-l/2015-12/msg00035.html): `lua_sethook` is the only Lua API call that is cross-thread/signal safe.

## 3. How sandboxing embedders bound LuaJIT execution

**OpenResty / ngx_lua — no preemption; author recommends exactly our design.** agentzh (Yichun Zhang) on [openresty-en](https://groups.google.com/g/openresty-en/c/NsmFB48gl-I): "The ngx_lua module has not yet provided a built-in mechanism for automatically aborting such infinite loop with a timeout"; the way to do it is "a custom OS thread to call lua_sethook() to add a hook with a count of 1 to abort the too hot Lua thread" plus "enable -DLUAJIT_ENABLE_CHECKHOOK for the LuaJIT build"; his *preferred* answer for untrusted input is a restricted DSL, not raw Lua. Production OpenResty otherwise trusts the cooperative event loop; a Lua infinite loop pins a worker at 100% CPU ([lua-nginx-module#1637](https://github.com/openresty/lua-nginx-module/issues/1637)). They did not patch LuaJIT for this (the openresty/luajit2 fork does not enable CHECKHOOK by default).

**Tarantool — the strongest production precedent.** [Discussion #5778](https://github.com/tarantool/tarantool/discussions/5778) proposed the exact recipe (POSIX signal → `lua_sethook` count=1 → error, with `LUAJIT_ENABLE_CHECKHOOK=1` for compiled code; PoC threw a LuajitError from the hook). Measured overhead of CHECKHOOK in their tests: **~0.15% on JIT-compiled loops** (sergos in #5778); [issue #7762](https://github.com/tarantool/tarantool/issues/7762) then **enabled `LUAJIT_ENABLE_CHECKHOOK` by default in Tarantool binaries** ("benchmarking showed negligible performance degradation"), merged via their luajit fork's build option (patch thread on lists.tarantool.org, merged 2022-11-11). What shipped as the user feature (2.11, 2023) is **fiber slices**: *cooperative* checks — box operations raise an error when the fiber has run >1s since yielding (`fiber.set_slice`/`fiber.check_slice`); CHECKHOOK is groundwork for async interruption. Important caveat raised there (gerold103): interrupting at arbitrary points risks corrupting in-flight transaction state — they preferred defined "unsafe points". (For OC this maps to: only inject while a resume is in flight, and treat the soft abort as a normal Lua error so kernel-level cleanup still runs.)

**Redis (PUC Lua 5.1, not LuaJIT) — independent invention of OC's re-arm escalation.** Verified in `redis/7.2/src/script_lua.c`: while a script runs with `busy_reply_threshold`, a standing `lua_sethook(lua, luaMaskCountHook, LUA_MASKCOUNT, 100000)` polls for timeout (line 1680); on `SCRIPT KILL` it escalates to `lua_sethook(lua, luaMaskCountHook, LUA_MASKLINE, 0)` with the comment "*Set the hook to invoke all the time so the user will not be able to catch the error with pcall and invoke pcall again which will prevent the script from ever been killed*" (lines 1617-1625). Affordable only because PUC's interpreter always services hooks; the two-stage UX (busy → KILL if no writes → else SHUTDOWN NOSAVE) parallels soft/hard abort.

**LÖVE / games**: no watchdog at all; an infinite loop in a callback freezes the game (love2d forums, multiple threads, e.g. [t=8491](https://love2d.org/forums/viewtopic.php?t=8491)); user code is trusted. Garry's Mod (LuaJIT) likewise; the [Metastruct/gmod_longjmp](https://github.com/Metastruct/gmod_longjmp) repo — "Escaping lua/C/C++ stack frames. DOES NOT WORK. For reference only what does not work." — is the recorded corpse of the longjmp-out-of-a-stuck-VM idea. eLua: interpreter-only on MCUs, nothing relevant found.

**Luau (Roblox) — the greenfield validation of the safepoint approach.** Luau's VM replaces debug hooks with a **host interrupt callback guaranteed to be called "eventually" at any function call or loop iteration**, and its native codegen **emits the same interrupt checks in compiled code** ([luau.org/sandbox](https://luau.org/sandbox/), [discussion #239](https://github.com/luau-lang/luau/discussions/239)); Roblox Studio's watchdog gives scripts 10s. Their stated residual hole is identical to ours: "a very long running script... a single C function that takes a lot of time." I.e., a modern sandboxing Lua designed from scratch converged on exactly `CHECKHOOK`-style compiled-code safepoints + a two-tier timeout — with the same native-call blind spot.

## 4. CC:Tweaked / Cobalt interruption model (the semantics CCLuaJIT cloned)

`SP\TimeoutState.java` (CC:T mc-1.20.x, read in full): `TIMEOUT = 7000ms` → soft abort flag; `ABORT_TIMEOUT = 1500ms` after that → hard abort; `ABORT_MESSAGE = "Too long without yielding"`. Javadoc: soft = "the Lua machine will attempt to abort the program in some safe manner (namely, throwing a 'Too long without yielding' error)"; hard = "destroy the entire Lua runtime and shut the computer down".

`SP\CobaltLuaMachine.java` (read in full): Cobalt (Java Lua interpreter) exposes an `InterruptHandler` polled by the VM at safepoints, including "within long-running processes (such as pattern matching)" (Cobalt `interrupt/InterruptHandler.java`) — the interpreter *owns* its safepoints, so no hook injection is needed. The handler (lines 60-68): hard-aborted/disposed → `throw new HardAbortError()` (a `java.lang.Error` — unwinds the entire interpreter, **uncatchable from Lua**); soft-aborted → throw `LuaError("Too long without yielding")` **once** per abort cycle (`thrownSoftAbort` latch, reset when the flag clears); paused → `InterruptAction.SUSPEND` (Cobalt can suspend/resume the whole VM — used for fair time-slicing across computers). The scheduler side signals via `state.interrupt()` (line 113). After `LuaThread.run` returns, `timeout.isHardAborted()` is re-checked and `HardAbortError` → `close()` + `MachineResult.TIMEOUT` (lines 131-146). Contrast with OC: Cobalt throws the soft error only once and relies on the impending hard abort to punish pcall-swallowers; OC instead re-raises at count=1 granularity (§5).

## 5. OC's abort semantics (verified in local sources) and the proposed Java watchdog state machine

**Stock/GTNH OC semantics** (`SP\machine.lua`, `SP\server_machine_Machine.scala`, `SP\luac_NativeLuaArchitecture.scala`, `SP\Settings.scala`, `SP\gtnh-oc\...\application.conf`):
- `computer.timeout = 5.0s` default (application.conf:132, `Settings.scala:60`). machine.lua main loop: `deadline = computer.realTime() + system.timeout()` before each top-level `coroutine.resume(co)`, with a count hook `debug.sethook(co, checkDeadline, "", hookInterval)` armed for the resume (machine.lua:1519, 1532; hookInterval calibrated ≥1000 via bogomips, lines 1-40).
- **Soft abort** = `checkDeadline` (machine.lua:45-54): past deadline → `debug.sethook(coroutine.running(), checkDeadline, "", 1)` (**re-arm on itself with count=1**), extend deadline **once** by `+0.5s` (`hitDeadline` latch), then `error(tooLongWithoutYielding)` where the error object is a unique table with `__tostring = "too long without yielding"` (line 44). The count=1 re-arm is the anti-swallow escalation: a sandbox `pcall` that catches it executes at most ~1 instruction before the hook re-raises; crucially the raise also lands on *unprotected* instructions (loop heads, call setup) of any `while true do pcall(...) end` griefing loop, so the error escapes user protection within a few instructions. Sandbox `pcall`/`xpcall` additionally check the deadline *before* running (763-768, 813-838), and `pcallTimeoutCheck` converts the table to its string form for user code (55-61).
- **Unwind path**: kernel ends with `return pcallTimeoutCheck(pcall(main))` (1548) → resume returns an error string → `NativeLuaArchitecture.runThreaded` builds `ExecutionResult.Error(error)` (`SP\luac_NativeLuaArchitecture.scala:277-284`) → `Machine.crash(message)` beeps `--`, stops the machine, and shows the message on the bluescreen (`SP\server_machine_Machine.scala:1027-1029, 304-313`).
- **Stock OC has no hard abort** because interpreted hooks are deterministic; the machine.lua mechanism *is* the whole watchdog. The Java side never kills anything (only OOM/kernel-panic style crashes are handled in `runThreaded`'s catches, 288-299).

**CCLuaJIT's Java-side two-stage version** (all read locally, `C:\Users\astro\Downloads\CCLuaJIT`):
- `TaskScheduler.java:250-292`: controller thread awaits runner completion **7000ms** → `computer.abort(false)` → await **1500ms** → `computer.abort(true)` → await **1500ms** → `runnerThread.interrupt(); runnerThread = null` (abandonment; a fresh runner thread is lazily created for the next task, line 241-245).
- `LuaJITMachine.java:236-251`: `softAbort`/`hardAbort` set `softAbortMessage` (+`hardAbortMessage` if hard) then call native `abort()`; `LuaJITMachine.cpp:804-807`: `lua_sethook(mainRoutine, thread_interrupt_hook, LUA_MASKCOUNT, 1)`. The hook (cpp:179-195) **clears itself**, then `try_abort` (cpp:373-389) raises `softAbortMessage` via `lua_error` — luajit.c-style one-shot, no re-arm. Two smart details worth copying: `invoke_java_fn` **also polls `try_abort` at every Lua→Java call boundary** (cpp:412), so aborts land even when the hook can't fire; and pending-yield requests are delivered by the same one-shot count-hook trick (cpp:457-460). Hard abort completes on the Java side after resume returns: `hardAbortMessage != null → destroyLuaState()` (`LuaJITMachine.java:216-219`). But CCLuaJIT ran with the JIT never enabled, so none of this was ever exercised against compiled traces.

**Proposed state machine for OC-LuaJIT** (Java watchdog thread + native injection; LuaJIT built with `-DLUAJIT_ENABLE_CHECKHOOK` from v2.1 HEAD ≥ `d4b6bb80ea3b`):

Machine.lua modification: **never arm a standing hook** (delete the `debug.sethook` calls around resumes and the bogomips calibration); keep `deadline`/`hitDeadline`/`tooLongWithoutYielding`/`checkDeadline` and all sandbox pcall/xpcall deadline logic; register `checkDeadline` (or a small wrapper) in the Lua registry at boot so C can call it.

States (per machine; `T0` = moment `runThreaded`'s `lua_resume` is entered; timeout = `Settings.timeout` = 5.0s):
1. **RUNNING** — watchdog records `deadline = T0 + timeout`. Resume returns → clear, done. (1:1 with machine.lua's own `deadline`, since machine.lua does exactly one top-level resume per `runThreaded`.)
2. **SOFT_ABORT** at `deadline`: Java sets `softPending`; native call `lua_sethook(L_main, watchdog_hook, LUA_MASKCALL|LUA_MASKRET|LUA_MASKCOUNT, 1)` (luajit.c mask set; `MASKCOUNT` is mandatory — it is what the CHECKHOOK trace guard tests). The C hook does **not** clear itself while `softPending`; it looks up the registry `checkDeadline` and `lua_call`s it — machine.lua then applies its own `+0.5s` grace, count=1 re-arm semantics, and raises the identical `tooLongWithoutYielding` table, preserving every sandbox behavior (pcallTimeoutCheck, xpcall special-case, rawequal identity) byte-for-byte. Compiled traces exit at the next iteration via the CHECKHOOK guard; in-progress recording is aborted by `lua_sethook` itself. Expected outcome: resume returns with `"too long without yielding"` → `ExecutionResult.Error` → `Machine.crash` — indistinguishable from stock OC. On return, always `lua_sethook(L, NULL, 0, 0)` before the next resume.
3. **HARD_ABORT** at `deadline + 1.5s` (CC precedent; resume still in flight): set `hardPending`, re-inject the hook (idempotent). Hook behavior unchanged mechanically (count=1 error storm defeats Lua-level swallowers), but Java bookkeeping differs: when the resume *does* return — normally, with an error, or even "successfully" because malicious code converted the error into a yield — the machine is condemned: `lua_close` the state from the Java thread (only now, with no resume in flight), and report `ExecutionResult.Error("too long without yielding")` → `Machine.crash` shows the standard message and the computer stops. This mirrors CC's "destroy the entire Lua runtime" and CCLuaJIT's `hardAbortMessage → destroyLuaState` exactly.
4. **ABANDON** at `deadline + 3.0s` (resume never returned → stuck in a C builtin/FFI, or a trace in a build without working CHECKHOOK): last resort, see §6. Requires the resume to run on a **dedicated per-machine runner thread** (CCLuaJIT's controller/runner split), with `runThreaded` (on OC's shared executor) awaiting it with a timeout — never abandon an OC pool thread. Mark machine dead, return `ExecutionResult.Error("too long without yielding")` (crash + bluescreen as usual), leak the runner thread and the `lua_State` (do **not** `lua_close` — see §6), leave the hook armed with an `abandoned` flag so that *if* the trace ever does hit a safepoint, the hook raises, the runner unwinds, observes abandonment, closes the state on its own thread, and exits.

Deltas vs. OC stock worth documenting for users: identical 5s + 0.5s-grace soft semantics and identical crash message; new hard/abandon stages only trigger where stock OC would have hung an executor thread forever.

## 6. The last-resort problem: threads stuck in native code

- **Thread abandonment (CCLuaJIT precedent)** — `TaskScheduler.java:286-290`: after both aborts fail, `runnerThread.interrupt(); runnerThread = null; done = true`. `interrupt()` only helps a thread blocked in Java waits (their native pull-event wait converts it to `InterruptedException` → `destroyLuaState`, `LuaJITMachine.java:227-228`); a thread spinning in a trace or C builtin ignores it and **burns a core forever**. Hazard found in their code: a later `unload()`/`finalize()` (`LuaJITMachine.java:144-148, 269-271`) calls `destroyLuaState()` → `lua_close` on a state possibly still executing on the abandoned thread — a cross-thread use-after-free. Our design fixes this with the deferred-close-on-eventual-return rule (§5.4). This is also CC's own historical model (ComputerCraft's ComputerThread abandoned stuck workers the same way).
- **TerminateThread (Windows)** — MSDN Remarks, verbatim: "TerminateThread is a dangerous function that should only be used in the most extreme cases... If the target thread owns a critical section, the critical section will not be released. If the target thread is allocating memory from the heap, the heap lock will not be released... the state of the DLL could be destroyed." In a JVM this is fatal in practice: the thread may hold the CRT heap lock (LuaJIT's allocator), JVM-internal mutexes via JNI, or be attached to the JVM (its JNIEnv/thread state is never detached) — a later GC safepoint or malloc can deadlock or corrupt the whole server process. Never acceptable for a Minecraft server addon.
- **pthread_cancel (POSIX)** — asynchronous cancellation can land between any two instructions (same locked-mutex/heap-lock problems, plus no unwinding through LuaJIT's non-C++ frames); deferred cancellation only takes effect at cancellation points (blocking syscalls) which a spinning trace or C loop never reaches. Equally unusable inside a JVM. Java's own `Thread.stop()` was deprecated-then-removed for precisely these reasons.
- **Process isolation** — Mike Pall's actual recommendation for untrusted code (§2): run the VM in a child process, bound it with OS quotas, and `kill(2)` it with impunity. Maximum-robustness option but heavyweight for OC (per-computer IPC for every component call, save/load, Windows+Linux server support); reasonable future escape hatch, not the v1 design. No Minecraft Lua mod surveyed does this.
- **mcode patching / longjmp tricks** — no working precedent found. [gmod_longjmp](https://github.com/Metastruct/gmod_longjmp) is explicitly labeled "DOES NOT WORK". Patching trace mcode from another thread (int3 injection etc.) has no precedent in any surveyed system and races with the VM's own trace management (`lj_trace_flushall` and friends must run on the VM thread, e.g. from inside an armed hook, never cross-thread). LuaJIT's own profiler interrupts traces only to *sample*, via a signal, not to abort them.
- **Partial backstop that costs nothing**: OC's JNLua-style allocator quota (`setTotalMemory`, `NativeLuaArchitecture.recomputeMemory`) remains active with LuaJIT builds using a custom allocator — any *allocating* runaway (string building, table growth) eventually faults with "not enough memory" even mid-trace, independent of hooks. Only allocation-free register loops in C/FFI escape both the hook and the allocator, which is exactly the residual hole Luau documents too (§3).

## Design conclusions grounded in precedent
1. The chosen mechanism (no standing hook; watchdog thread injects `lua_sethook(count=1)`; `LUAJIT_ENABLE_CHECKHOOK` build) is the **author-documented** pattern (lj_record.c comment points at luajit.c and explicitly says "from a signal handler or another native thread"), independently recommended by agentzh for OpenResty and adopted by Tarantool (CHECKHOOK on by default; ~0.15%–negligible measured overhead).
2. Keep the hook armed only during the abort window (arm → error → clear on resume-return); this both preserves JIT performance and shrinks exposure to CHECKHOOK-corner bugs; build from v2.1 ≥ `d4b6bb80ea3b` (June 2022 ITERN fix) and include a `pairs()`-loop CHECKHOOK regression test.
3. Route the injected C hook into machine.lua's own `checkDeadline` to inherit OC's exact soft-abort semantics (tooLongWithoutYielding identity, +0.5s grace, count=1 re-arm anti-swallow — the same escalation Redis invented independently).
4. Two-stage timings with precedent: soft at `Settings.timeout` (5s, OC), hard at +1.5s and abandon at +3s (CC:T's 1500ms constants); hard abort = post-resume `lua_close` + `Machine.crash("too long without yielding")` (CC/CCLuaJIT semantics mapped onto OC's `ExecutionResult.Error` path).
5. Last resort is **abandonment with deferred close** on a dedicated runner thread — never `TerminateThread`/`pthread_cancel` in a JVM, never `lua_close` under a live resume (fixes CCLuaJIT's latent race). Process isolation is the only stronger option and is deferred.

# KEY CLAIMS
- [high] LuaJIT's own CLI Ctrl-C handler is the canonical async-interrupt pattern — laction does lua_sethook(globalL, lstop, LUA_MASKCALL|LUA_MASKRET|LUA_MASKCOUNT, 1) and lstop clears the hook and raises a catchable 'interrupted!' error — and lj_record.c's LUAJIT_ENABLE_CHECKHOOK comment explicitly blesses setting a count=1 instruction hook 'from a signal handler or another native thread', pointing at luajit.c as the example; the trace-side check is a volatile XLOAD of g->hookmask guarded against MASKLINE|MASKCOUNT==0, so the injected mask must include LUA_MASKCOUNT for compiled traces to exit.
- [high] Production precedent exists: Tarantool enabled LUAJIT_ENABLE_CHECKHOOK by default (issue #7762, after measuring ~0.15%/negligible overhead) alongside cooperative fiber slices, and OpenResty's agentzh states ngx_lua has no built-in abort and recommends precisely 'a custom OS thread to call lua_sethook() with a count of 1' plus -DLUAJIT_ENABLE_CHECKHOOK; Luau independently designed the equivalent (interrupt callbacks at safepoints, emitted in native codegen too), while LÖVE/gmod simply hang on infinite loops.
- [high] CHECKHOOK had one known miscompile — Myria's June 2022 freelists report of JITted code spinning on 'test [hookmask],0x0C / je self' with no hook set — which Mike Pall fixed next day in v2.1 commit d4b6bb80ea3b ('Fix ITERN loop detection when hook checks are enabled'); the fix (ref += 3 in rec_itern) is present in the current v2.1 sources we hold locally.
- [high] CCLuaJIT is a faithful clone of CC:Tweaked's abort semantics — 7000ms to soft abort, +1500ms to hard abort, +1500ms to thread abandonment (TaskScheduler.java:250-292), soft/hard delivered by injecting lua_sethook(mainRoutine, hook, LUA_MASKCOUNT, 1) whose hook clears itself and lua_errors the abort message, with an extra try_abort poll at every Lua->Java call boundary, and hard abort completed by lua_close after resume returns — but its abandonment path leaks a spinning thread and its later unload() can lua_close a state still executing on the abandoned thread (use-after-free race).
- [high] OC's expected semantics, verified in GTNH machine.lua and the Scala machine: soft abort is the catchable tooLongWithoutYielding table raised by checkDeadline, which grants one +0.5s grace and re-arms itself as a count=1 hook so pcall-swallowing code is re-interrupted within an instruction (the same escalation Redis independently implements for SCRIPT KILL); an unhandled timeout unwinds to ExecutionResult.Error('too long without yielding') and Machine.crash; stock OC has no hard abort at all, so our Java watchdog's hard stage (post-resume lua_close + crash) and last-resort stage (dedicated-runner-thread abandonment with deferred close; never TerminateThread/pthread_cancel inside a JVM) are additions that only fire where stock OC would hang an executor thread forever.
