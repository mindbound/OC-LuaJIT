# Serializing a suspended LuaJIT coroutine (pinned v2.1, GC64/LJ_FR2, x64) — what the source says

All line references are to `C:/Users/astro/Downloads/OC-LuaJIT/prototype/LuaJIT/src/...` at the pinned commit.

## (1) Anatomy of a coroutine suspended at a plain `coroutine.yield`

### The yield itself
`coroutine.yield` is a **fast function executed entirely in the ASM VM** (`vm_x64.dasc:1703-1714`):

```
|.ffunc coroutine_yield
|  test aword L:RB->cframe, CFRAME_RESUME   // only yieldable if entered via vm_resume
|  jz ->fff_fallback
|  mov L:RB->base, BASE                     // L->base = base of the yield ffunc frame
|  lea RD, [BASE+NARGS:RD*8-8]
|  mov L:RB->top, RD                        // L->top = base + n_yielded
|  xor RDd, RDd
|  mov aword L:RB->cframe, RD               // L->cframe = NULL   <-- verified
|  mov al, LUA_YIELD
|  mov byte L:RB->status, al                // L->status = LUA_YIELD
|  jmp ->vm_leave_unw                       // return LUA_YIELD from lj_vm_resume
```

The C-API path is identical in effect: `lua_yield` (`lj_api.c:1188-1203`) moves the results down to `L->base`, then `L->cframe = NULL; L->status = LUA_YIELD; return -1`. **`cframe == NULL` for any suspended coroutine is confirmed twice in source** (`vm_x64.dasc:1710-1711`, `lj_api.c:1201`), and it is a *precondition* checked by both resume paths: the resume ffunc rejects `cframe != 0` (`vm_x64.dasc:1578`), and `lua_resume` requires `L->cframe == NULL && L->status <= LUA_YIELD` (`lj_api.c:1231`). The C stack of `lj_vm_resume` is fully unwound at yield (`vm_leave_unw`, `vm_x64.dasc:455-457`); the resume C frame is rebuilt from scratch on the next resume (`vm_x64.dasc:575-590`, note `lea KBASE, [esp+CFRAME_RESUME]` — the CFRAME_RESUME tag bit, `lj_frame.h:275`).

### Slot-by-slot stack picture (LJ_FR2/GC64)
`stack_init` (`lj_state.c:173-185`): `stack[0]` = the thread itself as a TValue (`setthreadV`, needed for `curr_funcisL` on an empty stack), `stack[1]` = nil (FR2 dummy), initial `base = top = stack+2`. All slots above are nil-cleared (`lj_state.c:183-184`, and on every resize `lj_state.c:78-79`).

At suspension:
- `[L->base-2]` = the `coroutine.yield` builtin (a tagged GCfunc TValue; frame func slot, `lj_frame.h:34-46`).
- `[L->base-1].ftsz` = the **frame link**: a raw 64-bit pointer to the caller's next bytecode instruction (`ins_call` stores caller PC at `[BASE-8]`, `vm_x64.dasc:250-254`; `setframe_pc`/`frame_pc`, `lj_frame.h:48,51`). Its low 2 bits are 00 = `FRAME_LUA` (`lj_frame.h:14-27`).
- `[L->base .. L->top)` = the yielded TValues. After the *parent* consumes them via the `coroutine.resume` ffunc, `co->top` is reset to `co->base` (`vm_x64.dasc:1631-1633` "Clear coroutine stack"); a C host (JNLua) similarly pops them. Either state is just (base, top) offsets + TValues.
- Below `L->base-2`: the caller frame chain (see below), terminating at the bottom frame at `stack+2` whose link is a **pure integer delta tagged `FRAME_CP`** left by `vm_resume` (`vm_x64.dasc:581` sets `PCd = FRAME_CP`; label 2 at `vm_x64.dasc:635-653` turns it into `delta+FRAME_CP` and `ins_call` stores it). No pointer into C in it — the tie to C is exclusively `L->cframe`, which is NULL.

`lua_State` itself (`lj_obj.h:692-706`) contains nothing else that needs persisting: `status` (byte), `base`/`top` (→ offsets from `stack`), `stacksize`/`maxstack` (recreate), `openupval` (rebuild, see §6), `env` (table ref), `cframe` (restore NULL), `glref/gclist/dummy_ffid` (reconstructed).

### Frame-link representability — yes, three symbolic forms cover everything
`frame_ftsz` under FR2 is one 64-bit word per frame (`lj_frame.h:47-51`), decoded by type bits (`lj_frame.h:14-27, 75-85`):
- **FRAME_LUA** (bits 00): the word *is* a bytecode pointer. Serialize as `(proto, bcpos)` via `proto_bc`/`proto_bcpos` (`lj_obj.h:421-422`); the owning proto is the function of the *next-outer* frame, discovered during the same walk. Previous frame found via `frame_prevl(f) = f - (1+LJ_FR2+bc_a(frame_pc(f)[-1]))` (`lj_frame.h:108`) — needs no extra data.
- **Delta types** (FRAME_VARG, FRAME_PCALL, FRAME_PCALLH, FRAME_CP, FRAME_C): the word is `byte_delta | type` (`frame_prevd`, `lj_frame.h:109`) — a small integer bounded by LUAI_MAXSTACK; store `(type, delta)` verbatim, position-independent.
- **FRAME_CONT** (bits 010): `(type, delta)` plus two extra slots (see §2).

So the answer to (1) is **yes**: a suspended stack = (a) an array of TValues `[0, top)`, (b) one `(proto, pcofs)` pair per FRAME_LUA link and per continuation-PC slot, (c) symbolic `(type, delta)` tags for the rest — plus the scalar `L` fields. Nothing else is live.

## (2) FRAME_CONT: a finite, symbolizable continuation set

Under LJ_FR2 the continuation frame has two extra slots below the func slot: `[base-4]=cont, [base-3]=contpc, [base-2]=func, [base-1]=ftsz` (`lj_frame.h:40-44`), accessed as `frame_contv(f) = ((f)-3)->u64` and `frame_contf(f) = (ASMFunction)(uintptr_t)((f)-3)->u64` (`lj_frame.h:91,97`). `setcont` under FR2 stores the **raw 64-bit ASM address** (`lj_obj.h:896-898`) — this is the one datum that must be relocated symbolically across a process restart.

The set is closed and small. Declarations: `lj_vm.h:108-114` — `lj_cont_cat`, `lj_cont_ra`, `lj_cont_nop`, `lj_cont_condt`, `lj_cont_condf`, `lj_cont_hook`, `lj_cont_stitch`. Labels in `vm_x64.dasc`: `cont_cat:721`, `cont_ra:790`, `cont_nop:868`, `cont_condt:939`, `cont_condf:948`, `cont_hook:2316`, `cont_stitch:2376`. Plus two **integer** specials that are values, not addresses: `LJ_CONT_TAILCALL=0`, `LJ_CONT_FFI_CALLBACK=1` (`lj_frame.h:87`), distinguished in `cont_dispatch` by `cmp RA,1; jbe` (`vm_x64.dasc:699-703`). Exhaustiveness verified by grepping every `setcont(` call site: `lj_meta.c:128` (mmcall: ra/nop/cat/condt/condf via callers at `lj_meta.c:156,194,238,343,400,417,432,462,475`), `lj_api.c:1208` (hook), `lj_ffrecord.c:138` (stitch). A 3-bit symbolic enum + table of `lj_cont_*` addresses at load time fully relocates this.

Which can actually be frozen in an OC persist:
- **ra/nop/cat/condt/condf**: yes — a yield inside a Lua-function metamethod (`__index`, `__newindex`, arith, concat, comparisons). Fully serializable.
- **lj_cont_hook**: only via yield-from-a-debug-hook (`lj_api.c:1204-1222`); it stores a raw MULTRES integer in the aux slot `[mbase-40]` (`lj_api.c:1207`, restored at `vm_x64.dasc:2319-2320`). OC does not persist with active hooks — can be declared unpersistable or handled (the aux slot is a plain integer).
- **lj_cont_stitch**: *can* occur — `coroutine.yield` has no `LJLIB_REC` (`lib_base.c:613`), so a compiled trace calling it goes through `recff_nyi` → stitch (`lj_ffrecord.c:161-169`), and while the stitched call runs, the stack holds a cont_stitch frame whose slot `[mbase-40]` contains a tagged reference to the parent **GCtrace** (`lj_ffrecord.c:110-142`; `lj_asm.c:2172-2174` patches the KGC trace constant; read back at `vm_x64.dasc:2380`). This is the one JIT-entangled stack slot. It is *designed* to degrade: `cont_stitch` treats a zero value (`vm_x64.dasc:2403-2404`) or `traceno==link` (`:2405-2408`) as "blacklisted" and falls through to `cont_nop`; `lj_trace_flushall` deliberately sets `T->traceno = T->link = 0` — comment "Blacklist the link for cont_stitch" (`lj_trace.c:288`). Serializer rule: on persist, write `u64 = 0` for the `[mbase-40]` slot of any cont_stitch frame; resume then behaves exactly like the interpreter (cont_nop). Correctness is guaranteed by the same mechanism jit.flush relies on.

## (3) Which frames are unserializable, and can they occur? (No — the VM forbids it)

`FRAME_C`/`FRAME_CP` markers are created only by C→VM entries: `vm_call` (`vm_x64.dasc:620`), `vm_pcall` (`:613`), `vm_cpcall` (`:681`), `vm_resume` (`:581`). All except `vm_resume` push an **untagged** C frame onto `L->cframe` (`vm_x64.dasc:629-633,671-673`); only `vm_resume`'s carries the `CFRAME_RESUME` bit. Both yield paths require that the *top* cframe be resume-tagged: `cframe_canyield` (`lj_frame.h:292`, used at `lj_api.c:1192`) and the ffunc test (`vm_x64.dasc:1705`); otherwise → `LJ_ERR_CYIELD` (`lj_api.c:1225`). Therefore **a suspended coroutine (cframe==NULL) can never contain an interior FRAME_C/FRAME_CP frame with a live C activation** — such a state is unreachable because the yield would have been refused. The only C-typed link in a suspended stack is the bottom `FRAME_CP` delta from `vm_resume`, whose C frame no longer exists.

How "fully resumable" yields across pcall and metamethods work — confirmed from source, no C frames involved:
- `pcall`/`xpcall` are fast functions that push only a Lua-stack delta frame `PCd = 16+FRAME_PCALL` / `24+FRAME_PCALL` (+1 → FRAME_PCALLH if a hook is active at call time) and jump straight to `vm_call_dispatch` (`vm_x64.dasc:1523-1556`). No cframe change.
- Metamethods: the C helpers (`lj_meta_tget` etc.) *return* before the metamethod runs; `mmcall` (`lj_meta.c:110-135`) lays out `[cont][contpc][mo][a][b]` on the Lua stack, and the interpreter builds the FRAME_CONT link and dispatches the call itself (`vmeta_tgetv` label 3, `vm_x64.dasc:797-806`; `vmeta_tsetv` label 3, `:872-885`). A yield inside the metamethod freezes only Lua-stack state.
- Yield **from a C function** (lua_yield → return -1): legal and serializable in principle. The C function's Lua frame has a *FRAME_LUA* link (interpreter calls C functions inline via BC_FUNCC, `vm_x64.dasc:4889-4923`; `ins_call` stored the Lua caller's PC), the -1 return triggers `vm_returnc → vm_unwind_yield` (`vm_x64.dasc:410-412,489-491`), and on resume the resume args become the C function's return values (LuaJIT has no `lua_yieldk`; the C body is never re-entered). Needs the C closure in the perms table; OC's protocol doesn't do this anyway.
- The FFI-only cases (`LJ_CONT_TAILCALL` via `lj_meta_tailcall`, used only from `lib_ffi.c`/`lj_carith.c`; `LJ_CONT_FFI_CALLBACK` from `lj_ccallback.c:592`) cannot arise in the FFI-less OC sandbox.

## (4) The kernel thread (lua_newthread + lua_resume from C)

Identical to (1). `lua_newthread` → `lj_state_new` (`lj_api.c:738-746`, `lj_state.c:362-378`): fresh stack via the same `stack_init`, `cframe = NULL`, `status = LUA_OK`, env inherited. `lua_resume` (`lj_api.c:1229-1234`) enters the same `lj_vm_resume`; the initial call plants the same bottom `FRAME_CP` delta (`vm_x64.dasc:581,635-653`), and yield leaves the same `{cframe=NULL, status=LUA_YIELD, base/top framing}`. The only difference from a `coroutine.resume`d coroutine is *who* reads the yielded values (JNLua reads `[base,top)` and pops, vs. the resume ffunc copying and clearing) — irrelevant to the serialized form. After restore, the host's `lua_resume` works because the precondition `cframe==NULL && status<=LUA_YIELD` is exactly what the serializer re-establishes. A fresh never-resumed coroutine (status LUA_OK, `top==base+1`, initial function at `[base]`, per `lib_base.c:603-611` and the status logic at `lib_base.c:567-582`) is a trivial sub-case.

## (5) JIT bytecode patching, hot counters, other entanglements

- **Trace unpatching is complete for root traces.** `lj_trace_flushall` (`lj_trace.c:276-303`) walks every trace; root traces go through `trace_flushroot → trace_unpatch` (`lj_trace.c:204-232`): `BC_JFORL` → restore `startins` + re-patch target `JFORI→FORI`; `BC_JITERL`/`BC_JLOOP` → restore `startins`; `BC_JFUNCF` → restore `startins`; anything else is "already unpatched". It also zeroes the penalty cache (`:295`), frees all mcode and exit stubs (`:297-298`), and blacklists stitch links (`:288`). So after a flush, **no J-variant opcodes remain in any proto**.
- **Blacklisting is NOT undone by flush.** `PROTO_ILOOP`-patched bytecode (`BC_IFUNCF/IFORL/IITERL/ILOOP`, flags at `lj_obj.h:402-403`, patching at `lj_trace.c:387,423-430`) survives; only `lj_trace_reenableproto` (`lj_trace.c:187-201`, called from `luaJIT_setmode`, `lj_dispatch.c:229`) restores it. The I-variants are ordinary interpreter opcodes, so serializing them verbatim round-trips *within the pinned build* — but they permanently suppress hot-counting for those protos after restore. The canonical normalization exists in-tree: `lj_bcwrite.c:300-315` maps `IFORL/IITERL/ILOOP/JFORI → FORL/ITERL/LOOP/FORI` and recovers J-variants from `traceref(J,rd)->startins` (the latter requires live traces, so a serializer should either flush first and only normalize I-variants, or copy this exact logic). Recommended order: normalize I-variants at dump time (bcwrite-style) and drop `PROTO_ILOOP`; preserve `PROTO_NOJIT` only where user-set.
- **Hot counters are trivially cold-restartable.** They are a global 64-entry array in `GG_State` keyed by `(pc>>2)&63` (`lj_dispatch.h:75-76,102,126-129`), not attached to any GC object; a fresh VM reinitializes them. Penalty slots (`J->penalty`, raw `MRef pc` keys, `lj_trace.c:392-413`) are likewise process-local and zeroed by flushall — losing them merely means a proto may retry compilation before re-blacklisting.
- **Remaining entanglements**: (a) the cont_stitch `[mbase-40]` GCtrace slot (§2 — zero it); (b) `GCproto->trace` root-chain anchor, cleared by flushall (`lj_trace.c:241-255`); (c) `GCupval->dhash` (JIT alias-analysis hash) — regenerated values after restore only affect compilation heuristics, not semantics; (d) `G->cur_L`/`jit_base` — transient, never persisted.

## (6) Is Pall's 2008 "could be serialized with some effort" still true? Yes — the effort, as a schema

Per suspended thread, the serializer writes:

1. **Header**: `status` byte (LUA_OK for fresh/dead-empty, LUA_YIELD for suspended; error statuses for dead-with-error), `top_ofs`, `base_ofs` (slot offsets from `stack`), optionally `stacksize` hint. Restore: `lj_state_new`, grow stack to fit, set base/top, `cframe=NULL` (already), status byte.
2. **Slots `[2, top)`** as ordinary Eris-style TValue records (slot 0 = self-thread and slot 1 = nil are reconstructed implicitly, `lj_state.c:180-181`). Every value is a normal GC ref/number/primitive — same machinery as table values.
3. **Frame-link rewrites**, produced by walking `f = L->base-1; while (f > stack+1+LJ_FR2) f = frame_prev(f)` (`lj_frame.h:108-111`). For each frame record one of:
   - `LUA(proto_ref, bcpos)` — restore `ftsz = (int64_t)(proto_bc(pt)+bcpos)`; validate `0 < bcpos < pt->sizebc`;
   - `DELTA(type ∈ {C,CP,VARG,PCALL,PCALLH}, delta_bytes)` — restore verbatim (only the bottom frame may be C/CP);
   - `CONT(delta_bytes, cont_sym ∈ {cat,ra,nop,condt,condf,hook,stitch,int0,int1}, contpc=(proto_ref,bcpos), aux)` — restore `ftsz`, `setcont` from the relocation table, `setframe_pc` for contpc; aux slot: MULTRES integer for hook, forced 0 for stitch.
   The func TValues at `[framebase-2]` are covered by item 2 (closures serialized Eris-style; C closures via perms).
4. **Open upvalues**: for each open GCupval reachable from serialized closures, record `(owner_thread, slot_index)`; restore by find-or-create in the per-thread sorted list — `func_finduv` (`lj_func.c:37-69`) maintains sort order regardless of insertion order; carry the `immutable` flag.
5. **Sanity/refusal rules**: refuse (or defer to OC's persist-failure fallback) if `cframe != NULL`, if any non-bottom frame is FRAME_C/CP, if a cont value is outside the known set, or if a C closure in a func slot is not in perms. Precede everything with `lj_trace_flushall` and bytecode normalization (§5).

The three genuinely LuaJIT-specific "effort" items beyond a PUC/Eris port: (i) frame links are tagged machine words instead of a `CallInfo` array — but they decode losslessly into the three symbolic forms above; (ii) continuation ASM addresses — a 9-entry relocation table; (iii) JIT hygiene — flush + I-variant normalization + zeroing stitch slots. Everything else (TValue NaN-boxing, GC64 47-bit pointers) is invisible once values are written symbolically. Within one pinned build, nothing observed in the source is unserializable for the OC yield protocol.

# KEY CLAIMS
- [high] A coroutine suspended at a plain coroutine.yield has L->cframe == NULL and L->status == LUA_YIELD, with L->base/L->top framing the yielded values; the entire resumable state lives on the Lua stack (vm_x64.dasc:1703-1714, lj_api.c:1188-1203), and cframe==NULL is a checked precondition of both resume paths (lj_api.c:1231, vm_x64.dasc:1578).
- [high] A suspended stack can never contain an interior live-C frame: FRAME_C/FRAME_CP links are created only by vm_call/vm_pcall/vm_cpcall/vm_resume, all of which push a cframe, and both yield paths refuse unless the top cframe carries CFRAME_RESUME (vm_x64.dasc:1705, lj_api.c:1192,1225); the only C-typed link in a suspended stack is the bottom FRAME_CP delta from vm_resume, whose C frame is already unwound. Yields across pcall and metamethods use pure Lua-stack FRAME_PCALL/FRAME_CONT frames (vm_x64.dasc:1523-1556, 797-806; lj_meta.c:110-135).
- [high] Frame links decode into exactly three symbolic forms — (proto, bytecode offset) for FRAME_LUA, (type, byte-delta) for C/CP/VARG/PCALL/PCALLH, and delta+continuation-symbol+contpc for FRAME_CONT — and the continuation set is finite: 7 ASM entry points (lj_cont_cat/ra/nop/condt/condf/hook/stitch, lj_vm.h:108-114) plus integer specials 0/1 (lj_frame.h:87), verified exhaustive by all setcont call sites; under GC64 the cont slot holds a raw 64-bit ASM address at frame[-3] (lj_obj.h:896-898, lj_frame.h:91-97) needing a 9-entry relocation table.
- [high] lj_trace_flushall fully unpatches J-variant bytecode (JFORL/JITERL/JLOOP/JFUNCF, lj_trace.c:204-232,276-303) but does NOT undo PROTO_ILOOP blacklist patching (only lj_trace_reenableproto does, lj_trace.c:187-201); lj_bcwrite.c:300-315 is the canonical normalization recipe. Hot counters are a global 64-entry pc-hash array in GG_State (lj_dispatch.h:75-129) safe to cold-restart, and penalty slots are process-local and zeroed by flush. The single JIT value that can be frozen on a suspended stack — the GCtrace ref in a cont_stitch frame's aux slot — is designed to degrade to cont_nop when zeroed (vm_x64.dasc:2380-2408, lj_trace.c:288).
- [medium] Pall's 2008 assessment holds for current v2.1: a complete serializer for one suspended thread writes {status, base/top offsets, TValue slots [2,top), a frame-rewrite list in the three symbolic forms, open-upvalue (thread,slot) records}, and the kernel thread resumed via lua_resume from C has the identical shape; the schema is sufficient per the structures read, though end-to-end round-trip is unproven until prototyped.

EVIDENCE: Confirmed elements: (a) suspended threads hold no C-stack state — lua_yield sets L->cframe=NULL, status=LUA_YIELD (lj_api.c:1201-1202), ff_coroutine_yield likewise (vm_x64.dasc:1710-1713), both resumes require cframe==NULL (lj_api.c:1231, vm_x64.dasc:1578); (b) stack_init puts thread@slot0, nil@slot1, base=top=slot2, so [2,top) is right for the default GC64/FR2 build (lj_state.c:180-182, lj_arch.h:216-217/597-598); (c) frame links come in exactly three encodings — PC, cont+PC, delta+type (lj_frame.h:14-27), continuations are a closed set (lj_vm.h:108-114, lj_frame.h:87), and interior C-entry frames cannot exist in a yieldable stack (cframe_canyield, lj_api.c:1192, vm_x64.dasc:1705); (d) kernel-thread shape identity holds — ff_coroutine_resume calls ->vm_resume (vm_x64.dasc:1620), the same entry as lua_resume (lj_api.c:1232), both stamping a FRAME_CP bottom frame (vm_x64.dasc:581,635-640); (e) open-upvalue (thread,slot) records suffice since uv->dhash is address-derived and recomputed on re-open (lj_func.c:149,175); (f) Pall's 2008-09-01 lua-l post (http://lua-users.org/lists/lua-l/2008-09/msg00000.html) says exactly that 2.x keeps one C stack and a suspended coroutine "could be serialized with some effort". REFUTING the sufficiency clause: the enumerated schema is incomplete on OC's hot path. coroutine.yield has no JIT recorder (no entry in lj_recdef.h), so a compiled loop yielding goes recff_nyi -> recff_stitch (lj_ffrecord.c:162-189; exclusions at 173-177 omit yield), which plants a FRAME_CONT stitch frame whose below-cont slot holds an LJ_TTRACE-tagged GCtrace object (lj_ffrecord.c:130, lj_ir.c:288-292), read back by ->cont_stitch as [RB-40] (vm_x64.dasc:2380). The thread then suspends with a live, unserializable JIT trace reference on its Lua stack — covered by neither the three symbolic forms nor verbatim TValue copy. Additionally, hook-yield CONT frames embed a raw untagged u64 multres slot (lj_api.c:1207), not a valid TValue (Eris itself refuses yielded hooks: eris_53.c:186,1792). Pall's remark also predates trace stitching (2.1, 2015), so "holds for current v2.1" cannot cover this case.
CORRECTION: The go/no-go answer survives, but the schema as stated is insufficient. Corrected claim: a complete LuaJIT 2.1 suspended-thread serializer needs {status, base/top offsets, TValue slots [2,top), frame rewrites in the three symbolic forms, open-upvalue (thread,slot) records} PLUS (1) a fourth rewrite class for cont_stitch frames: the LJ_TTRACE-tagged GCtrace TValue in the below-cont slot must be replaced on restore with a zero-payload trace reference — not nil, since ->cont_stitch tests the cleartp'd payload for zero (vm_x64.dasc:2380-2404) and nil's NaN-boxed payload is non-zero — which safely degrades resumption to cont_nop/interpreter; and (2) an explicit policy for hook-yield frames' raw u64 multres slot (serialize as raw bits or refuse, matching Eris's "cannot persist yielded hooks"). This is unavoidable in OC practice because machine code yields inside JIT-hot loops, making stitched-yield frames the common case, not an edge case. With those two amendments, no structural blocker remains in the sources read; residual risk stays confined to untested integration. The kernel-thread shape-identity and Pall-2008 feasibility parts of the claim are confirmed as stated.
