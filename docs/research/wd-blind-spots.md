# Threat Model: Evading / Outlasting an Async-Injected Count Hook (CHECKHOOK build)

## 0. Core thesis (the one thing the design section must state)

An asynchronously injected count hook — `lua_sethook(L, hook, LUA_MASKCOUNT[, …], count=1)` from the Java watchdog, with LuaJIT built `-DLUAJIT_ENABLE_CHECKHOOK` — fires **only at points where the VM executes a bytecode (interpreter dispatch) or a trace IR head/back-edge (CHECKHOOK guard).** It therefore has exactly one structural blind spot: **any single call that stays inside C for a long time executes no bytecode and no trace IR, so the hook cannot fire until that call returns.** CHECKHOOK closes the *compiled-loop* hole (that was the whole reason to enable it) but does nothing for the *long C builtin / long GC* hole. Consequently the **soft abort (hook raises a catchable error) is a best-effort mechanism; the Java-side HARD abort (destroy the `lua_State`, or abandon the thread) is the only guaranteed bound** for the residual C-side hazards. Everything below is organized around that split.

Verified mechanism facts:
- Hook dispatch is driven by `g->hookmask` / `g->hookcount`, checked in `lj_dispatch_ins` (`lj_dispatch.c:437`: `if ((g->hookmask & LUA_MASKCOUNT) && g->hookcount == 0)`), and an armed COUNT/LINE hook forces slow interpreter dispatch `DISPMODE_INS` (`lj_dispatch.c:121`).
- CHECKHOOK emits, once per root trace at the trace head, a **volatile** load of `g->hookmask`, `BAND (LUA_MASKLINE|LUA_MASKCOUNT)`, guarded `== 0` (`lj_record.c:2967-2972`). A volatile load cannot be hoisted/CSE'd, so the LOOP pass re-emits it into the looped iteration; a compiled hot loop re-checks the mask each iteration and side-exits to the interpreter when it is nonzero. Mike Pall's own comment there ("check … from compiled code … expensive in tight loops … *asynchronously* interrupt the execution … set the instruction hook via `lua_sethook()` with a count of 1 from … another native thread") confirms this is precisely our use case.
- **Design constraint that falls out of the guard mask:** the injected mask MUST include `LUA_MASKCOUNT` or `LUA_MASKLINE`. A mask of only `LUA_MASKCALL|LUA_MASKRET` would set `DISPMODE_CALL/RET` in the interpreter but the trace-head guard ANDs against `(LUA_MASKLINE|LUA_MASKCOUNT)` only — so **CALL/RET-only masks do not exit compiled loops.** The planned `count=1` (COUNT) is correct.
- `lua_sethook` is explicitly documented "can be called asynchronously" (`lj_dispatch.c:336`) and internally does `lj_trace_abort(g)` + `lj_dispatch_update(g,0)` (`lj_dispatch.c:345-346`), aborting any in-progress *recording* and flipping every dispatch slot to the hook path.

## 1. Long-running VM builtins / C functions (the primary residual)

All of these run to completion in C between two bytecodes. **The soft hook cannot fire inside any of them, CHECKHOOK or not.** The question for each is only: *what bounds its runtime?*

### 1a. Native pattern matching — `string.find/match/gmatch/gsub` — the worst offender
- The matcher `match()` (`lib_string.c:352-435`) is recursive with a depth guard `if (++ms->depth > LJ_MAX_XLEVEL) lj_err_caller(...STRPATX)` where **`LJ_MAX_XLEVEL = 200`** (`lj_def.h:65`). That guard bounds *recursion depth* (prevents C-stack overflow from pattern nesting) but **does not bound total work**: `max_expand`/`min_expand` (`lib_string.c:286-313`) plus the outer scan loop (`str_find_aux` `do { … } while (sstr++ < ms.src_end && !anchor)`, `lib_string.c:498-511`) multiply. Chained quantifiers such as `("…"):match("%a-%a-%a-…-%a-z")` on a no-match string produce **super-polynomial (`O(nᵏ)`) backtracking**, uninterruptible, in native C. (Lua patterns can't quantify groups, so classic `(a+)+` ReDoS isn't expressible, but chained single-item `-`/`*`/`+` items reproduce the blow-up.)
- **Runtime bound:** none useful. Memory is bounded (fixed `capture[LUA_MAXCAPTURES]` array + ≤200-deep C recursion), so it is a pure-CPU DoS.
- **Mitigation (already present and it works *for us*):** machine.lua ships a **pure-Lua reimplementation of the whole matcher** and routes every string `>= SHORT_STRING (500)` chars through it (`machine.lua:97,503-504,558,641`; `string.find/match/gmatch/gsub` are replaced at `machine.lua:682-685`). The Lua matcher executes bytecode/traces, so the hook (interpreter dispatch or CHECKHOOK) **can** interrupt it — and under JIT it gets compiled, so the perf penalty OC accepted for it is largely repaid. The comment at `machine.lua:86-91` states it exists "so that timeouts also apply while matching stuff, which can take a looong time for certain 'evil' patterns." This is a genuine win under JIT.
- **Residual:** strings `< 500` chars still use the **native** matcher (`machine.lua:503-504`). Super-polynomial backtracking on a ≤499-char string is still achievable and still uninterruptible. Recommend either (a) lower `SHORT_STRING` / route *all* pattern ops through the Lua matcher, or (b) rely on the hard abort. The hard abort is the definitive backstop.

### 1b. `string.rep(s, n)` — memory-bounded
- `lib_string.c:87-104` → `lj_buf_putstr_rep` (`lj_buf.c:217-225`): total length pre-checked; `> LJ_MAX_BUF (≈2 GB)` → `lj_err_mem`; otherwise a **single** `lj_buf_more(sb, tlen)` allocation. Under a few-MB counting allocator this returns NULL → `lj_mem_realloc`→`lj_err_mem` (`lj_gc.c:869-881`) → **catchable `LUA_ERRMEM` *before* the fill loop.** Runtime ≤ O(mem cap). Not a serious CPU DoS.
- **Mitigation:** memory cap is the natural bound. Optional `n` cap in the sandbox wrapper is cosmetic.

### 1c. `string.format` — memory/bitfield-bounded
- `lib_string.c:657-668` loops `lj_strfmt_putarg`. Field width/precision are parsed into the packed `SFormat` bitfield (`lj_strfmt.c:57-71`) and padding is written via `lj_buf_more(sb, need)` (`lj_strfmt.c:324-341`). Huge width → large allocation → OOM (bounded); width is additionally capped by its bitfield size. Bounded, uninterruptible, low risk.

### 1d. `table.concat` — memory-bounded
- `lib_table.c:152-170` → `lj_buf_puttab` C loop; output size bounded by table length × element size → OOM under cap. Uninterruptible mid-loop but bounded. `lj_gc_check` after.

### 1e. `table.sort` — well-behaved for the watchdog
- **With a comparator:** each comparison is `lua_call(L,2,1)` into Lua (`lib_table.c:180-194`), i.e. **a bytecode/trace boundary → the hook fires inside the comparator → interruptible.** An inconsistent/malicious comparator can force `O(n²)` comparisons, but the `LJ_ERR_TABSORT` guards (`lib_table.c:231,236`) prevent OOB, and every comparison is an abort opportunity.
- **Without a comparator:** pure C `O(n log n)` on numbers/strings; `n` bounded by table size (memory cap → ~10⁵ elements at a few MB) → sub-second. Uninterruptible but bounded.
- **C-stack:** `auxsort` recurses on the *smaller* partition and tail-loops the larger (`lib_table.c:250-255`) → depth ≤ log₂n ≤ ~17. No C-stack risk.

### 1f. Huge table allocation — memory-bounded
- `table.new(a,h)` / `lua_createtable` presize via `lj_tab_resize`: one large allocation → OOM under cap (`lj_gc.c:869-897`). Uninterruptible but bounded; catchable error.

## 2. GC pauses

**Single GC steps are bounded; the one indivisible C region (atomic) is bounded by the memory cap; the allocator-failure path is safe, including on-trace.**

- **Incremental steps:** `lj_gc_step` caps work per invocation (`lim = (GCSTEPSIZE/100)*stepmul`, `lj_gc.c:734`); `gc_onestep` does one unit at a time — propagate one gray object, sweep `GCSWEEPMAX=40` objects, one string chain, one finalizer (`lj_gc.c:661-725`).
- **Atomic phase** (`atomic()`, `lj_gc.c:620-658`, invoked from `GCSatomic`, returns 0 after the whole thing) is **not** incremental: it drains remaining gray + grayagain + weak lists in one C call. Cost ∝ live set, which is **bounded by the per-computer memory cap (a few MB)** → low-millisecond pause. Uninterruptible (no bytecode) but bounded. Not unbounded even in the worst case under the cap.
- **On-trace GC is deferred, never a big pause on a trace:** `lj_gc_step_jit` returns 1 to **force a trace exit** when it reaches atomic/finalize (`lj_gc.c:768-777`), and both `GCSatomic` and `GCSfinalize` early-out with `LJ_MAX_MEM` while `g->jit_base` is set (`lj_gc.c:674-675, 709-710`). So the heavy phases only run in the interpreter, where they are anyway bounded by the cap.
- **Allocator NULL is safe everywhere:** `lj_mem_realloc`/`lj_mem_newgco` → `lj_err_mem(L)` (`lj_gc.c:874, 888`). `lj_err_mem` (`lj_err.c:813-833`) is jit-aware: it restores `L->base` from `jit_base` (819-822), fixes `L->top`, pushes the preallocated "not enough memory" string, and throws a **catchable `LUA_ERRMEM`**. On x64/GC64 an OOM raised *inside a trace* is caught by the JIT unwinder (`LJ_UNWIND_JIT`: `err_unwind_win_jit` on Windows, `err_unwind_jit` on SysV, `lj_err.c:346-373, 517-548`) which jumps to the trace's side-exit stub and rethrows via `lj_err_trace`→`lj_err_run` (`lj_err.c:919-928`). `lj_err_throw` also does `lj_trace_abort(g)` first (`lj_err.c:771`). **Confirmed graceful on Windows x64 (the JVM target).** (Note: `lj_err.c:384-387` shows on-trace errors are *not* catchable on **Win/x86 SEH** — irrelevant for GC64, which implies x64.)

## 3. Coroutine tricks

**The hook is VM-global, so nesting cannot evade it; the sandbox exposes no way to clear it; pcall/xpcall swallowing is closed by the count=1 re-arm escalation.**

- **Globality (decisive):** `hookmask`, `hookcount`, `hookcstart`, `hookf` all live in **`global_State`** (`lj_obj.h:641, 653-655`), not per-thread `lua_State`. Moreover LuaJIT's `debug.sethook` **discards the thread argument** — `(void)getthread(L,&arg)` then `lua_sethook(L,…)` on the current L (`lib_debug.c:323-342`) — and `lua_sethook` writes `G(L)->hook*` (`lj_dispatch.c:337-347`). Therefore an injected hook fires on the next counted bytecode of **whatever coroutine is running**, regardless of nesting depth or which thread was "targeted." Nested `coroutine.wrap`/`resume` cannot dodge it. (This is a divergence from PUC-Rio, where hooks are per-thread; here it works in our favor.)
- **No clear path from the sandbox:** the sandbox `debug` table exposes only `getinfo, traceback, getlocal, getupvalue` — **no `sethook`** (`machine.lua:1001-1030`), and `lua_sethook` is not otherwise reachable. Sandbox code cannot disarm the injected hook. `coroutine.wrap`'s error path just re-raises (`machine.lua:867-877`); it cannot suppress a re-arming hook.
- **pcall/xpcall swallowing is closed:** machine.lua's `checkDeadline` **re-arms with `count=1` before raising** (`machine.lua:45-53`): `debug.sethook(coroutine.running(), checkDeadline, "", 1)` then `error(tooLongWithoutYielding)`. After a `pcall` catches the error, the *very next* interpreted instruction hits the hook again (deadline still past → re-raise). This works because the error-unwind path **clears `HOOK_ACTIVE`** when unwinding through a pcall/CP frame (`hook_leave(g)` at `lj_err.c:155, 185`), so the hook is re-armable immediately — an infinite `while true do pcall(f) end` gets re-raised every instruction. The sandbox `pcall`/`xpcall` wrappers additionally call `checkDeadline` *before* each (`machine.lua:763-769, 813-838`), preventing a tight pcall loop from starving the check. **Note for us:** `count=1` forces `DISPMODE_INS` (interpreter) and CHECKHOOK exits any live trace, so the abort phase runs interpreted — correct and intended.
- **Caveat to preserve:** `lj_err.c:155` carries the comment *"Assumes nobody uses coroutines inside hooks."* Keep the injected hook function trivial (set a flag / raise) and **never resume a coroutine inside it**, or the `HOOK_ACTIVE` accounting can desync.
- **`__gc` finalizers — a real evasion window (part 3 + part 2 overlap):** C-level finalizer dispatch calls **`hook_entergc(g)` which sets `HOOK_ACTIVE|HOOK_GC`** and sets `threshold=LJ_MAX_MEM` (`lj_gc.c:504-535`, esp. 514, 516); `callhook` only fires when `!hook_active(g)` (`lj_dispatch.c:370`). **So while a user `__gc` runs, all hooks — including an async-injected one — are suppressed until the finalizer returns.** A malicious `__gc` that loops forever therefore evades the soft abort entirely. This is exactly what machine.lua discovered and documents: *"Garbage collector callbacks apparently can't be sandboxed after all, because hooks are disabled while they're running. So we just disable them altogether by default"* (`machine.lua:780-806`; user `__gc` is only wrapped/allowed when `system.allowGC()`, and even then the coroutine-wrapped deadline is unreliable for the same reason). Worse, `__gc` may run **on the server main thread** during world save (`machine.lua:785-788`), where **no per-computer watchdog thread applies** → neither soft nor hard abort can act → server hang. **Mitigation: keep user `__gc` disabled by default (allowGC=false); the executor-thread hard abort is the only backstop when enabled, and it does not cover main-thread finalization.**

## 4. Memory-limit interplay (counting allocator + GC64)

- **allocf → NULL is handled gracefully everywhere** — see §2. `lj_mem_realloc`/`lj_mem_newgco`→`lj_err_mem`→catchable `LUA_ERRMEM`; on-trace OOM → trace side-exit via `LJ_UNWIND_JIT` → rethrow (x64). String-length and buffer overflows raise catchable `LJ_ERR_STROV`/OOM (`lj_str.c:317, 351-353`; `lj_buf.c:54-55, 65-66, 84`).
- **`maxmcode` exhaustion is graceful → interpreter fallback:** `lj_mcode_reserve` raises `LJ_TRERR_MCODEOV` (single trace too big) or `LJ_TRERR_MCODEAL` (`szallmcarea + sizemcode > maxmcode`) (`lj_mcode.c:446-455`); executable-memory alloc failure also raises `LJ_TRERR_MCODEAL` (`lj_mcode.c:333, 349`). These are **trace errors**, not fatal: `trace_abort` penalizes and **blacklists** the starting bytecode (`lj_trace.c:585-615`), so the loop runs in the **interpreter** thereafter — which is fully hookable. No crash, no unbounded behavior, and interruptibility is *restored* (interpreter path). (`LJ_TRERR_MCODELM` is the benign "retry with a fresh mcode area" case, `lj_trace.c:599-603`.)
- **GC64 specifics:** `LJ_MAX_MEM = LJ_MAX_MEM64`, `LJ_MAX_STR = LJ_MAX_MEM32 ≈ 2 GB` (`lj_def.h:49-55`). The per-computer cap (a few MB) is hit long before these, so every "huge allocation" attack terminates as a catchable OOM.
- **Residual (design-level, not a Lua evasion): cross-thread injection race.** `lua_sethook` was designed for **same-thread async** (signal handler — the VM is paused during signal delivery). Our watchdog calls it from a **separate OS thread while the VM thread is executing**, so there is a genuine data race on `g->hookmask`/`hookcount`/`hookf` **and** on the dispatch table that `lj_dispatch_update` rewrites (a loop of `GG_LEN_SDISP` pointer stores, `lj_dispatch.c:151-207`). On x64 the individual aligned pointer/byte stores are atomic, but the multi-slot dispatch rewrite is not a single atomic region, and there is no memory barrier contract with the VM reader. CCLuaJIT used this pattern **with the JIT off**, so it never exercised the dispatch-table rewrite under a running compiler. **Mitigation options:** (a) write `hookf` first and the mask byte last, relying on the VM only acting once it observes the mask bit and re-reading `hookf`; (b) briefly suspend the VM thread (e.g. `SuspendThread`/`GetThreadContext` on Windows) around the `lua_sethook` call; (c) insert a full barrier. This must be settled explicitly — it is the one place where "async like OC's signal handler" is *not* equivalent to "async from another thread."

## 5. Stack overflow / deep recursion

- **Lua-level recursion is bounded and catchable:** `lj_state_growstack` grows to `LUAI_MAXSTACK = 65500` slots (`luaconf.h:91`, `lj_state.c:110-153`); beyond that → `lj_err_stkov`→"stack overflow", a **catchable** error (`lj_err.c:911-917`). Pattern recursion depth is separately capped at `LJ_MAX_XLEVEL=200` (`lib_string.c:354`). `LUAI_MAXCSTACK=8000` (`luaconf.h:92`) bounds slots a C function may claim (e.g. `string.byte` huge range → `LJ_ERR_STRSLC` before allocating, `lib_string.c:56-58`).
- **Native C-stack overflow is a genuine residual (JVM crash risk).** LuaJIT has **no PUC-style `LUAI_MAXCCALLS` counter**; it relies on the Lua stack limit. Pure Lua→Lua recursion consumes Lua stack (not C stack), so it hits the catchable 65500 limit. But **C→Lua→C→Lua re-entrancy** — recursive `string.gsub`/`gmatch` with a function replacement that recurses (`add_value`→`lua_call`, `lib_string.c:592-598`), a `table.sort` comparator that recurses, recursive metamethods routed through C, etc. — pushes a **native** C frame (`string_gsub`'s MatchState+luaL_Buffer ≈ ~1 KB) per level. A JNI/executor thread with a default ~512 KB–1 MB native stack overflows after only a few thousand such levels, **before** the 65500-slot Lua limit is reached → **SIGSEGV / access violation → whole JVM (server) crash**, which the watchdog cannot convert to a catchable error. **Mitigation:** give the computer's executor thread a generously sized native stack (size it so the Lua-frame limit is hit first for realistic per-level slot usage), and treat pathological deep C-callback recursion as a crash-hardening item, not something the hook can catch. (OC already runs each computer on its own executor thread; the fix is the stack-size argument on that thread plus awareness that LuaJIT lacks a C-recursion guard.)

## 6. Final table (design-doc security section)

| 12 | Deep C↔Lua re-entrant recursion (recursive gsub-callback / sort comparator / metamethods) | Lua-only recursion → catchable stack overflow at 65500 (`lj_state.c:110-153`); **C-boundary recursion → native stack overflow (no `LUAI_MAXCCALLS`) → SIGSEGV / JVM crash** | Whole-JVM crash before any catchable error | Large native stack on executor thread; harden/accept; hook can't catch | **Medium-High** |
| 13 | Cross-thread `lua_sethook` injection race | Works in practice (single-slot mask byte) but multi-slot dispatch-table rewrite under a running JIT is a data race not exercised by CCLuaJIT (JIT was off) | Torn dispatch table / missed hook / rare corruption | Ordered writes (hookf first, mask last) + barrier, or briefly suspend VM thread during injection | Medium |

## 7. Design recommendations distilled

1. **Two-stage abort is mandatory, and the hard stage is not optional garnish** — it is the sole bound for hazards #2 (short-string native patterns), #11 (`__gc`), and #12 (native stack). Budget for "resume returned but state is wedged → destroy `lua_State` from Java."
2. **Inject with `LUA_MASKCOUNT` count=1** (optionally `|LINE`). Never a CALL/RET-only mask — it won't exit compiled loops (#1).
3. **Keep the pure-Lua matcher, and consider routing *all* pattern ops through it** (not just ≥500 chars) since JIT compiles it; this converts hazard #2 from High to Low.
4. **Keep user `__gc` disabled by default** (`system.allowGC()=false`), per machine.lua's own hard-won conclusion; document that finalizers on the main thread are outside any watchdog.
5. **Settle the cross-thread injection ordering/barrier explicitly** (#13) — this is the one behavior CCLuaJIT never validated because it ran with the JIT off.
6. **Size the executor thread's native stack generously and note LuaJIT has no C-recursion counter** (#12).
7. Remove machine.lua's *standing* periodic `debug.sethook(co,…,hookInterval)` (per the chosen no-standing-hook direction); the global single hook slot is then free for the watchdog, avoiding contention between kernel hook management and injection.

# KEY CLAIMS
- [high] Hook state (hookmask/hookcount/hookf) is VM-global in global_State, and LuaJIT's debug.sethook discards its thread argument, so an async-injected count hook fires in whatever coroutine is currently running — nested coroutines cannot evade it, and the sandbox exposes no sethook to disarm it.
- [high] The soft (hook-based) abort cannot interrupt any long-running C builtin or the GC atomic phase because no bytecode/IR executes there; the native pattern matcher's only guard is LJ_MAX_XLEVEL=200 depth (not total work), so catastrophic backtracking on <500-char strings is uninterruptible super-polynomial CPU that only the Java hard-abort bounds.
- [high] CHECKHOOK inserts a volatile load of g->hookmask masked by (LUA_MASKLINE|LUA_MASKCOUNT) guarded ==0 at the trace head (re-checked on loop iterations because volatile loads can't be hoisted), so compiled loops exit to the interpreter only if the injected mask includes COUNT or LINE — a CALL/RET-only mask would NOT interrupt compiled loops.
- [high] Memory-cap allocator NULL is handled gracefully everywhere, including inside compiled traces on x64/GC64 (lj_err_mem -> LJ_UNWIND_JIT trace side-exit -> catchable LUA_ERRMEM); GC atomic/finalize are deferred off-trace; and maxmcode/mcode exhaustion aborts the trace and blacklists the bytecode -> interpreter fallback, which is fully hookable.
- [high] User __gc finalizers run with hooks disabled (hook_entergc sets HOOK_ACTIVE) and can run on the server main thread during world save, so the soft abort cannot fire and the executor-thread hard abort does not apply there — which is exactly why machine.lua disables user __gc by default; keep it disabled.
