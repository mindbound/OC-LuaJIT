# Precedent study: OpenPython and OC-Wasm as third-party OpenComputers architectures

## A. OpenPython (https://github.com/OpenPythons/OpenPython)

### What it is
"OpenPython makes micropython available on OpenComputers" (README.md). Kotlin mod (uses Forgelin), MIT-licensed, **MC 1.12.2 / Forge 14.23.4.2727 / OpenComputers 1.7** per `gradle.properties` (`minecraft_version=1.12.2`, `opencomputers_version=1.7`, `mod_version=1.1.0`). NOT a 1.7.10 mod — it would need porting for GTNH. The whole org (OpenPythons) is archived; last substantive activity ~2019, repo archived May 2026, 44 stars.

### Architecture registration
- Main mod class `src/main/java/kr/pe/ecmaxp/openpython/OpenPython.kt`: `@Mod(modid = "openpython", ..., dependencies = "required-after:forgelin;required-after:opencomputers;")`; in `preInit` it calls:
  ```kotlin
  Machine.add(OpenPythonArchitectureV1_0::class.java)
  Machine.add(OpenPythonArchitectureV1_1::class.java)
  ```
  It also registers EEPROM and floppy items via OC's `Items.registerEEPROM()` / `Items.registerFloppy()` API.
- `arch/versions/v1/OpenPythonArchitectureV1.kt` declares e.g. `@Architecture.Name("OpenPython v1.0") class OpenPythonArchitectureV1_0(machine: Machine) : OpenPythonArchitecture(...)`, and the shared base `arch/OpenPythonArchitecture.kt` implements `li.cil.oc.api.machine.Architecture` (imports `li.cil.oc.api.machine.{Architecture, ExecutionResult, Machine}`; `recomputeMemory` iterates component ItemStacks against `li.cil.oc.api.driver.item.Memory` drivers). The README confirms the CPU is obtained by "Shift+Right Click on Lua CPUs" — i.e., the standard OC architecture-cycling UI that any `Machine.add`-registered architecture gets for free.

### How the MicroPython VM is embedded — neither pure-Java port nor JNI
This is the surprising part: OpenPython runs **real MicroPython C code, cross-compiled to bare-metal ARM Cortex-M0 firmware, executed by a software ARM Thumb instruction-set emulator written in Kotlin**:
- Firmware: `src/main/resources/assets/openpython/firmwares/v1.0.1/firmware.bin` (~256 KB firmware per README), built from the org's `OpenPythonFirmware` (C) and `micropython-opencom-legacy` (MicroPython fork) repos; linked against musl (LICENSE files for micropython/musl/msgpack-java in repo).
- Emulator: `src/main/java/kr/pe/ecmaxp/thumbsf/CPU.kt` (~42 KB) — org description: "Thumb Simulator (Kotlin) for Cortex-M0" (sibling ports ThumbSJ/ThumbSC in Java/C#). Public API `fun run(insnCount: Int, handler: (imm: Int) -> Unit)`: interprets up to `insnCount` Thumb instructions via a large `when` dispatch with a decoded-instruction cache (`memory.loadExecCache(pc)`), stopping on budget exhaustion or on `ControlPauseSignal`/`ControlStopSignal` exceptions; `SVC` instructions call back into the host `handler`.
- Host services: `arch/versions/v1/OpenPythonInterruptHandlerV1.kt` dispatches SVC syscall groups (SYS_CONTROL, SYS_SIGNAL, SYS_COMPONENT, SYS_VALUE, SYS_COMPUTER, SYS_VFS, SYS_TIMER...). Component calls parse `ComponentInvoke.fromArray(...)`; when running on the OC thread pool and the callback is not direct it throws `ControlPauseSignal(ExecutionResult.SynchronizedCall())` so OC re-enters via `runSynchronized` on the server thread; `LimitReachedException` (direct-call budget) likewise pauses gracefully. Signals come from `machine.popSignal()`; empty queue → `ControlPauseSignal(ExecutionResult.Sleep(...))`.
- `OpenPythonArchitecture.runThreaded()` returns the unsynchronized step result, or the cached result of the last `runSynchronized()`; `OpenPythonVirtualMachineV1.step` runs `cpu.run(if (synchronized) 1 else 10000000)` — 10M emulated instructions per threaded timeslice.

### Persistence — a genuine mid-execution memory-image snapshot
`arch/versions/v1/OpenPythonVirtualMachineV1.kt` save/load:
- **Save**: firmware name/protocol; **CPU registers** (`cpu.regs`); each `Memory` region written with `address`, `size`, `flag` and a **GZIP-compressed buffer** of its contents; plus `state.save(...)` for VM host-side state (`OpenPythonVirtualMachineStateV1`, `state/FileHandle.kt`, `state/ValueContainer(Map).kt` for fd/value handles).
- **Load**: validates firmware name matches, restores register array, decompresses buffers back into each region, reloads state. `OpenPythonArchitecture.load(nbt)` only applies when `machine.isRunning`.
- Because the *emulated CPU's* program counter and registers are part of the snapshot, the machine resumes **exactly where it paused — mid-Python-program, even mid-C-function inside MicroPython**. This is why the README can claim "Fully persistable": persistence is trivial once your whole VM is a flat memory image + 16 registers. This is the exact property a LuaJIT-in-a-real-process lacks.
- Extra plumbing: `arch/OpenComputersLikeSaveHandler.kt` re-implements OC's external-file save scheme because big blobs don't belong in chunk NBT: it hooks `onChunkSave` Forge events and writes compressed blobs under OC's `savePath()` (obtained by reflection on `li.cil.oc.Settings`) in dimension/chunk folders — mirroring OC's internal `SaveHandler`, which is not exposed through the addon API. This is a documented-in-code pitfall for any architecture addon with large state.

### Maturity / pitfalls documented
README: "It is still unstable"; OS partially implemented; "Ctrl + C is not supported, so if you accidentally run infinite repeated code, the only way to stop it is to turn the computer off" (an infinite loop can't be interrupted from inside, though the server stays healthy since each timeslice is capped at 10M emulated instructions). Performance was never a selling point — an interpreted Cortex-M0 running interpreted MicroPython is orders of magnitude below JNLua native Lua, let alone LuaJIT.

## B. OC-Wasm-GTNH (https://github.com/DCNick3/OC-Wasm-GTNH, fork of https://gitlab.com/Hawk777/oc-wasm)

### What it is / GTNH integration
Port of Hawk777's OC-Wasm (MC 1.12.2) to GTNH's 1.7.10 stack. `gradle.properties`: `minecraftVersion=1.7.10`, `forgeVersion=10.13.4.1614`, `opencomputersVersion=MC1.7.10-1.7.+`, GTNH blowdryer buildscript, `modId=ocwasm`; `dependencies.gradle` pulls `li.cil.oc:OpenComputers:<ver>:api`, GTNH Forgelin 1.9.9, ASM 9.1 (shadowed), and `co.nstant.in:cbor` 0.9. LGPL-3.0, last push March 2024, 6 stars; default branch `gtnh`. Java core (`ca.chead.ocwasm`) + a **vendored, patched copy of the Asmble WASM compiler in Kotlin** (`src/main/kotlin/asmble/...`).
- Registration: `OCWasm.java` (`@Mod(modid = "ca.chead.oc-wasm", ...)`) calls exactly `li.cil.oc.api.Machine.add(CPU.class);` in `postInit`. `src/main/java/ca/chead/ocwasm/CPU.java` is `@Architecture.Name("WebAssembly") public final class CPU implements Architecture`. README: "hold it in your hand and Shift-Right-Click to switch architectures—just like you would to switch between Lua 5.2 and 5.3—and you should see WebAssembly in the list" — again, plain `Machine.add` + `@Architecture.Name` gives the CPU-switching UI for free.

### WASM runtime: AOT compilation to JVM bytecode (not Chicory, not an interpreter)
`Compiler.java`: `BinaryToAst.toModule(binary)` → Asmble `AstToAsm.fromModule(...)` → JVM bytecode → `Postprocessor.postprocess()` → custom ClassLoader; compiled classes cached "keyed by the binary image" (`Cache.java`, `HashableByteArray`). So guest code runs as real JITtable JVM bytecode — near-native speed once HotSpot warms it.

`Postprocessor.java` is the most instructive file for anyone building an architecture on a compiled runtime; it rewrites Asmble's output to:
- **inject timeout checks** "at the top of each function or loop": polls a `this.timedOut` boolean (on `ModuleBase`) at function entries and loop back-edges and throws `TimeoutException`;
- add **stack-depth/RAM accounting**: on method entry subtracts `maxLocals + maxStack + 1` from a `freeMemory` field, throws `StackOverflowException` when negative, refunds on return;
- reparent the module class onto `ModuleBase`, add a constructor taking a snapshot `ByteBuffer`, generate `saveMutableGlobals(ByteBuffer)`, and **bypass the WASM start function when restoring from snapshot**;
- enforce exactly one linear memory and function-only imports (syscalls are WASM function imports, per javadoc overview).

Timeouts: `OCWasm.getTimeout()` reads OC's own `computer.timeout` setting; `state/Run.java` schedules a background task that sets `instance.timedOut = true` when the budget expires (with careful interrupt/monitor handshaking). A `TimeoutException` escapes `run()` and `ExceptionTranslator.translate` turns unhandled guest exceptions into a **terminal `ExecutionResult.Error`** — javadoc overview: "The `run` function is not allowed to run indefinitely!" and if it exceeds the timeout "it will crash", explicitly mimicking Lua's "too long without yielding".

### Execution model and the 'cannot pause inside a call' problem
OC-Wasm **does not solve** mid-call pausing — it defines it away with a cooperative contract:
- The module must export `run`. `ModuleBase.run(int)` javadoc: param is "1 if a method call was previously started but not finished and has now finished, or 0 if not"; return is "The number of ticks to sleep before the next call". `state/Run.java` invokes `requestedSleep = instance.run(syscalls.component.hasCallResult() ? 1 : 0)` once per timeslice and maps the return into `ExecutionResult.Sleep(...)` (squashed to 0 if a signal was already popped but not yet delivered — a subtle signal-queue pitfall handled explicitly in code). Component calls that need the server thread set a flag; `Run` returns `ExecutionResult.SynchronizedCall` and OC re-enters `runSynchronized()` where `syscalls.component.runSynchronized()` performs the call; the *result* is delivered at the next `run` invocation. Method calls are thus queued/split-phase from the guest's view.
- Javadoc overview: "an OC-Wasm program needs to do a little bit of work on each call to `run`, then save its progress (in a combination of mutable global variables and linear memory) and return, resuming execution later."

### Persistence: memory + globals snapshot, NO call stack — fresh entry into run()
- `Snapshot.java`: holds `binary` (the WASM binary), `globals` ("values of the module's mutable globals"), `memory` ("contents of the module's linear memory"), `executeBuffer` (pending exec-replacement binary), and a `generation` counter. **No program counter or call-stack field exists.** Large blobs go to a ZIP (stored, CRC32) at `[save-root]/oc-wasm/[computer-uuid]` with entries `binary.wasm`, `globals.bin`, `memory.bin`, ...; small state to NBT — same "keep big data out of chunk NBT" lesson as OpenPython.
- `CPU.save()` cancels any pending writeout, snapshots the current state and submits an **asynchronous background write**; snapshotting happens between timeslices (OC pauses the machine around save; `Run.snapshot()` has no internal locking and assumes quiescence).
- Restore path (`state/` package: `FindEEPROM → Compile → InstantiateClean/InstantiateFromSnapshot → Run`, `State`/`Transition` state machine): `LoadFromSnapshot.java` reads NBT + `Snapshot.load(machine.node().address())`, checks generation match, then **recompiles the binary** (compile cache permitting) and `InstantiateFromSnapshot.java` instantiates the class with `Optional.of(ByteBuffer.wrap(snapshot.globals.get()))` (constructor restores globals and skips the start function) and overwrites linear memory (`memory.limit(len); memory.put(memoryData)`). Then it transitions to `Run` and simply **calls `run` again from the top**. So OC-Wasm persists *data* state exactly but *execution* state only at run()-boundary granularity; a program that wants to survive save/load transparently must be written as an explicit state machine over its own memory/globals.
- Opaque OC values DO survive: `DescriptorTable.java` — "in OC-Wasm, Values are represented as small nonnegative integers called descriptors"; save writes descriptor→pool-index arrays, and `ValuePool.java` persists each `li.cil.oc.api.machine.Value` by storing its class name plus `value.save(nbt)`, restoring via `Class.forName(...).newInstance()` + `value.load(nbt)` (hard failure if the class is missing). This is the same mechanism OC's own Lua machine uses for values, reimplemented addon-side.

### Maturity
Upstream oc-wasm is a polished, heavily documented codebase (full javadoc at https://hawk777.gitlab.io/oc-wasm/, overview.html shipped in-tree); ecosystem has Rust crates (OC-Wasm-safe etc.) and early Zig support, but "OC-Wasm-OpenComputers is incomplete, and there are no crates for high-level wrappers around other mods" (README). The GTNH fork is a build-system/API-level port, functional as of Mar 2024.

## Cross-cutting lessons for a LuaJIT architecture
1. **Registration is trivial and version-agnostic**: both projects need only `implements Architecture` + `@Architecture.Name` + `li.cil.oc.api.Machine.add(...)`, and the shift-right-click CPU switcher picks it up automatically — confirmed working on GTNH's 1.7.10 OC fork by OC-Wasm-GTNH.
2. **Persistence strategies bracket the design space**: OpenPython gets exact mid-instruction persistence by emulating a whole CPU (paying a catastrophic performance tax); OC-Wasm gets near-JVM performance by AOT-compiling to bytecode but abandons execution-state persistence, keeping only memory+globals and restarting `run()` — pushing the persistence burden onto guest program structure. Neither achieves Eris-style "serialize a suspended coroutine" persistence, which remains unique to OC's patched Lua VMs. A JNI-embedded LuaJIT would sit in OC-Wasm's corner: process-native state that cannot be snapshotted portably; realistic options are OC-Wasm-style memory/agreed-checkpoint persistence or reboot-on-load.
3. **Timeout enforcement must be built in**: OC only gives you `runThreaded` on a worker thread; OpenPython bounds each slice by emulated instruction count (10M), OC-Wasm injects `timedOut`-flag polls at loop back-edges/function entries and crashes the computer on `TimeoutException` (matching OC's Lua debug-hook behavior). LuaJIT equivalent: `lua_sethook`-style count hooks (JIT-hostile) or instrumented bytecode.
4. **Synchronized vs direct component calls** must round-trip through `ExecutionResult.SynchronizedCall` → `runSynchronized()`; both projects implement this split-phase dance (OpenPython via `ControlPauseSignal`, OC-Wasm via a flag + queued call result), and both persist open `Value` handles via `value.save/load` NBT.
5. **Keep large state out of chunk NBT**: OpenPython reflected into `li.cil.oc.Settings.savePath()` and re-built OC's external SaveHandler on chunk-save events; OC-Wasm writes its own ZIPs under the save root with async writeout — the addon API gives no helper for this.
6. **Signal-queue subtleties are real**: OC-Wasm explicitly handles the popped-but-undelivered-signal case by zeroing requested sleep; `onSignal()` is an empty stub in both projects (signals consumed at timeslice start via `machine.popSignal()`).

# KEY CLAIMS
- [high] OpenPython registers its architectures with plain OpenComputers API calls: @Architecture.Name-annotated Kotlin classes implementing li.cil.oc.api.machine.Architecture, added via Machine.add(OpenPythonArchitectureV1_0::class.java) in the mod's preInit (OpenPython.kt); it targets MC 1.12.2 / OC 1.7, not 1.7.10.
- [high] OpenPython embeds MicroPython by cross-compiling real MicroPython C code to bare-metal ARM Cortex-M0 firmware (firmware.bin in resources) and interpreting it with a Kotlin ARM Thumb emulator (kr.pe.ecmaxp.thumbsf.CPU, run(insnCount, svcHandler)), with host services via SVC interrupts — no JNI and no Java port of MicroPython.
- [high] OpenPython achieves true mid-execution persistence by snapshotting the emulated machine: save() writes CPU registers plus GZIP-compressed images of every memory region to NBT (with large blobs routed through an OC-style external chunk-save handler), and load() restores them so execution resumes at the exact saved program counter.
- [high] OC-Wasm executes WASM by AOT-compiling it to JVM bytecode with a vendored Asmble compiler, then postprocessing the bytecode to inject timeout checks (polling a timedOut flag at function entries and loop back-edges, throwing TimeoutException that crashes the computer, budget taken from OC's computer.timeout setting) and stack/RAM accounting; it is registered via li.cil.oc.api.Machine.add(CPU.class) with @Architecture.Name("WebAssembly"), and the GTNH fork builds against MC 1.7.10 / OpenComputers MC1.7.10-1.7.+.
- [high] OC-Wasm's persistence saves only the WASM binary, linear memory contents, mutable globals, execute buffer, and descriptor/value pool (opaque OC Values via class-name + value.save/load NBT); no call stack or instruction pointer is saved — on world load it recompiles, re-instantiates with globals/memory restored (skipping the start function), and calls the exported run() again from the top, so programs must be written as state machines that yield by returning from run each timeslice.
