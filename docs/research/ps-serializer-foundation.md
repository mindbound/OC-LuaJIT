# Build-on-what: lj_serialize.c, lj_bcwrite/bcread, extension paths, prior art, upstream

## 1. What lj_serialize.c actually is (read in full)

**Wire format.** Single-byte-ish tag space defined at `lj_serialize.c:27-56`: `SER_TAG_NIL/FALSE/TRUE/NULL` (0x00-0x03), `LIGHTUD32/64`, `INT`, `NUM`, `SER_TAG_TAB` = 0x08 occupying 6 tag values (0x08-0x0d, encoding presence of array/hash parts and 0-vs-1-based array, see below), `SER_TAG_DICT_MT` = 0x0e, `SER_TAG_DICT_STR` = 0x0f, `INT64/UINT64/COMPLEX` (0x10-0x12), **tags 0x13-0x1f explicitly reserved/unused** (`SER_TAG_0x13`…`SER_TAG_0x1f`, lines 42-54), and `SER_TAG_STR = 0x20 + str->len` (line 55) — strings carry their length in the tag itself. Variable-length ints use a custom "U124" varint (1/2/5 bytes: `serialize_wu124` lines 71-94, `serialize_ru124` lines 96-124). Numbers are raw little-endian-normalized 4/8-byte payloads (lines 177-184).

**Object walk** (`serialize_put`, lines 169-335) is a **plain recursive tree walk with no visited-set of any kind**. There is no object→id map anywhere in the file or in `SBufExt` (`lj_buf.h:23-33` — the struct carries only `dict_str`, `dict_mt` GCRefs and an `int depth`). Consequences, verified in source:

- **Shared references are silently duplicated** — each encounter of the same table re-serializes it in full; nothing records identity.
- **Cycles are caught only by the depth counter**: `sbx->depth` is initialized to `LJ_SERIALIZE_DEPTH` = 100 (`lj_serialize.h:14`, `lj_serialize.c:472,480,491,504`), decremented per table at `lj_serialize.c:191-192` and checked `if (sbx->depth <= 0) lj_err_caller(..., LJ_ERR_BUFFER_DEPTH)` — a cycle is indistinguishable from a 100-deep tree and dies with `"too deep to serialize"` (`lj_errmsg.h:195`). The docs confirm intent: "The encoder serializes nested structures as trees. Multiple references to a single object will be stored separately and create distinct objects after decoding. Circular references cause an error." (`doc/ext_buffer.html:403-405`).

**Table handling** (lines 188-276): computes effective array length by scanning down from `asize` for the last non-nil (193-199), detects 1-based-with-nil-at-0 via the `one = 2/4` trick folded into the tag (line 200, 226 — tag encodes `nhash?1:0` + `narray? one:0`), counts live hash slots (202-207), optionally writes a metatable *dictionary index* (never the metatable itself — only tables pre-registered in `dict_mt` get an index, lines 209-223; **an unregistered metatable is silently dropped**), then array slots in order and hash slots in reverse node order, with string keys optionally compressed through `dict_str` (237-260). Decoder (`serialize_get`, 338-465) rebuilds via `lj_tab_new` + `lj_tab_set`, errors on `DUPKEY` (409-410), validates dict indices (`BADDICTX`, 370, 385).

**Error dispatch.** One catch-all: anything not str/int/num/pri/tab/(cdata int64/uint64/complex)/lightud falls through to `lj_err_callerv(..., LJ_ERR_BUFFER_BADENC, lj_typename(o))` — `"cannot serialize %s"` (`lj_serialize.c:327-333`, `lj_errmsg.h:192`), with comments `/* NYI userdata */` (line 328) and `goto badenc; /* NYI other cdata */` (line 304). So **functions, threads, full userdata, and non-scalar cdata all error out today**. Decoder side: `BADDEC` "cannot deserialize tag 0x%02x" (line 459), `EOB` (463), `LEFTOV` for trailing bytes in standalone decode (`lj_serialize.c:506`).

**JIT coupling — important for any extension.** The serializer is wired into trace recording: `lj_ffrecord.c:1440-1480` records `buf:encode/decode` and `buffer.encode/decode` as IR calls, and `lj_serialize_peektype` (`lj_serialize.c:509-536`) pre-reads the first tag to pick the IR result type, with the comment "This must match the handling of all tags in the decoder above" (line 515). Any new tag added in-fork must be reflected there (or made to abort recording), otherwise traces speculate wrongly.

## 2. lj_bcwrite.c / lj_bcread.c (read in full)

**What a proto dump contains** — grammar at `lj_bcdump.h:14-29`: per-proto `phead` = flags byte (masked to `PROTO_CHILD|PROTO_VARARG|PROTO_FFI|PROTO_BITOP`, `lj_bcwrite.c:343`), `numparams`, `framesize`, `sizeuv`, then ULEB128 `sizekgc/sizekn/sizebc`, optional debug block (unless `BCDUMP_F_STRIP`, lines 350-358), then raw bytecode, then **upvalue refs as bare uint16s** (`p = lj_buf_wmem(p, proto_uv(pt), pt->sizeuv*2)`, line 362), then GC constants, number constants, debug info.

**Upvalue VALUES are excluded — confirmed.** The only upvalue data written is `proto_uv(pt)`, the uint16 descriptor array whose semantics are "local slot|0x8000 or parent uv idx" (`lj_obj.h:382`, flags `PROTO_UV_LOCAL`/`PROTO_UV_IMMUTABLE` at `lj_obj.h:413-414`). Runtime upvalue values live in separate `GCupval` objects (`lj_obj.h:433-446`: `closed` flag, closed value `tv` or open stack pointer `v` + prev/next chain) pointed to by `GCfuncL->uvptr[]` (`lj_obj.h:465-468`), and neither GCfunc nor GCupval is touched by bcwrite. `string.dump`/`lua_dump` (`lj_load.c:175`) dumps the *proto* only — an Eris-style layer must persist proto (via this machinery or equivalent) **plus** closure identity **plus** upvalue values/sharing separately.

**kgc handling** (`bcwrite_kgc`, lines 199-256): strings inline (`BCDUMP_KGC_STR+len`), **nested protos as a bare `BCDUMP_KGC_CHILD` marker** — children are recursively written *before* the parent (`bcwrite_proto` lines 327-335) and the reader pops them off the Lua stack when it sees CHILD (`lj_bcread.c:254-261`), i.e. the dump is a post-order stream, inherently a tree (protos form a tree, so no ref-tracking needed there). Template tables via `bcwrite_ktab` (153-196); int64/uint64/complex cdata constants via ULEB128 pairs.

**Live-code safety:** `bcwrite_bytecode` un-patches JIT-modified bytecode (`ILOOP/JLOOP/JFORL` etc. back to their generic forms, reading original ins from `traceref(J, rd)->startins`) at lines 301-315 — precedent that dumping protos of *hot, trace-patched* running code is already handled in-tree, which a persist layer gets for free by reusing `lj_bcwrite` (relevant even with `jit.flush` before persist, since flush is what removes traces; the unpatching also covers `PROTO_ILOOP` hot-counting instrumentation).

**Strip vs full:** header flag `BCDUMP_F_STRIP` (`lj_bcdump.h:43`) drops chunkname + lineinfo/uvinfo/varinfo; full dumps keep them (`bcwrite_proto` 350-358, 370-374; `bcread_header` 412-418). For OC persistence, full (non-stripped) is desirable so restored tracebacks keep line info.

**Determinism:** hash-part iteration order of template tables is node order (nondeterministic across builds/runs of table construction) unless `BCDUMP_F_DETERMINISTIC` (0x80000000, `lj_bcdump.h:50`) is passed, which heap-sorts keys (`lj_bcwrite.c:182-185`, sort machinery 84-150). Within one pinned build and one process the dump of a given proto is stable regardless; determinism flag matters only if you want byte-identical dumps for content-addressing.

**Format-version escape hatch:** `lj_bcdump.h:36-38`: "If you perform *any* kind of private modifications to the bytecode itself or to the dump format, you *must* set BCDUMP_VERSION to 0x80 or higher." — Mike Pall's sanctioned protocol for exactly the kind of private-format fork this project is.

## 3. Question 1 — Path A: extend lj_serialize.c in-fork

**What's structurally missing: only the ref map (plus the new object walkers).** Eris's mechanism (verified from https://raw.githubusercontent.com/fnuecke/eris/master/src/eris.c): a Lua table at fixed stack index `REFTIDX` (=2); `persist_keyed()` checks `lua_rawget(L, REFTIDX)` and writes `reference + ERIS_REFERENCE_OFFSET` for already-seen objects; `registerobject()` assigns sequential ids `++(info->refcount)` and `lua_rawseti(L, REFTIDX, reference)`; unpersist keeps the inverse id→obj array and `lua_rawgeti`s on reference tags. Everything that can be shared (tables, protos, upvalues — keyed by `lua_upvalueid` — closures, strings optionally, userdata, threads) goes through it.

**Adding this to lj_serialize's SBuf walk is mechanically feasible.** The walk is a private recursive `serialize_put(w, sbx, o)`; `SBufExt` already carries two GC-ref'd dictionary tables (`dict_str`, `dict_mt`, `lj_buf.h:30-31`) and the metatable path already does raw hash lookups keyed by a GC object (`hashgcref(tabref(sbx->dict_mt), mto.gcr)`, `lj_serialize.c:213`) — so a third `GCRef map_ref` table keyed by object with an id counter is the same pattern, plus a `SER_TAG_REF + id` tag on hit. 13 free tags (0x13-0x1f) are available for `REF/PROTO/FUNCL/UPVAL_OPEN/UPVAL_CLOSED/THREAD/PERM/UDATA-hook` — enough. Real work items beyond the map:

- GC anchoring: the standalone encode path borrows the global tmpbuf with a stack-local SBufExt (`lj_serialize_encode`, lines 485-494); a ref table created mid-encode must be anchored (registry or stack slot) — Eris uses stack slots.
- Thread tag: serialize `L->status`, stack slice `[stack, top)`, and the frame chain by rewriting frame links (`frame_ftsz` delta/type encoding, `lj_frame.h:75-85`: FRAME_LUA/C/CONT/VARG/LUAP/CP/PCALL/PCALLH) into (function-ref, pc-offset, delta, type) tuples, plus `openupval` list (`lj_obj.h:702`) re-linked on restore. Given the OC constraint (suspend only at plain `coroutine.yield`, `cframe == NULL`, no FRAME_C/FRAME_CP live on suspended threads — kernel enforces this), only Lua/VARG/PCALL/CONT frames need round-tripping.
- JIT: new tags must either extend `lj_serialize_peektype` (`lj_serialize.c:509-536`) consistently or the persist entry points must be separate functions that never appear in `lj_ffrecord.c`'s fast paths (much safer: a separate API is invisible to recording).
- Proto encoding: either embed `lj_bcwrite` output as a string payload (writer callback into the SBuf — simplest and reuses the unpatching logic) or re-walk protos natively.

**Scope estimate (path A):** touched files: `lj_serialize.c` (+~1,200-2,000 LOC: ref map, ~6 new put/get pairs, thread walker), `lj_serialize.h`, `lib_buffer.c` (perms-table plumbing in the options table, ~100 LOC), `lj_errmsg.h` (+~6 msgs), `lj_ffrecord.c` (guard), `lj_buf.h` (SBufExt field). Calibration: Eris is ~2,400 LOC total for the same feature set against PUC 5.3, and lj_serialize.c today is 540 LOC / lj_bcwrite 455 / lj_bcread 458. Total new code ~2-3k LOC; core-file *diff* spread across 6 files of the serializer/buffer/JIT surface.

## 4. Question 2 — Path B: sidecar eris-lj.c against private headers

Everything a persist layer must *read* is visible from `lj_obj.h` alone: `GCproto` (372-396), `GCupval` (433-446), `GCfuncL` (465-468), `GCtab`/`Node` (488-509), `lua_State` (692-706), frames via `lj_frame.h`. Public API already covers a surprising amount: `lua_dump` (`lj_load.c:175`), `lua_getupvalue`/`lua_upvalueid`/`lua_upvaluejoin` (`lj_api.c:896-925`) — this is exactly the subset lua-marshal lives on. What genuinely needs internals: open-upvalue enumeration and re-linking, suspended-frame chain + saved PCs, thread stack reconstruction (`lj_state.c` growstack, `lj_func.c` constructors), and interning restored protos (`lj_bcread` is `LJ_FUNC`, reachable when compiled into the library).

**Recommended hybrid (and the honest comparison):** compile `eris-lj.c` **into our pinned LuaJIT build** (one new source file + Makefile/ljamalg line) rather than as an out-of-tree .so — `LJ_FUNC` internals aren't exported from the DLL, so true out-of-tree linkage would force exporting symbols anyway; we ship the build, so in-tree-sidecar costs nothing. This variant:

- **Diff size:** core-file diff ≈ 2 lines of build glue; path A diffs 6 JIT-coupled files. Every future rebase of the pinned commit (security backports etc.) is trivial vs. re-merging a modified `lj_serialize.c` whose tag enum/peektype upstream may touch (the `(yet)` in the docs means upstream *intends* to claim tags 0x13+ for functions/threads eventually — a guaranteed future conflict for path A's tag choices).
- **Safety-by-pinning:** private-struct layout risk is exactly the risk Eris already accepts against PUC (it reads `Proto`/`CallInfo` directly and OC pins its Lua build the same way); with commit 1ee778a4 pinned, GC64-only, two ABIs, layouts are frozen.
- **Format independence:** a sidecar defines its own container (Eris-style header + reftable ids), embedding `lj_bcwrite` dumps as payloads with `BCDUMP_VERSION`-style private versioning per `lj_bcdump.h:36-38`; it does not perturb `string.buffer`'s format, so OC sandbox code can keep using stock `buffer.encode` for data.
- What path A would buy instead — JIT-accelerated encode of the *data* subset inside persisted graphs — is worthless for OC persistence (persist runs once at world-save with the JIT flushed).

Verdict: **Path B (in-tree sidecar file), modeled line-for-line on Eris's persist/unpersist architecture, reusing lj_bcwrite/lj_bcread for protos.** Scope ~2.5-3.5k LOC in one new file, core diff ~nil.

## 5. Question 3 — Prior art sweep

- **[Eris](https://github.com/fnuecke/eris)** / **[OC-Eris](https://github.com/MightyPirates/OC-Eris)** (the actual OC fork): the algorithm template. Reftable at stack index 2, perms protocol (`ERIS_PERMANENT` tag + persist the perms *key*), `p_proto` walks bytecode/constants/children/debug manually, `p_closure` persists upvalue values via `lua_getupvalue` keyed by `lua_upvalueid`, `p_thread` walks stack slots + CallInfo chain (`func/top/nresults/callstatus/savedpc`) + `openupval` + `status` + `errfunc`, C-boundary continuations only for 5.2+ `CIST_YPCALL` k-functions. ~2,400 LOC. Its README states flatly it **won't work on LuaJIT** (relies on PUC internals) — confirming the port must be a rewrite of the *walkers*, keeping the *architecture*.
- **[Pluto](https://github.com/hoelzro/pluto)** (Lua 5.1 ancestor of Eris): same design; [Mike Hadlow's writeup](http://mikehadlow.blogspot.com/2013/04/serializing-lua-coroutines-with-pluto.html) shows suspended-coroutine round-trips in production-ish use on PUC 5.1. Proves the *semantic model* (persist at yield points) that OC adopted.
- **[lua-marshal](https://github.com/richardhundt/lua-marshal)** (Richard Hundt): **the closest thing to LuaJIT closure serialization that actually exists** — serializes tables *with cycles* (its own ref table) and **Lua functions with upvalues** via `lua_dump` + upvalue walk, using only public API, so it runs on LuaJIT. Explicit limits: "Coroutines are not serialized. Metatables and function environments are not serialized"; C functions/threads/userdata without `__persist` raise. What it proves: on LuaJIT, closures+upvalues+cycles need zero private headers; **threads are the only piece that forces internals**.
- **[bitser](https://github.com/gvx/bitser)** / **[binser](https://love2d.org/forums/viewtopic.php?p=187827)** (LÖVE/LuaJIT save systems): data-only. bitser's `register()` stores *named references* for functions/resources — the perms-table idea independently reinvented for LuaJIT games; binser doesn't serialize functions at all. Proves shipping games on LuaJIT persist by *refusing* closures, not dumping them. smallfolk: data-only, safety-oriented (no load-as-code).
- **Don't Starve**: uses modified **PUC Lua 5.1.4, not LuaJIT** ([wiki](https://dontstarve.wiki.gg/wiki/Lua)); saves are data-only; the [DontStarveLuaJIT patch](https://github.com/paintdream/DontStarveLuaJIT) swaps engines without touching saves. Not prior art for closure persistence.
- **Tarantool** (largest production LuaJIT deployment, maintains its own fork): [.snap/.xlog are MessagePack tuple rows](https://www.tarantool.io/en/doc/latest/dev_guide/internals/file_formats/) — snapshots are memtx *data inserts* only; fibers (C-stack coroutines) are never persisted, apps recreate them on restart. A deliberate architectural negative: they chose data-only persistence rather than VM-state capture despite owning their fork.
- **[RaptorJIT](https://github.com/raptorjit/raptorjit)**: auditlog/vmprofile can snapshot raw process memory regions **one-way for offline diagnostics** (Studio decodes them) — proves raw-struct snapshotting of LuaJIT heaps is tractable for *reading*, nothing about restore. **moonjit**: no serialization work, unmaintained.
- **coroutine.clone**: [LuaJIT issue #612](https://github.com/LuaJIT/LuaJIT/issues/612) — Mike Pall (2020-08-27, verbatim from the GitHub API): *"While it would be theoretically possible to create some kind of `coroutine.clone` functionality, it would be quite difficult to get it to work properly under all circumstances. I don't see a real need for it, anyway."* Note the qualifier — "all circumstances" includes C-call boundaries and mid-trace states; OC's constraints (c) and (d) delete precisely those circumstances. Older lua-l threads ([2008-09](https://lua-users.org/lists/lua-l/2008-09/msg00001.html), [2009-09](https://lua-users.org/lists/lua-l/2009-09/msg00139.html)) note LuaJIT 2.x doesn't switch C stacks per-coroutine, making suspended-coroutine capture feasible "with some effort" (search-level, unverified verbatim).
- **Academic**: ALua + luaNua pickling platform ([Skyrme et al., "Exploring Lua for Concurrent Programming"](https://www.inf.puc-rio.br/~roberto/docs/ry08-05.pdf)) does Lua computation migration with **explicit suspension points** — the programmer yields, the platform captures and transfers; [reflection-based capture/restore work](https://arxiv.org/pdf/1010.0371) and continuation-based mobile-agent literature reach the same design. All PUC-based; all converge on "capture only at cooperative yield points," which is exactly OC's yield protocol — independent validation of constraint (c) as the thing that makes this tractable.
- **No LuaJIT fork adding function/coroutine serialization was found** from any search angle (VM snapshot, migration, eris/pluto ports, fork surveys).

## 6. Question 4 — Upstream

- **Velocity:** healthy as of now — GitHub API sample shows a steady commit stream on v2.1 through **2026-08-19** ("Add FOLD rule for ALEN of TNEW/TDUP", "Fix unpack() recording" #1512/#1513, "Compile unpack()", plus ~15 more July-Aug 2026): [commits](https://github.com/LuaJIT/LuaJIT/commits/master). Not a dead project.
- **Contribution pattern:** every commit is authored/committed by Mike Pall; external work appears as *"Thanks to <name>. #NNNN"* — he absorbs fixes as his own patches after review rather than merging PRs. Large feature PRs historically sit for years or are reimplemented (e.g. the [s390x port PR #395](https://github.com/LuaJIT/LuaJIT/pull/395) saga). He [stepped back from full-time maintenance in 2015](https://en.wikipedia.org/wiki/LuaJIT), does no releases, and directs users to v2.1 tip. A multi-thousand-line VM-state-persistence feature from outside has essentially zero precedent of landing.
- **The "(yet)" signal:** `doc/ext_buffer.html:398-400` — "Functions, thread objects, other FFI cdata and full userdata cannot be serialized (yet)." — is genuine intent, but combined with issue #612's "I don't see a real need" (for coroutine state specifically) and **no visible issue/mailing-list WIP** on function/thread encoding found in searches, there is no evidence anyone is working on it or that thread state (vs. plain functions) is even in scope for his eventual design.
- **Realistic assessment:** fork-first is not just pragmatic, it is the *sanctioned* path — `lj_bcdump.h:36-38` explicitly instructs private forks to mark modified formats (version >= 0x80). Conceivably upstreamable someday: a tree-only *function* tag (proto+closed-upvalue-values) matching whatever design the "(yet)" turns into — but our reftable/thread/perms container will be structurally different from anything upstream would accept, so plan for zero upstreaming and a trivially-rebased sidecar instead. The pinned-build + reboot-on-mismatch fallback (OC's existing persistKey/spkey + persist-failure protocol in luac_PersistenceAPI.scala / machine.lua from prior study) is the correct compatibility story.

# KEY CLAIMS
- [high] lj_serialize.c is strictly tree-only with no reference tracking: SBufExt carries only dict_str/dict_mt and a depth counter (lj_buf.h:23-33); shared references are silently re-serialized as copies, and cycles die on the depth counter (LJ_SERIALIZE_DEPTH=100, checked at lj_serialize.c:191) with 'too deep to serialize' — functions/threads/userdata hit the single BADENC catch-all at lj_serialize.c:327-333 marked '/* NYI userdata */'.
- [high] The bytecode dump excludes upvalue values by construction: bcwrite_proto writes only the uint16 upvalue descriptor array ('local slot|0x8000 or parent uv idx', lj_obj.h:382) at lj_bcwrite.c:362; runtime values live in separate GCupval objects referenced by GCfuncL (lj_obj.h:433-468). It also un-patches JIT-modified bytecode of live code (lj_bcwrite.c:301-315), and nested protos serialize as a post-order tree via BCDUMP_KGC_CHILD stack pops (lj_bcread.c:254-261).
- [high] Path B — a sidecar eris-lj.c compiled INTO the pinned build (one new file + build glue, private headers, its own container format, never touching lj_serialize.c) — dominates path A: core diff ~2 lines vs 6 files, no entanglement with the serializer's JIT recording contract (lj_ffrecord.c:1440-1480 / peektype 'must match the handling of all tags', lj_serialize.c:515), no future tag-space collision with upstream's documented intent ('cannot be serialized (yet)', ext_buffer.html:398-400), and lj_bcdump.h:36-38 explicitly sanctions private forks marking their own formats. Estimated ~2.5-3.5k LOC modeled on Eris's ~2.4k.
- [high] Prior art is unanimous that nobody has shipped LuaJIT coroutine serialization: Tarantool snapshots are MessagePack data rows with fiber state never persisted; bitser/binser (LuaJIT game saves) refuse functions or use perms-style registries; RaptorJIT snapshots memory one-way for diagnostics only; no fork adds it. The closest existing artifact is lua-marshal, which serializes closures WITH upvalues and cyclic tables on LuaJIT using only public API (lua_dump + upvalue walk) but explicitly excludes coroutines — so threads are the only component that truly requires private headers.
- [high] Upstreaming is unrealistic and fork-first is effectively sanctioned: LuaJIT is actively maintained (steady commits through 2026-08-19) but Mike Pall self-commits everything, absorbing external work as attributed patches rather than merging feature PRs; on coroutine cloning he wrote (issue #612, 2020, verbatim): 'While it would be theoretically possible... it would be quite difficult to get it to work properly under all circumstances. I don't see a real need for it, anyway.' No issue or list WIP on the docs' '(yet)' for function/thread serialization was found.
