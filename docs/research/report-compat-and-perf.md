## PART 1 — Language compatibility

### 1.1 What LuaJIT 2.1 actually provides (read directly from luajit.org/extensions.html)

**Lua 5.2 features unconditionally enabled:** `goto`/`::labels::`; hex `\x3F` and `\z` string escapes; `load(string|reader [,chunkname [,mode [,env]]])`; `loadfile(filename [,mode [,env]])`; `math.log(x [,base])`; `string.rep(s,n[,sep])`; `string.format` `%q` reversible / `%s` checks `__tostring` / `%a`/`%A`; pattern class `%g`; `io.read("*L")`; `os.exit(status|true|false[,close])`; `package.searchpath`; various `debug.getinfo/getlocal/getupvalue` enhancements; `debug.upvalueid/upvaluejoin`; C-API additions (`lua_loadx`, `luaL_loadbufferx`, `luaL_traceback`, ...).

**Only with `-DLUAJIT_ENABLE_LUA52COMPAT`:** `goto` as reserved word; `__len` for tables + `rawlen()`; `pairs`/`ipairs` checking `__pairs`/`__ipairs`; `coroutine.running()` two results; `string.find` nil for out-of-range init; **`table.pack()` and `table.unpack()`**; `io.write` returning file handle; detailed `os.execute` status; `debug.setmetatable` returns object; `debug.getuservalue`/`setuservalue`; `package.searchers`.

**Lua 5.3 extras in 2.1:** `\u{XX...}` escapes; `io.read` formats without leading `*`; `assert()` with any error object; **`table.move`**; **`coroutine.isyieldable()`** (+ `lua_isyieldable`).

**LuaJIT-only relevant extras:** `xpcall(f, err [,args...])` passes arguments (5.1 stock does not); built-in `bit.*` (Lua BitOp: `band/bor/bxor/bnot/shifts/rol/ror/bswap/tohex`); `table.new`/`table.clear`; "fully resumable VM": *"you can yield across pcall() and xpcall(), across iterators and across metamethods"*; `string.dump(f [,mode])` with strip/deterministic/cross-format modes.

**Backported LuaJIT 3.0 syntax (current 2.1 rolling only):** *"Bit Operators: unary ~, binary & | ~ << >> ~>>"*, plus `!`, `&&`, `||`, `!=`, ternary `?:`, `?.`, `??`, compound assignment, `continue`, `const`. Explicitly **not** backported: *"bit operator metamethods, floor division operator //, compound assignment metamethods"*. Note: *"Bytecode that uses a bit operator can only be loaded by LuaJIT 2.1.1784535649 or higher"* — i.e. a mid-2026 rolling build; exact 32-vs-64-bit semantics of these operators were not verifiable from the page and must be tested before relying on them for a `bit32` shim.

**Missing vs 5.2/5.3 (confirmed absent from the page):** `_ENV` (*"LuaJIT is API+ABI-compatible with Lua 5.1, which prevents implementing features that would otherwise break the Lua/C API and ABI (e.g. _ENV)"*), the **integer subtype**, `string.pack/unpack/packsize`, `math.type/tointeger/maxinteger/mininteger/ult`, the `utf8` library, `bit32` library, `//` operator, ephemeron semantics.

### 1.2 What GTNH OC's machine.lua actually requires (direct inspection of `src/main/resources/assets/opencomputers/lua/machine.lua`, 1548 lines)

The kernel's compat layer is remarkably thin — it targets 5.2/5.3/5.4 with graceful degradation, not hard requirements:

- **Version adaptation:** `local isLuaOver54 = _VERSION:match("5.4")` / `isLuaOver53` (lines 65–66). `isLuaOver54` is used **exactly once** (line 563, an `init`-argument nuance in the pure-Lua `gmatch` port). Everything else degrades via `X = lib and {...}` or `f = f or fallback`: `bit32 = bit32 and {...}` (965), `utf8 = utf8 and {...}` (1033), `math.atan2 or math.atan` / `math.ldexp or fn` / `math.pow or fn` (922–942). 5.3 sandbox entries `string.pack/unpack/packsize` (901–903), `math.maxinteger/mininteger/tointeger/type/ult` (957–961), `table.move` (914), `coroutine.isyieldable` (882) are plain references that are simply **nil on 5.2 already** — so their absence under LuaJIT is a state OC/OpenOS already supports. `sandbox._VERSION` falls back to reporting `"Lua 5.2"` for anything that isn't LuaJ/5.3/5.4 (line 812) — LuaJIT would masquerade as 5.2 with zero changes.
- **Hard requirements LuaJIT satisfies:** `table.pack/table.unpack` used pervasively (spcall 691, invoke 1080–1103, main loop 1533...) and `rawlen` (773) → need **LUA52COMPAT build** (or tiny pure-Lua shims); `load(ld, source, mode, env)` with env param (754–758) → LuaJIT extension covers it (no `_ENV` needed — OC sandboxes via load's env parameter, never via `_ENV` upvalue manipulation; zero `_ENV` references exist in machine.lua or OpenOS); `xpcall(f, msgh, ...)` with extra args (813–839) → LuaJIT extension; error objects that are tables (`tooLongWithoutYielding`, line 44) → fine; `debug.sethook(thread, hook, "", count)` per-coroutine count hooks (21, 47, 718, 847, 1532) → API exists in 5.1/LuaJIT but see Part 2 for the JIT interaction problem; `coroutine.running()` (47) → fine (kernel always runs inside a coroutine); `debug.getinfo/traceback/getlocal/getupvalue` (1001–1030) → present; `collectgarbage("collect")` every 10 resumes is **skipped when `persistKey` is nil** (1524–1530, the LuaJ path a LuaJIT arch would take).
- **Notable kernel design point:** machine.lua ships a **pure-Lua port of the PUC pattern matcher** (lines 86–686) used for strings ≥ `SHORT_STRING = 500` chars so timeouts apply during matching. Under LuaJIT this hot pure-Lua code is exactly what the JIT compiles well.
- **The host↔kernel protocol never yields across a C boundary.** Direct component calls return normally (or return 0 results on `LimitReachedException`), and the *Lua* code then does `coroutine.yield(function() ... end)` for synchronized calls (machine.lua 1080–1103; `NativeLuaArchitecture.runSynchronized` / `LuaJLuaArchitecture.runThreaded` show the same closure-yield protocol). So LuaJIT's lack of `lua_yieldk`/continuations is a non-issue for OC — unlike ComputerCraft, where this forced "hacky things" in CCLuaJIT.

### 1.3 OpenOS scan (`loot/openos`, 129 .lua files)

- **Zero uses of `//` integer division; zero `goto`.**
- **Bitwise-operator syntax appears in exactly one file:** `lib/bit32.lua` — a pure-Lua bit32 reimplementation *for Lua 5.3* using `<< >> & | ~` (*"prepopulated with the existing global bit32 in 5.2"*). Under LuaJIT the global `bit32` doesn't exist, so this file must load; the current 2.1 rolling parses those operators, but a safer port is a ~100-line shim over LuaJIT's built-in `bit.*` (normalizing signed BitOp results to bit32's unsigned range with `% 2^32`). Only consumer found: `lib/uuid.lua`.
- **All 5.3-isms are guarded:** `math.maxinteger or math.huge` (init.lua:7, bios.lua:50, install_basics.lua:119); `utf8 and utf8.codepoint(...) or charOrCode:byte()` (lib/keyboard.lua:49). Text/terminal handling uses OC's **host-provided `unicode.*` API** (machine.lua 1454–1489), not the `utf8` library.
- `table.pack/unpack` in 34 files (covered by LUA52COMPAT); `xpcall(fn, handler, args...)` in bin/rc.lua, boot/90_filesystem.lua, init.lua (covered by LuaJIT's xpcall extension); no `debug.sethook`, no `string.pack` dependence.

**Part 1 verdict:** LuaJIT 2.1 built with `LUAJIT_ENABLE_LUA52COMPAT` covers machine.lua + OpenOS almost entirely. Port cost ≈ a `bit32` shim, `_VERSION`/cosmetics, and testing around number formatting (no integer subtype means `string.format("%d", 2.5)` and `1/2 == 0.5` behave like 5.2 doubles — the profile OC already supports as "Lua 5.2", where `bit32` computers likewise have no integer subtype). The existing 5.2/5.3/5.4 compat layer is so thin that "extending down" to 5.1+ext is days, not months, of Lua-side work. The heavy cost is host-side (Part 2 / persistence).

### 1.4 Persistence

- **Eris cannot work on LuaJIT — authoritatively.** fnuecke/eris (the OC author's own library, the one compiled into OC's JNLua natives) README: it *"won't work with other Lua implementations, such as LuaJIT, because Eris works directly on some internal structures of vanilla Lua and uses non-API macros and functions."* No LuaJIT port of Eris/Pluto-style coroutine persistence exists; LuaJIT's suspended-coroutine stacks, upvalues and its incompatible bytecode format would require a from-scratch serializer against unstable internals. **OC-style transparent persistence is not realistically achievable on LuaJIT.**
- **But OC already ships the fallback pattern.** `LuaJLuaArchitecture.save()` is empty and `load()` just does `machine.stop(); machine.start()` (LuaJLuaArchitecture.scala 254–261) — LuaJ computers simply **reboot on chunk-unload/world-load**. machine.lua supports this natively: `[persistKey and persistKey() or "LuaJ"]` (line 1061) — with no `persistKey` global the whole Eris special-persist machinery is bypassed. A LuaJIT architecture would declare itself non-persistent exactly like LuaJ. (Also: `debug.disablePersistence` is a supported OC config for native archs.)
- **Registration is public API, no OC fork needed:** `li.cil.oc.api.Machine.add(Class<? extends Architecture>)` (src/main/java/li/cil/oc/api/Machine.java:33) + `@Architecture.Name` annotation (cf. `NativeLua52/53/54Architecture`, LuaStateFactory.scala). A LuaJIT addon mod registers a fourth architecture and users pick it per-CPU (OC's shift-rightclick arch switching).

## PART 2 — Performance reality check

### 2.1 Raw LuaJIT vs PUC interpreter speedups

- vs **Lua 5.3**: array-access benchmark 0.95 s → 0.07 s (**~13.6×**); N-queens integer benchmark 5.83 s → 0.58 s (**~10×**). vs **Lua 5.4**: ~10.3× and ~6.8× respectively (eklausmeier.goip.de Pallene/Lua/LuaJIT comparison, 2020). LuaJIT lands within ~2–3× of unoptimized C in the same tables.
- Micro-benchmarks (gitspartv.github.io/LuaJIT-Benchmarks, vs Lua 5.1): JIT-on **~2–11.5×** (string concat 11.5×, table init 4.8×, locals 4.3×); **interpreter-only ~1.9–3.9×**. The interpreter floor matters because sandbox-hostile code (see 2.3) may run un-JITted.
- In-Minecraft precedent: **CCLuaJIT** (sci4me, Jan 2019, ComputerCraft forums) measured **"~10-13x speedup"** on a SHA-256 Lua benchmark inside MC. (The vereena0x13/CCLuaJIT repo is now stripped to README+LICENSE — 3 files on `main` per GitHub API — so the forum thread is the surviving technical record.)
- Realistic overall expectation for OC compute-bound programs: **3–15× typical, more on tight numeric loops, ~2–4× worst-case (interpreter-only)** — string/table/GC-heavy code sits at the low end, numeric/bit code at the high end.

### 2.2 How much of an OC program is actually Lua execution? (verified in GTNH source)

OC's throttling is component-call-based, and it dominates I/O-style programs:

- **Direct calls** consume a per-tick budget: `consumeCallBudget(1.0/annotation.limit)` or explicit costs; over budget → `LimitReachedException` → machine.lua converts it into a **synchronized call** (Machine.scala 286–294, 385–402; machine.lua 1080–1103). Budget = `callBudgets` averaged over CPU/memory tiers: **[0.5, 1.0, 1.5]** per tick (application.conf), reset each tick (`callBudget = maxCallBudget`, Machine.scala:532).
- **GPU costs** (GraphicsCard.scala 64–69): `set` 1/64–1/256, `copy` 1/16–1/64, `fill` 1/32–1/128 by tier → a T3 CPU + T3 GPU maxes at **384 `gpu.set`/tick ≈ 7,680/s**; T1+T1 at **32/tick**. After that the call degrades to synchronized.
- **Indirect/synchronized calls** run on the main server thread, effectively **one per tick (50 ms)** per computer (SynchronizedCall protocol in runThreaded, both architectures).
- Signals: queue capped at 256 (`maxSignalQueueSize`); `pullSignal` is a plain yield. Scheduler adds `executionDelay: 12` ms between slices; `timeout: 5.0` s is the no-yield watchdog limit.

**Consequence:** for terminal/network/disk/robot programs (the majority of casual OC use), wall-time is set by budgets and tick alignment — **LuaJIT ≈ 0% gain**. LuaJIT pays off where the 5-second timeslices are actually CPU-bound: crypto (SHA/AES in Lua), compression (deflate ports), image/ANSI rendering pipelines *before* the gpu calls, emulators (CHIP-8/GB interpreters exist for OC), pathfinding, and OC's own pure-Lua long-string pattern matcher (machine.lua 86–686). Those programs today burn multiple 50 ms server-tick-adjacent slices; 10× less CPU per slice also directly reduces executor-thread load on GTNH servers.

### 2.3 Does the JIT survive OC's yield-heavy execution model? Yes — but OC's watchdog design must change

- **Traces persist across yields/resumes.** The trace cache lives in the per-VM `jit_State J` inside `GG_State` alongside `global_State` and the hot-counter table (lj_dispatch.h:89–102; `GCRef *trace` array, `maxtrace` default 1000, lj_jit.h). Nothing in coroutine resume/yield or `lua_resume` flushes traces — flushes happen only via `jit.flush`, engine mode changes, or trace-table exhaustion (lj_trace.c). So compiled traces survive OC's per-slice resumes for the lifetime of the computer's Lua state.
- **`coroutine.yield`/`resume` themselves are never trace-compiled**: in lib_base.c they are `LJLIB_ASM(coroutine_yield)` / `LJLIB_ASM(coroutine_resume)` with **no `LJLIB_REC` recording handler** (lib_base.c 613/636) — each yield exits to the interpreter and re-enters traces afterwards. Fine at OC granularity (yields every few thousand+ instructions); fatal for gains in loops that call components every iteration (consistent with 2.2).
- **The blocker: machine.lua keeps a count hook armed during all sandbox execution** (`debug.sethook(co, checkDeadline, "", hookInterval)` before every resume — lines 847, 1532). In LuaJIT v2.1, verified in source:
  1. Every hook invocation **aborts any in-progress trace recording**: `lj_trace_abort(g); /* Abort recording on any hook call. */` (lj_dispatch.c:372).
  2. A count/line hook forces `DISPMODE_INS`: the whole dynamic dispatch table becomes `lj_vm_inshook` (lj_dispatch.c:97–146) — a permanently slower, hook-checking interpreter path.
  3. **Compiled traces never check hooks or decrement the hook count** unless built with `-DLUAJIT_ENABLE_CHECKHOOK` (lj_record.c ~2953): *"Regularly check for instruction/line hooks from compiled code and exit to the interpreter if the hooks are set. This is a compile-time option and disabled by default... Note this is only useful if hooks are *not* set most of the time. Use this only if you want to *asynchronously* interrupt the execution. You can set the instruction hook via lua_sethook() with a count of 1 from a signal handler or another native thread."*
  Net effect of running machine.lua unmodified on LuaJIT: `while true do end` compiles to a self-contained loop trace, the deadline hook never fires, the `"too long without yielding"` kill never happens, and an OC executor thread hangs forever — an unacceptable griefing vector. And "fixing" it by keeping the hook set with CHECKHOOK enabled would make every trace immediately exit to the interpreter, killing the JIT.
- **The correct design (matches LuaJIT's own Ctrl-C handler and CCLuaJIT's approach):** remove the always-armed Lua-side count hook for this architecture; run a Java watchdog that, when the 5 s deadline expires, calls `lua_sethook(L, hook, MASKCOUNT, 1)` **asynchronously from another thread**, with LuaJIT built with `LUAJIT_ENABLE_CHECKHOOK` so even in-trace loops take the exit promptly. machine.lua already contains the count=1 escalation pattern (line 47) for post-deadline enforcement. CCLuaJIT's author described exactly this workaround: *"set a debug hook with a count of 1 at the time when a Lua thread needs be yielded"*. Cost: CHECKHOOK adds a small per-loop check in compiled code (Mike Pall: "may be quite expensive in tight loops" — but it is the price of preemptibility), and normal execution runs hook-free at full interpreter+JIT speed (also removing today's `DISPMODE_INS` interpreter tax).

### 2.4 JNI boundary and integration cost

- OC's native architectures already cross **JNI on every host call**: JNLua is a JNI binding (vendored as `li.cil.repack.com.naef.jnlua`, natives from BlueAmulet/JNLua-Natives with Lua 5.2/5.3/5.4 + Eris compiled in). A LuaJIT architecture bound the same way adds **no new class of per-call overhead** vs today's Lua 5.2/5.3 archs — the JNI hop (sub-microsecond) is noise next to OC's budget system (hundreds of direct calls/tick max) and 50 ms synchronized calls. CCLuaJIT shipped native LuaJIT binaries with a JNI-style bridge for CC on this same premise and still netted 10–13×.
- Port work on the C side: JNLua's 5.2+ backend uses 5.2 C-API calls (`lua_arith`, `lua_compare`, `lua_rawlen`, ...) which LuaJIT (5.1 API+ABI) lacks — either shim them or start from the older Lua 5.1-targeting JNLua lineage; LuaJIT does provide `luaL_loadbufferx`, `lua_loadx`, `luaL_traceback`, `lua_isyieldable` (extensions.html C-API list).
- **Memory limiting** (`limitMemory` / `lua.setTotalMemory`, NativeLuaArchitecture.scala 152–163) relies on JNLua's counting allocator. Verified in lj_state.c (v2.1): `lua_newstate(allocf, allocd)` **is** exported and honors a custom allocator on GC64 builds (the modern x64 default; only `LJ_64 && !LJ_GC64` hides it), with the `checkptrGC` 47-bit address constraint — so JNLua-style memory capping is portable, with care (JIT mcode areas are allocated outside the Lua allocator and won't be counted). Fallback: `gcinfo()`-polling enforcement. `ramScaleFor64Bit: 1.8` already exists to tune per-arch RAM scaling.
- Platform natives: LuaJIT must be built per OS/arch like JNLua-Natives already is; LuaJIT 2.1 supports the same win/linux/mac x86/x64 (+ARM) matrix, and GC64 bytecode incompatibility between 32/64-bit is irrelevant since OC loads machine.lua from source (`mode="t"` unless `allowBytecode`).

### 2.5 Bottom line

Feasible as a **non-persistent addon architecture** (LuaJ-style reboot-on-reload), registered through the public `Machine.add` API, using LuaJIT 2.1 + `LUA52COMPAT` (+ ideally `CHECKHOOK`) with: a bit32 shim, a rewritten watchdog (async `lua_sethook` count=1 from a Java timer instead of an always-on count hook), and a JNLua-for-5.1 JNI layer. Language compatibility is a small, well-bounded problem because OC already targets a 5.2 floor with graceful degradation. Persistence is the one hard "no" (Eris is PUC-internals-bound), and performance gains are real but sharply bimodal: ~an order of magnitude on compute-bound code, ~nothing on component-bound code, with server-CPU relief as a secondary benefit.

# KEY CLAIMS
- [high] LuaJIT 2.1 lacks _ENV, the integer subtype, string.pack/unpack/packsize, math.type/tointeger/maxinteger, the utf8 and bit32 libraries, and the // operator, but provides goto, xpcall-with-args, load with mode/env, coroutine.isyieldable, table.move, yield-across-pcall/metamethods, table.pack/table.unpack and rawlen under LUAJIT_ENABLE_LUA52COMPAT, and (current 2.1 rolling builds) backported & | ~ << >> bit operators.
- [high] GTNH OC's machine.lua and OpenOS have no hard dependency LuaJIT+LUA52COMPAT cannot meet: no _ENV, goto, or // anywhere; utf8, math.maxinteger, string.pack and bit32 are all optional/guarded (nil already under the supported Lua 5.2 profile); the only active porting items are a bit32 shim (lib/bit32.lua uses 5.3 operator syntax) and heavy table.pack/unpack + rawlen + xpcall-with-args + load-env usage that LuaJIT's extensions cover.
- [high] OC-style persistence is not achievable on LuaJIT — the Eris README states it won't work with LuaJIT because it uses vanilla Lua internals — but OC ships a working non-persistent precedent: LuaJLuaArchitecture.save() is empty and load() reboots the machine, and machine.lua's persistKey-nil path already bypasses all Eris machinery.
- [high] OC's timeout watchdog (an always-armed debug.sethook count hook around every resume) is incompatible with the JIT: LuaJIT aborts trace recording on any hook call (lj_dispatch.c: 'Abort recording on any hook call'), compiled traces never check hooks unless built with LUAJIT_ENABLE_CHECKHOOK (lj_record.c comment), and with a permanently-set hook CHECKHOOK would evict every trace — so the watchdog must be redesigned as an asynchronous lua_sethook(count=1) from a Java timer thread, the pattern LuaJIT's own source recommends and CCLuaJIT used.
- [medium] Expected gains are bimodal: roughly 3-15x for compute-bound OC programs (LuaJIT measured ~10-13.6x vs PUC Lua 5.3 on numeric/array benchmarks, ~2-4x interpreter-only floor, and CCLuaJIT measured ~10-13x on SHA-256 inside Minecraft) and approximately zero for component-bound programs, because GTNH OC caps direct calls via a per-tick budget of 0.5/1.0/1.5 (e.g. max 384 T3 gpu.set per tick) and forces indirect calls to one per 50 ms server tick.
