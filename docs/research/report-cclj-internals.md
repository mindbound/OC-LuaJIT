## (1) LuaJIT embedding: JNI bridge, state mapping, value conversion

**Design.** One hand-written C++ translation unit, `src/main/cpp/LuaJITMachine.cpp` (811 lines), compiled to `cclj.{so,dll,dylib}` and dynamically linked against a stock LuaJIT shared lib. The Java side is `gay.vereena.cclj.computer.LuaJITMachine implements ILuaMachine, ILuaContext` with six native methods (`LuaJITMachine.java:131-141`): `createLuaState`, `destroyLuaState`, `registerAPI`, `loadBios`, `resumeMainRoutine`, `abort`.

**State-per-computer.** Each CC `Computer` gets its own `lua_State`: the `LuaJITMachine` constructor calls `createLuaState(ccVersion, mcVersion, ThreadLocalRandom.nextLong())` (`LuaJITMachine.java:121-129`). The C++ stores the raw `lua_State*` and the main-coroutine `lua_State*` into Java `long` fields `luaState`/`mainRoutine` via `SetLongField` (`LuaJITMachine.cpp:523-537`, field IDs cached at cpp:632-633). The machine `jobject` is reachable from Lua via a registry entry: lightuserdata key `REGISTRY_KEY_MACHINE` → `jobject_ref` userdata holding a JNI global ref, with a `__gc` metamethod that deletes the ref (cpp:131, 151-177, 722-724). `JNI_OnLoad` (cpp:547-658) caches ~20 classes and method IDs (Number.doubleValue, Double.valueOf, Map/Iterator plumbing, `ILuaObject.getMethodNames/callMethod`, machine fields, etc.).

**State setup** (`createLuaState`, cpp:686-731): opens only `base, math, string, table, bit` (cpp:692-696) — no `io`, `os`, `package`, `debug`, `ffi`, and notably no `jit` library (but the JIT compiler itself stays on; there is **no** `luaJIT_setmode` call anywhere). Sets `_VERSION="Lua 5.1"`, `_CC_VERSION`, `_MC_VERSION`; nils out `collectgarbage`, `gcinfo`, `newproxy` (cpp:709-714); installs a global `__inext` C helper (cpp:143-149, used by CC's `ipairs` replacement in bios); seeds `math.randomseed` with a Java-supplied long.

**Value conversion — eager deep copy at every boundary crossing** (no lazy proxies):
- Java→Lua `to_lua_value` (cpp:269-302): `null`→nil; any `Number`→`doubleValue()`→`lua_pushnumber`; `Boolean`; `String` via `GetStringUTFChars`→`lua_pushstring`; `byte[]` is malloc'd, NUL-terminated and pushed with `lua_pushstring` (cpp:283-294 — **embedded NUL bytes truncate the string**; should be `lua_pushlstring`); `Map`→recursive `map_to_table` with an `IdentityHashMap` tracking in-progress maps so cyclic/shared tables map to the same Lua table (cpp:197-227); `ILuaObject`→`wrap_lua_object`; anything else → Lua error "Attempt to convert unrecognized Java value...".
- Lua→Java `to_java_value` (cpp:313-363): number→`Double.valueOf`; boolean→`Boolean.valueOf`; string→copied to `byte[]`→`LuaJITMachine.decodeString(bytes)` which decodes **US_ASCII** (`LuaJITMachine.java:103-105`); table→`table_to_map` building a `HashMap` with cycle tracking via a scratch Lua table mapping table→lightuserdata-jobject (cpp:229-267); **functions, threads, userdata all raise Lua errors** — no cross-boundary function values.
- Java API objects become plain Lua tables of C closures: `wrap_lua_object` (cpp:501-521) iterates `getMethodNames()` and binds each name to `invoke_java_fn` closed over a `JavaFN{machine, obj, index}` userdata (global refs, `__gc` finalizer cpp:470-499). `invoke_java_fn` (cpp:402-468) converts all args, calls `ILuaObject.callMethod(context, index, args)` once via cached jmethodID, converts Java exceptions into `lua_error` with a `"short_src:line: message"` prefix built from `lua_getinfo(L, "Sl")` (cpp:427-451), and converts results back.
- `registerAPI` (cpp:742-761) wraps the API table and `lua_setglobal`s it under each `getNames()` entry. `loadBios` (cpp:763-777) does `lua_newthread` + `luaL_loadbuffer(..., "bios.lua")` — the bios chunk on a fresh coroutine is the "main routine". `resumeMainRoutine` (cpp:779-802) pushes args, `lua_resume(L, nargs)`; on `LUA_YIELD`/`0` returns the stack delta as `Object[]`, on error returns `[Boolean.FALSE, errorValue]`.

## (2) Sandboxing, limits, aborting runaway code

- **No instruction counting, no memory accounting.** Limits are wall-clock, enforced by `TaskScheduler.TaskExecutor.execute()` (`TaskScheduler.java:238-307`): wait **7000 ms** for task completion (line 253); if not done → `computer.abort(false)` (soft), wait **1500 ms**; then `computer.abort(true)` (hard), wait **1500 ms**; then `this.runnerThread.interrupt(); this.runnerThread = null; done = true;` (lines 286-290) — i.e. the runner thread is **abandoned** and replaced. A thread stuck inside native LuaJIT code ignores `interrupt()` and keeps burning a core forever.
- **Abort delivery** (`LuaJITMachine.java:236-251` → native `abort`, cpp:804-807): Java sets `volatile softAbortMessage` (and `hardAbortMessage` if hard), then native does `lua_sethook(main_routine, thread_interrupt_hook, LUA_MASKCOUNT, 1)` — a **one-shot count hook with count=1**. The hook (cpp:179-195) immediately unregisters itself (`lua_sethook(L,0,0,0)`), fetches the machine jobject from the registry, and calls `try_abort` (cpp:373-389) which consumes `softAbortMessage` and raises it as a `lua_error` — surfacing as "Too long without yielding"-style errors in the resumed coroutine. After the resume returns, Java `handleEvent` destroys the Lua state if `hardAbortMessage` was set (`LuaJITMachine.java:216-218`).
- **The trace problem and its (partial) mitigation.** Nothing in the codebase disables the JIT (no `luaJIT_setmode`, no `jit.off()`), so LuaJIT-compiled traces — which never poll debug hooks — will not observe the count hook until control returns to the interpreter. Two things make aborts mostly work anyway: (a) `invoke_java_fn` calls `try_abort` at the top of **every** Java-API call (cpp:412), and calls to C functions are not compiled into traces, so every CC API touchpoint is an interpreter-mode abort checkpoint; (b) in LuaJIT (unlike PUC 5.1) hook state lives in `global_State`, so a hook set on `main_routine` fires in whatever nested coroutine is actually running. The residual hole: a **pure-Lua compiled infinite loop that never calls a Java function can dodge both mechanisms**, leaving only the abandon-the-thread fallback. This is the key lesson for an OC LuaJIT architecture: you need either periodic `jit.flush`/trace-exit forcing, `LUAJIT_ENABLE_CHECKHOOK`-style patches, or acceptance of thread abandonment.
- **Sandboxing is by omission** (libs not opened, globals nil'd). One deliberate weakening: `FIX_STRING_METATABLES = true; // @TODO: un-hackify this` (`LuaJITMachine.java:28`) makes `loadBios` **strip the entire bios.lua section between** `"-- Prevent access to metatables or environments of strings"` and `"-- Install lua parts of the os api"` (`LuaJITMachine.java:158-187`) — i.e. CC's string-metatable protection is removed because it breaks under LuaJIT, reopening that sandbox hole.
- **No per-computer memory limit whatsoever** — plain `luaL_newstate()`, no `lua_setallocf` quota (contrast with OC/JNLua, which meters allocations for configured RAM sizes).

## (3) Coroutines / yielding across the JNI boundary

Lua 5.1/LuaJIT cannot `lua_yield` across an active C call (no `lua_yieldk` continuations), so CCLJ never yields from inside `invoke_java_fn`. Instead:

1. **Java-side blocking.** `LuaJITMachine` itself implements `ILuaContext`. When peripheral Java code calls `pullEvent(filter)`/`yield(...)` (`LuaJITMachine.java:274-313`), the machine **blocks the executor thread** (`yieldResultsSignal.wait()`) until a matching event arrives. Only "special events" (see PullEventScanner below) are permitted: a non-registered filter throws `"Attempt to call yield with an event filter that is not registered"` (line 293), and a filterless yield throws `"Attempt to yield but no filter was provided!"` (line 311).
2. **Synchronous special-event routing.** The ASM-patched `Computer.queueEvent` checks `PullEventScanner.isSpecialEvent(event)` and, if true, calls `machine.handleEvent` **directly on the caller's thread**, bypassing CC's queue (`ComputerTransformer.transformQueueEvent`, `ComputerTransformer.java:63-89`). `handleEvent` stashes such events in a synchronized `ListMultimap yieldResults` and notifies the sleeping thread (`LuaJITMachine.java:205-211`).
3. **Deferred real yield via one-shot hook.** On wake-up, `yield()` sets `volatile yieldRequested = true` and queues a null event (`LuaJITMachine.java:299-300`), then returns results to the Java API method, which returns through JNI into `invoke_java_fn`. That C function sees `yieldRequested`, clears it, and arms `lua_sethook(L, thread_yield_request_handler_hook, LUA_MASKCOUNT, 1)` (cpp:457-460); it then pushes the results as the Lua call's return values. One VM instruction later the hook fires, unhooks itself, and executes a genuine `lua_yield(L, 0)` (cpp:391-394) — cleanly unwinding `lua_resume` with `LUA_YIELD`. The previously queued null event then re-resumes the coroutine through the normal task path, and execution continues right after the API call with its results already delivered.
4. **Scheduler cooperation.** While a machine is parked in `yield()`, `TaskScheduler.notifyYieldEnter` marks that executor blocked and frees the single "running" slot so **other computers keep executing** (`TaskScheduler.java:88-110`); `notifyYieldExit` re-activates it. This whole scheduler exists because stock CC 1.7x ran all computers on one `ComputerThread` that a blocked pullEvent would deadlock.

## (4) What the ASM transformers patch (and what OC's Architecture API would obviate)

`CCLJClassTransformer` (FML coremod, registered in `CCLuaJIT.java:26-28`) applies three transformers:

- **`ComputerTransformer`** (targets `dan200.computercraft.core.computer.Computer`): (a) `transformInitLua` rewrites the `NEW dan200/computercraft/core/lua/LuaJLuaMachine` + `INVOKESPECIAL <init>` pair to instantiate `gay/vereena/cclj/computer/LuaJITMachine` instead (`ComputerTransformer.java:26-61`) — needed **only because CC 1.7x hard-codes its machine class**; (b) `transformQueueEvent` injects the special-event bypass described above.
- **`ComputerThreadTransformer`** (targets `dan200.computercraft.core.computer.ComputerThread`): **guts the class** — clears all fields, deletes all methods except `<init>`, and rewrites `queueTask`/`start`/`stop` bodies to delegate to `TaskScheduler.INSTANCE` (`ComputerThreadTransformer.java:20-68`) — replacing CC's single-threaded computer executor with CCLJ's blocking-aware multi-executor scheduler.
- **`PullEventScanner`** (targets *every* loaded class, `clazz() == null`): scans all methods of all classes for `INVOKEINTERFACE ILuaContext.pullEvent/pullEventRaw(String)` preceded by an `LDC` string constant, and registers that constant as a special event (`PullEventScanner.java:39-59`). If the filter is not a compile-time constant it **throws** `"Found call to pullEvent(raw?) but could not determine its event filter!"` — a fragile heuristic covering third-party peripheral mods. `"task_complete"` is pre-registered (line 30).

**OC relevance:** every one of these hacks addresses something OpenComputers' Architecture API already provides cleanly — `li.cil.oc.api.Machine.Architecture` is a registered, pluggable interface (no constructor patching); OC owns its own multi-threaded executor pool with per-machine `runSynchronized`/direct-call semantics (no ComputerThread gutting, no scheduler replacement); and OC's signal-queue + `machine.invoke` callback model never lets arbitrary Java block inside a Lua resume (no pullEvent scanning). A clean OC port needs **zero ASM**; the C++ bridge plus a yield protocol adapted to `ExecutionResult.Sleep`/`SynchronizedCall` is the whole job.

## (6) Persistence

**None.** `saveState(OutputStream)` and `restoreState(InputStream)` both `return false;` (`LuaJITMachine.java:253-261`). The `ILuaMachine` interface (src/api/.../ILuaMachine.java:25-27) has the hooks, but CC never used them for LuaJ either — CC computers simply reboot on chunk unload/server restart, so CCLuaJIT inherited a world where persistence was not required. **There is no Eris/Pluto-style serialization anywhere in this codebase**, and nothing here answers how to persist a LuaJIT VM (LuaJIT has no upstream Eris port; its coroutines contain raw C stacks/trace state that Eris-style heap serialization was never built for). For OC — whose contract is Eris-persisting the whole machine state across saves — this is the single biggest gap CCLuaJIT does not address; an OC LuaJIT architecture would have to either mark itself non-persisting (reboot on load, as OC's LuaJ fallback architecture effectively degrades to) or invent new persistence machinery.

## (7) Known limitations, TODOs, thread-safety, memory

- **In-code TODOs:** `LuaJITMachine.java:28` (`un-hackify` the bios string-metatable strip), `:116` (`Do we really need to differentiate hard and soft any more?`), `:141` (pass abort message directly to native to drop the registry machine ref), `TaskScheduler.java:13` (`cancel all tasks when world unloads? or something similar`), `:304` (on InterruptedException: `what are we to do here?`), `CCLJClassTransformer.java:16` (OSAPI queueEvent sentinel for special-event collisions), `LuaJITMachine.cpp:419` (`should we do the exception check before or after servicing yield requests?`).
- **Thread model:** one global `TaskScheduler.INSTANCE` for all computers; a dispatcher thread plus a soft-reference cache of `TaskExecutor`s, each owning a controller thread and a runner thread. Only **one** task executes at a time (`dispatchTask` throws `"Attempt to dispatch parallel ITask!"`, `TaskScheduler.java:142-143`) *except* that executors blocked in pullEvent release the slot — so effective parallelism = 1 running + N parked. `BinarySemaphore` is a minimal monitor-based signal (`BinarySemaphore.java:1-24`). `finalize()` calls `unload()`→`destroyLuaState` potentially from the GC thread — a latent race against a live state.
- **Correctness edges:** `byte[]`→Lua uses `lua_pushstring` on a NUL-terminated copy → binary payloads with embedded `\0` truncate (cpp:288-291); Lua→Java strings decode as US-ASCII only (`LuaJITMachine.java:103-105`); all numbers collapse to `Double`; Lua functions/threads/userdata cannot cross the boundary at all (cpp:345-356); yields require statically-known constant event filters (PullEventScanner) — dynamic filters crash class transformation.
- **Runaway-code fallback leaks threads** (abandoned runner spinning in a compiled trace, see §2). No memory caps (see §2). No benchmarks exist anywhere in the repo; the README claims only "in the interest of performance" with no numbers (`README.md:5`).

## Takeaways for an OC-LuaJIT architecture (grounded in this code)

1. The JNI bridge pattern is proven and compact (~800 lines C++): state-per-machine, eager value marshalling with cycle detection, Java callbacks as C closures, resume/yield as the only control-flow crossing. OC's `Architecture`/`Machine.invoke` maps onto this more cleanly than CC did — no ASM required.
2. The abort story is the hard part CCLuaJIT only half-solved: count hooks + per-callback checks work for API-touching code, but JIT-compiled pure-Lua loops are un-interruptible without extra measures; OC's stricter timeslicing would need `jit.flush`-on-abort, a patched LuaJIT with trace hook checks, or watchdog thread abandonment.
3. OC-style persistence is completely unaddressed here and has no known LuaJIT solution; a LuaJIT OC architecture should plan for "computers reboot on world load" semantics.
4. OC-style memory limits are also unaddressed (no `lua_setallocf` quota); LuaJIT additionally complicates this because its allocator/GC arena assumptions differ from PUC Lua (custom allocfs are restricted on 64-bit LuaJIT).
5. Ship model (Docker cross-compile to 3 desktop x86_64 targets, gzip in jar, temp-extract + `System.load`) mirrors what JNLua-Natives already does for OC, so packaging is a solved problem — but ARM64 (Apple Silicon servers/clients) needs adding.

# KEY CLAIMS
- [high] CCLuaJIT embeds LuaJIT through a single ~811-line JNI C++ bridge (src/main/cpp/LuaJITMachine.cpp) with one lua_State per CC computer stored as a raw pointer in Java long fields; all values are eagerly deep-copied at the boundary (Numbers→lua_Number/Double, tables↔HashMap with cycle detection, Java API objects exposed as Lua tables of C closures over JNI global refs), and Lua functions/threads/userdata cannot cross at all.
- [high] Runaway-code control is wall-clock only (7000ms then soft abort, +1500ms hard abort, +1500ms then Thread.interrupt and abandon the runner thread, TaskScheduler.java:253-290), delivered via a one-shot LUA_MASKCOUNT/count=1 debug hook set by the native abort() plus a try_abort check at the entry of every Java-API C closure; the code never disables or flushes the JIT (no luaJIT_setmode/jit.off anywhere), so its abort mechanism relies on interpreter-mode execution at C-function boundaries.
- [high] Yielding across JNI is implemented by blocking the Java executor thread inside ILuaContext.pullEvent/yield until a matching 'special event' arrives (special events are dispatched synchronously via an ASM-patched Computer.queueEvent), then forcing a real lua_yield through a second one-shot count hook armed after the JNI call returns (yieldRequested field, LuaJITMachine.cpp:457-460, 391-394); special-event filters must be compile-time string constants discovered by scanning every loaded class's bytecode (PullEventScanner).
- [high] CCLuaJIT has zero Lua-state persistence (saveState/restoreState both return false, LuaJITMachine.java:253-261) and zero memory-limit enforcement (plain luaL_newstate, no lua_setallocf accounting); CC computers simply reboot, so neither OC requirement is addressed anywhere in this codebase.
- [high] Natives are cross-compiled in one fedora:29 Docker container (clang for Linux, mingw64 for Windows, osxcross/MacOSX10.11 SDK for macOS) for x86_64 only, shipped gzipped inside the jar and temp-extracted + System.load'ed at class-init; and the repo itself is a low-maturity 2024 re-upload whose source arrived in a commit titled 'Copy old files; needs fixed.', with the 1.7.10_CC and 1.12.2_CC branches containing byte-identical src/ trees.
