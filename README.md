# OC-LuaJIT

A LuaJIT-based CPU architecture addon for [GTNH OpenComputers](https://github.com/GTNewHorizons/OpenComputers) (Minecraft 1.7.10).

Adds a **LuaJIT** architecture selectable with shift+right-click on any OC CPU, alongside the stock Lua 5.2/5.3/5.4 and LuaJ options — additive, never a replacement for any of them.

**Persistence is NOT the trade.** An earlier version of this file said LuaJIT computers would reboot on chunk reload, like OC's LuaJ fallback. That premise was disproved: `serializer/eris_lj.c` persists and restores a full LuaJIT state, suspended coroutines and live for-in loops included, through OC's own `PersistenceAPI`. The harness boots OpenOS 1.8.9, persists it, restores it into a fresh workspace and asserts the machine *resumed* — same boot nonce, counter still counting.

**Status: runs in Minecraft and in the harness; not released.** Since 2026-09-16 the mod has run in a real GTNH-based instance on OpenComputers 1.12.61-GTNH and 1.12.64-GTNH: OpenOS boots on it with the JIT on, and a machine persists across save-and-quit, a live REPL with an open file included — see [docs/in-game-tests.md](docs/in-game-tests.md). Under [ocelot-brain](https://gitlab.com/cc-ru/ocelot/ocelot-brain), real operating systems boot on the same VM, driven by **our own `Architecture` and our own `LuaState` class**, with OpenComputers' stock PUC-Lua 5.2 native loaded alongside in the same JVM:

| run | what it establishes |
|---|---|
| OpenOS 1.8.9, smoke suite | boots to a shell, **persists and resumes** (same boot nonce, counter still counting), the deadline watchdog fires and the machine survives, the RAM cap holds and OOMs at the cap, the bytecode gate refuses, a `1LL` literal is a syntax error, `string.pack` is in the sandbox and behaves as our Lua 5.3.6 port, with its two decided deviations, 5.3's bitwise operators compute 5.3.6's 64-bit results in the sandbox and raise past 53 significant bits, file handles a program drops unclosed are disposed and free their slots, live, after a restore and at a save — 82 checks, 0 failures (2026-10-17, JIT on) |
| AxisOS, census | boots to a login prompt over 14000 ticks, emergency collector refusing nothing |

Both run on `ocljit.arch.OCLuaJITArchitecture` over the additive `libjnluajit52` library, which is the shape the mod ships. Both rows, like every in-game run so far, are on Windows. The smoke suite has since passed on the release Linux library too, built on glibc 2.28 (below): in AlmaLinux 8 under JDK 8, every arm of the suite gives the same checks and verdicts as on Windows (82 checks, 0 failures, for the shape the mod ships), and in Ubuntu 26.04 under JDK 17 the shipped shape gives 82 checks, 0 failures, both under WSL (2026-10-19). No Minecraft client or server has loaded the Linux library yet (see the roadmap). The same suite also runs in two control arms — our VM as a drop-in under OpenComputers' own 5.2 architecture, and stock PUC-Lua 5.2 as a baseline — and each arm refuses the others' fingerprint.

The mod-side adapter is the same construction, compiled against the pinned OpenComputers jar (1.12.58-GTNH) and run in game on 1.12.61 and 1.12.64. Its jar carries the patched watchdog kernel under our own asset domain and loads it in place of OpenComputers' after `initialize()`. What is still open, release blockers included, is in [docs/roadmap.md](docs/roadmap.md).

## Lua dialect

The LuaJIT architecture runs LuaJIT 2.1 with its Lua 5.2 compatibility switched on. It has **no FFI**: the native is built without it, so there is no `ffi` module, and LuaJIT's 64-bit and imaginary number literals (`1LL`, `2ULL`, `0x10ULL`, `3i`) are a syntax error, `malformed number`. (PUC Lua 5.2 and 5.3 have no such literals either: they read `1LL` as the number `1` followed by the name `LL`, which is usually a different syntax error, such as `<eof> expected near 'LL'`.) The reason is persistence: an FFI value cannot be saved, and one alive when the world saves would cost the computer its state ([docs/ffi-decision.md](docs/ffi-decision.md)).

Our LuaJIT is a fork, and it takes Lua 5.3 functions where they fit. Its string library has Lua 5.3's `string.pack`, `string.unpack` and `string.packsize`, with Lua 5.3.6's whole format language and 5.3.6's results and errors, checked against PUC Lua 5.3.6 by a conformance suite and a differential fuzzer, apart from two decided deviations, one choice of the port and what the VM decides. The deviations: every number is still a double, so an unpacked integer that needs more than 53 bits comes back as the nearest double of the 64-bit integer 5.3.6 computes (unsigned 8-byte formats, `I8`, `J`, `L` and `T`, wrap to negative first, as in 5.3.6: eight `ff` bytes are -1), and it is refused only where 5.3.6 refuses, a field wider than 8 bytes that does not fit in 64 bits (Plan9k's GPT scan reads such fields from every drive). And `l`/`L` are 8 bytes on every platform, so a format means the same bytes on every server (PUC uses the C `long`, 4 bytes on 64-bit Windows). The port's choice: a string given to a numeric option converts by 5.3.6's rules, but through LuaJIT's numeral scanner, so a numeral with 2^20 or more digits after the point (trailing zeros aside) or an exponent of 2^20 or more is refused where 5.3.6 reads it.

What the VM decides stays LuaJIT's: NaN payloads; at most about 8000 results per call; numbers given to `c`/`s`/`z`, which LuaJIT formats (`string.pack('z', 100000000000000)` gives `1e+14` here, `100000000000000` in 5.3.6); a result over the RAM cap, refused as `not enough memory`, after every argument check; and function names, positions and method argument numbers in error messages, which are LuaJIT's for every library function (through a tail call the name and the position are lost and a method's argument number shifts). [test/native/pack/deviations.txt](test/native/pack/deviations.txt) lists the cases that show them and the scanner's, apart from the over-cap refusal, which `test/native/pack_test.c` checks, and the function names, which the suites normalise away. Like `table.move` and `coroutine.isyieldable`, which LuaJIT already had, the three are there for programs that test for them, and such a program now takes its 5.3 path here: Plan9k's FAT driver does, and so inherits a bug in that path, one it has on OpenComputers' own Lua 5.3 architecture too (`mkdir` on a FAT12 image fails with `unsigned overflow` on an odd free cluster, after the directory entry is written; the roadmap's string.pack row has the detail).

The fork also has Lua 5.3's bitwise operators, `&`, `|`, `~` (binary and unary), `<<` and `>>`, with Lua 5.3.6's 64-bit integer semantics in the parser's constant folding, the interpreter and the JIT: `1 << 32` is 4294967296, `1 << 63` is -2^63, `-1 >> 63` is 1 (`>>` is logical), a shift by 64 or more gives 0, and a negative count shifts the other way. Every result that does not raise is exactly 5.3.6's, checked against PUC Lua 5.3.6 by a conformance matrix, a differential fuzzer and a generator of JIT-compiled loops (`test/native/run-bitop.sh`, `run-bitfuzz.sh` and `run-bitjit.sh`). The operators' one deviation, decided: every number is still a double, which holds an integer exactly only up to 53 significant bits, so a result with more than 53 significant bits raises instead of returning a value 5.3.6 would not, naming its operator and the usual remedy: `result of '|' has more than 53 significant bits (mask each operand to 32 bits first)`.

Every operator gives an exact result when its operands are non-negative and below 2^32, whatever the shift count, so masks, bytes, 24-bit colours, CRC32 and xorshift32 compute as in 5.3.6. A raise therefore always has an operand outside that range, and the commonest is a shifted value that meets another operator before it is masked. **5.3's usual 32-bit rotate raises here.** In `((x >> n) | (x << (32 - n))) & 0xFFFFFFFF` the `|` joins the two pieces into up to 64 - n significant bits before the mask can drop the high ones, so a right rotation by 1 to 10 raises for most words (by 2, 6 and 7, SHA-256's own counts, for 82-99% of random 32-bit words; by 10, for a quarter), and so does the left rotation `((x << n) | (x >> (32 - n))) & 0xFFFFFFFF` by 22 to 31. A right rotation by 11 to 31, or a left one by 1 to 21, never raises (written this way, a right rotation by 0 joins all of `x << 32` and raises too). So unmodified 5.3 code that rotates like this, SHA-256 written for 5.3 among it, raises here, where PUC Lua 5.3 computes it, and where this fork's earlier 32-bit operators happened to compute it too (their shifts dropped the high bits, and the result came back in BitOp's signed 32-bit form). The remedy is one mask, on the shifted piece, before the `|`: `(x >> n) | ((x << (32 - n)) & 0xFFFFFFFF)` for the right rotation and `((x << n) & 0xFFFFFFFF) | (x >> (32 - n))` for the left never raise for x in [0, 2^32), and give PUC 5.3.6's results. The other common case is `>>` of a negative number, which 5.3 shifts as 64 bits: `-1 >> 1` raises, and so does `(n >> 8) & 0xFF` for most negative `n`, -2 or -256 among them, at the `>>`. The remedy is the same, to mask to the width you mean first: `((n & 0xFFFFFFFF) >> 8) & 0xFF` is exact, and equal to 5.3.6's. 5.3's `math.maxinteger` idiom, `~0 >> 1`, raises too (2^63 - 1 has 63 significant bits); `~0 >> 11`, 2^53 - 1, computes.

An operand converts as in 5.3.6: a double with an integer value in [-2^63, 2^63), or a string that 5.3.6 reads as one, through the same reader as `string.pack`'s (`"3" & 1` is 1, `"0x10" | 0` is 16, and a hex string wraps modulo 2^64, so `"0xffffffffffffffff" | 0` is -1). Anything else raises: 1.5, NaN, inf and 2^63 with 5.3.6's `number has no integer representation`, and any other value, such as nil or a table, with 5.3.6's `attempt to perform bitwise operation on a nil value` (or `a table value`). Where the message names a variable, the word order is LuaJIT's (`on local 't' (a table value)`, where 5.3.6 says `on a table value (local 't')`), and it names fewer operands than 5.3.6 does (5.3.6's `number (field '?') has no integer representation` is `number has no integer representation` here). The type name is LuaJIT's too, so a metatable's `__name` is not used: with `t = setmetatable({}, {__name = 'Foo'})`, `t | 1` says `on local 't' (a table value)` here and `on a Foo value (local 't')` in 5.3.6, whose naming this fork's `string.pack` does follow (`string.pack('i4', t)` says `got Foo` on both); LuaJIT's own arithmetic errors name a table the same way (`t + 1`). The parser folds a constant expression only when its operands convert and its result is exact, so `1.5 & 1` and `~0 >> 1` compile and raise when they run (5.3.6 does the same with `1.5 & 1`). LuaJIT's own extensions follow the same rules: the compound assignments (`x <<= 40` gives 2^40) and `~>>`, an arithmetic right shift that no other OC CPU parses (a count of 64 or more fills with the sign: `-1 ~>> 64` is -1). `bit32` is unchanged, OC's Lua 5.2 library, 32-bit (`bit32.lshift(1, 32)` is 0).

What 5.3's integers give beyond that is not here. There is no integer subtype: a result is a double, `tostring` prints one of 1e14 or more in `%.14g` form (`1 << 47` prints `1.4073748835533e+14`; `string.format('%d', 1 << 47)` gives `140737488355328`), and arithmetic between the operators is double arithmetic, exact only up to 2^53. So an algorithm whose sums or products pass 2^53 cannot match 5.3: a 64-bit hash or SHA-512, and also a 32-bit hash that multiplies a word by a large constant, which then gives a wrong value without an error, because the double product is rounded before the mask sees it (FNV-1a's `((h ~ b) * 16777619) & 0xFFFFFFFF` hashes `hello world` to 4030533980 here and to 3582672807 in 5.3.6). An algorithm whose values pass 53 significant bits raises even if it only shifts and xors: xorshift64 (`x = x ~ (x << 13)`, `x = x ~ (x >> 7)`, `x = x ~ (x << 17)`) raises at its second step from seed 1. A 32-bit algorithm whose sums and products stay below 2^53 matches 5.3 when it masks each shifted piece, or each operand, to 32 bits before the next operator, as the rotate's remedy above does. LuaJIT's lexer reads a numeric literal as the nearest double, so a hex literal with more than 53 significant bits is rounded, silently, before any operator sees it: `0x00ff00ff00ff00ff & 0xff` is 0 here and 255 in 5.3.6, and `0xffffffffffffffff` (2^64), `0x7fffffffffffffff` and `0x8000000000000000` (both 2^63) raise as operands, where 5.3.6 reads -1, `math.maxinteger` and `math.mininteger`. A string operand with an exponent of 2^20 or more is not a number here, the same scanner residual as `string.pack`'s (`"1e-1048576" | 0` raises the type error; 5.3.6 gives 0). And there are no bitwise metamethods (`__band`, `__bor`, `__bxor`, `__shl`, `__shr`, `__bnot`): such an operand raises the type error, where 5.3 would first look for one; they are planned, with `//` ([docs/roadmap.md](docs/roadmap.md)). [test/native/bitop/deviations.txt](test/native/bitop/deviations.txt) lists the conformance cases that differ from PUC Lua 5.3.6, and why. The operators alone do not let MineOS boot here: its `Libraries/Color.lua` takes its 5.3 path on any architecture not named "Lua 5.2", and that path needs `//` (the roadmap's MineOS row). The sandbox's `_VERSION` still says 5.2, and there is no `utf8`, no `math.type`, `math.tointeger` or `math.maxinteger`, no integer subtype and no `//`.

## Building

Requires a JDK 17+ to run Gradle (the mod itself compiles to Java 8 bytecode via the GTNH toolchain):

```bash
./gradlew build
```

Dev-run the client with OpenComputers present:

```bash
./gradlew runClient
```

### Natives

The jar carries one native for each supported platform, windows-x86_64 and linux-x86_64. `native/build-native.sh` builds each on its own platform (the Windows DLL under Git Bash with MinGW-w64, the Linux .so on Linux; its header lists what each needs), and with `OCLJ_VARIANT=additive` it leaves the library in `build/native/dist/`, from where `./gradlew build` packages it.

**LuaJIT is pinned to one upstream commit, written in one file:** `native/luajit/upstream.commit`, the full 40-digit hash. `make -C prototype/watchdog luajit-src` clones LuaJIT into `prototype/watchdog/luajit` and checks that commit out.

- **What a build compiles.** `build-native.sh` needs git and refuses a LuaJIT checkout whose HEAD is any other commit (naming both commits and the file). It exports that commit's tree from the checkout's git history and checks it object by object against the 40 digits, so the LuaJIT source is that commit's files byte for byte, up to a SHA-1 collision. It then changes the tree with its twelve patch scripts (`native/luajit/`) and compiles it with its own flags. Anything that would change the exported files (a git filter or line-ending attribute, an export-ignore, a forged object) stops the build, a replace ref is ignored, and a local edit in the checkout is named in a warning and not built.
- **The environment.** The compiler, make and linker variables on the script's list (`CFLAGS`, `CPATH`, `MAKEFLAGS`, `MAKEOVERRIDES`, `LIBRARY_PATH` and the rest, in any letter case) are dropped, and the build log names the ones it dropped. The list is what was found to change the build, not every name make or gcc can read.
- **The toolchain is not pinned.** The release DLL is built with MinGW-w64 gcc 16.2.0 (WinLibs) and the release .so with AlmaLinux 8's gcc 8.5.0; another compiler gives other bytes.
- **What a build may touch.** Every directory the script is given is taken at its physical path before the script checks it and its tools use it, and on Windows a path with a name ending in a dot or a space is refused. The build removes only the three directories it remakes in its build directory and files of its own names, and writes files of its own names only. It refuses a checkout inside those three directories, a build directory inside the LuaJIT checkout or inside the repository outside `build/` (the repository `OCLJ_REPO` names, and the one the script lives in), and an output directory inside a `dist` directory. So it removes or overwrites no file of the checkout or of the repository, and only a pinned additive build replaces the library in `build/native/dist/`.
- **What the checks guard against.** Accidents and plausible configurations: a wrong or stale checkout or build copy, local edits, git configuration and attributes, the environment variables on the list, and directories named through symlinks, junctions, `..` or another letter case. Deliberate tampering by someone who can edit `build-native.sh` itself is out of their scope. What they leave is listed in the guide's open question 15.
- **Experiments.** `OCLJ_LUAJIT_UNPINNED=1` builds the checkout's working tree instead, at any commit and with any edits, with a warning, for local experiments only. Such a native names the commit `unpinned` in its blob fingerprint, so its saved machines and a pinned native's cannot restore on each other; it is not collected into `build/native/dist/`, and `./gradlew build` refuses to package it.
- **The jar build** checks every native's commit against the file, whatever the native was built with. To move the pin, see section 8.2a of [docs/jit-guide.md](docs/jit-guide.md).

**The Linux .so is built on glibc 2.28.** A Linux library can need symbol versions as new as the glibc it was linked against: the .so we linked on Ubuntu 26.04 needed glibc 2.38, and would not have loaded on Ubuntu 22.04, Debian 12 or RHEL 9. So the release .so is built on an AlmaLinux 8 host (ours is AlmaLinux 8 under WSL), with the floor enforced:

```bash
OCLJ_GLIBC_MAX=2.28 OCLJ_VARIANT=additive OCLJ_JNLUA=/path/to/OC-JNLua \
  OCLJ_JNI=/usr/lib/jvm/java-1.8.0-openjdk/include sh native/build-native.sh
```

For players, the supported systems are x86_64 Linux with glibc 2.28 or newer: RHEL, AlmaLinux and Rocky Linux 8 and later, Debian 10 and later, Ubuntu 20.04 and later. That list comes from those distributions' glibc versions; the library has been tested on AlmaLinux 8 and Ubuntu 26.04. The 2.28 floor is a policy, which the jar build enforces: today's release library needs only glibc 2.17, but older systems are untested and unsupported. Where the system's glibc lacks a version the library needs, the dynamic loader refuses it, so the LuaJIT CPU is not offered there, and OpenComputers' own CPUs are unaffected. Windows is unaffected by any of this.

A Linux build on a newer distribution, Ubuntu for instance, is a development build. `build-native.sh` finishes it and reports which glibc version the .so needs. Give such a build its own `OCLJ_BUILD`, so that its .so never lands in `build/native/dist/`. `./gradlew build` reads the glibc versions every packaged .so needs and refuses one that needs more than 2.28, or that imports a symbol with no version. The floor's evidence and its checks are in the glibc row of [docs/roadmap.md](docs/roadmap.md), and the build details in [docs/jit-guide.md](docs/jit-guide.md) section 7.7.

## Layout

- `src/main/java/io/github/astronfo/ocluajit/` — mod entry point ([OCLuaJIT.java](src/main/java/io/github/astronfo/ocluajit/OCLuaJIT.java)) and the architecture ([arch/](src/main/java/io/github/astronfo/ocluajit/arch/)), which is a subclass of OpenComputers' own `NativeLuaArchitecture` plus a `LuaStateFactory` — not an implementation of `Architecture` from scratch.
- Natives ship inside the jar at `assets/opencomputers/lib/` — **OpenComputers'** asset namespace, not ours. `native/build-native.sh` builds them into `build/native/dist/`, `build.gradle.kts` stages them into the jar, and no binary is checked in. The path is not a preference: it is where OC's `LuaStateFactory` resolves a library from the classpath, and we inherit its loader rather than write one; the filename `libjnluajit52-*` is ours alone. Seen working in game since 2026-09-16: OpenComputers' own loader logs `Found a compatible native library` for our file. The patched kernel ships beside it under our own domain, at `assets/ocluajit/lua/machine.lua`. See [docs/research/shipping-model.md](docs/research/shipping-model.md).
